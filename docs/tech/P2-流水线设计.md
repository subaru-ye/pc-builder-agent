# P2 单进程三 Agent 流水线 — 实现设计

> 本文是 **P2 实现层设计**:编排拓扑、各 Agent 提示词 SOP 骨架、tool 契约、Loop 控制与错误恢复、上下文工程约定。
>
> 口径边界:**schema 冻结在[设计方案](../装机Agent设计方案.md) §四.1/§四.2,本文不重定义**,只引用;规则表见设计方案 §五;目录布局唯一出处 mvp.md §4.4。开工前对照[工程实践指引](工程实践指引.md) §九 P2 检查单。冲突时以设计方案 + mvp.md 为准。

## 1. 目标与范围

- **DoD(用例 A)**:dev UI 输入「8000 元 2K 玩黑神话」,一轮对话产出全 pass 配置单 + 快照日期 + 人话解释报告。
- **范围内**:初筛 / 生成 / 校验三 Agent,Sequential + Loop 编排;生成 Agent 用**纯 SQL 结构化过滤**选件(不等 embedding);校验 Agent 将 P1 引擎包装为 tool;Loop 有最大轮数、重复 SKU 检测、熔断。
- **范围外**(去向):pgvector 语义候选 → P3;版本落库 / 快照日期绑定持久化 → P4(P2 报价用最新快照即时合计,不落库);A2A 跨进程 → P5;Redis 会话状态 → P6(P2 用进程内内存)。

## 2. 编排拓扑

单进程,ADK-Go 编排;所有 Agent 与工具在 `internal/agents`,入口在 `cmd/host`。

```
SequentialAgent(root)
├── 初筛 Agent(LLM 低价档)          user 对话 → RequirementSpec
└── LoopAgent(max_rounds=N)
    ├── 生成 Agent(LLM 旗舰档)       RequirementSpec(+上轮失败报告)→ BuildDraft
    │     └── tool: 结构化选件检索(SQL,零 LLM)
    └── 校验 Agent(零 LLM)          BuildDraft.selection → ValidationReport
          └── tool: 规则校验(包装 internal/rules)
                ↓ escalate: overall_status == pass|review 即出栈
出口翻译(LLM):ValidationReport + 报价合计 → 人话报告
```

- **初筛在 Loop 外**:需求澄清是一次性收敛,不参与重试回路(工程实践指引 §八.2:移交只传结构化事实)。
- **Loop 体 = 生成→校验一对**(proposer-reviewer,工程实践指引 §五.1)。校验产出即 Loop 的停止信号载体。
- **出口翻译**:可作为 Loop 后的一个 LLM 步骤,或复用初筛 Agent 的会话上下文;实现当日按 ADK-Go 编排原语最省的方式接,但**报告数字一律来自 ValidationReport 与 DB,不由翻译步骤重算**。

## 3. Agent 职责与提示词 SOP

提示词随代码入 Git、确定性渲染;**静态前缀(system prompt + tool 定义)冻结,动态信息(时间戳、快照日期、当前需求单、上轮失败报告)一律尾部追加,绝不嵌进 system prompt**(工程实践指引 §二.1)。

### 3.1 初筛 Agent(低价档模型)

- 职责:多轮对话 → 冻结的 `RequirementSpec`(设计方案 §四.2);追问缺失字段、消解冲突。
- SOP(分步,写死顺序):
  1. 必须问齐 `budget_cny` 与 `use_case.type`;gaming 追加问 `resolution`(缺失不得产出 RequirementSpec)。
  2. 依次补 `noise_pref` / `size_pref` / `existing_parts`;用户未提及则取缺省(any),不硬逼。
  3. 冲突消解:预算与目标明显失配(如 5000 元要 4K 光追)→ 主动降低预期并说明,不静默妥协。
  4. 字段齐备 → 输出结构化 RequirementSpec,移交生成 Agent。
- 依据:工程实践指引 §二.2(SOP 化,追问顺序写死);§六.4(评测用用户模拟器渐进透露,追问能力是被测对象)。

### 3.2 生成 Agent(旗舰档模型)

- 职责:RequirementSpec(+上轮失败报告)→ `BuildDraft`(设计方案 §四.2);调结构化选件检索 tool 拿候选,组装八大件。
- **预算分配写死数字区间**(不写「合理分配」这类模糊话,工程实践指引 §二.2):

  | 主用途 | GPU | CPU | 主板 | 内存 | SSD | 电源 | 机箱 | 散热 |
  |---|---|---|---|---|---|---|---|---|
  | gaming | 35–45% | 15–20% | 8–12% | 6–10% | 6–10% | 6–9% | 4–8% | 3–6% |
  | productivity | 20–30% | 25–35% | 8–12% | 10–15% | 8–12% | 6–9% | 4–8% | 3–6% |
  | general | 0–15%(可核显) | 15–22% | 8–12% | 8–12% | 8–12% | 6–9% | 4–8% | 3–6% |

  `priority` 命中的品类在区间内取上沿;`existing_parts` 命中的品类不选件、其预算并入 `priority` 首项。区间为指引非硬约束,最终由校验 + 报价合计裁定。
- **改单/重试输入**:Loop 第 2+ 轮把上一轮 `ValidationReport` 中 fail/unknown 的具体项(哪条规则、哪个件、observed 值)原样追加进上下文,要求定向换件(工程实践指引 §四.5:反馈越具体自纠越好)。
- 输出 BuildDraft;`rationale` 每件一句、`budget_allocation` 自报——均为纯展示字段。

### 3.3 校验 Agent(零 LLM)

- 职责:取 `BuildDraft.selection` → `store.ResolveBuild` → `rules.NewDefaultEngine().Validate` → `ValidationReport`;附报价合计。
- **本 Agent 不含 LLM**:它是一个把 P1 引擎与 store/报价包成 ADK tool 的确定性节点(工程实践指引 §五.1、§八.3:确定性断链器,结论覆盖上游任何 Agent 自评)。`internal/agents` 中校验相关代码同样受 depguard 约束不得 import LLM 包(与 `internal/rules` 一致的零 LLM 边界)。
- 报价:P2 用 `store.LatestSnapshot` 取最新快照即时合计;报告带 `snapshot_date`,不落库(落库归 P4)。缺价 SKU 优雅降级(合计标注「N 件缺价」),不阻断校验。

## 4. Tool 契约

工具描述从 Agent 视角写:边界 + 2–3 个调用示例 + 协作关系(工程实践指引 §四.2);参数保真,禁止静默转换/截断(§四.3/§四.4)。

### 4.1 结构化选件检索 tool(SQL,零 LLM)

- 用途:按**硬约束**从 parts 表结构化过滤候选(插槽/板型/内存代数/品牌/价格带),供生成 Agent 选件。软偏好(安静/颜值)P2 不做,留 P3 语义路径。
- 输入(结构化):`category`(必填,八类枚举)+ 过滤条件(如 `socket=AM5`、`price_max`、`brand`、`form_factor`)+ `top_n`。
- 输出:结构化候选列表 `[{sku, brand, model, 关键参数摘要, price_cny}]`,按性价比或价格排序;**超出 top_n 显式注明「另有 X 条被截断」**,严禁静默截断。
- 边界:只接受结构化条件,不接受自然语言;硬约束永远走 SQL(工程实践指引 §七.1)。

### 4.2 规则校验 tool

- 用途:包装 §3.3 的确定性校验,把 BuildDraft 变成 ValidationReport + 报价。
- 输入:BuildDraft(或其 `selection` 部分)。
- 输出:设计方案 §四.1 的 `ValidationReport` + 报价块(`snapshot_date` / `total_cny` / 缺价计数)。
- 保真:未知 SKU、schema error 作为工具错误显式返回,不静默吞。

## 5. Loop 控制与错误恢复

- **三停止条件**(命中即出栈,工程实践指引 §五.2):
  1. 校验 `overall_status ∈ {pass, review}`(review = 仅 warning/unknown,可交付并提示);
  2. 达到最大重试轮数 N(建议 N=3,实现时定为常量);
  3. 不可恢复错误(数据缺失导致无候选、DB 不可达)。
- **重复 SKU 检测**:连续两轮生成回到**完全相同的 selection** 视为死循环,立即出栈(§五.2)。
- **错误分类 → 策略映射表**(§五.3):

  | 错误类型 | 策略 | 熔断 |
  |---|---|---|
  | LLM 超时/限流 | 指数退避重试 | 独立上限 |
  | BuildDraft schema 校验失败 | 原样重试无意义,回喂错误要求改输出 | 计入 Loop 轮数 |
  | 规则 fail(error 级) | 回喂具体失败项,定向换件 | 计入 Loop 轮数 |
  | 规则 unknown / warning | 不算错误,直接进报告(不触发重试) | — |
  | 无候选 / DB 不可达 | 不可恢复,立即熔断 | 即时 |
- **熔断后如实出栈**(§五.4):重试烧完带着最后一版 ValidationReport 与失败原因面向用户,不硬撑、不展示假成功。
- **成本三件套**(§五.5):单会话 token 预算上限;LLM/检索结果 P2 用**进程内 map** 缓存(P6 迁 Redis);模型分档已定(初筛低价、生成旗舰),分档效果用端到端成本验证。

## 6. 会话状态块(P2 精简版,P4/P6 扩展)

即便 P2 是单轮,也由 Go 代码维护结构化状态块并注入上下文末尾,不让模型从历史里数(工程实践指引 §三.1):

- 当前 RequirementSpec 摘要(预算、主用途、关键偏好);
- 当前 BuildDraft 草稿与报价 vs 预算余量;
- Loop 读数配操作策略:注入「重试第 k/N 轮」时同时写明「到 N 轮带失败报告出栈」(§三.3)。

P2 状态放进程内内存;跨进程共享(Redis)是 P6 的事,字段口径此处先立,P6 直接搬。

## 7. 目录与包边界

遵循 mvp.md §4.4:

```
cmd/host/          # 初筛 Agent + 内置 launcher(dev UI)入口;P2 起挂载完整流水线
internal/agents/   # 初筛 / 生成 / 校验三 Agent、编排、tool、提示词(随代码入 Git)
internal/rules/    # P1 已有,零 LLM,不动
internal/schemas/  # RequirementSpec / BuildDraft(§四.2)在此新增,单一出处
internal/store/    # P1 已有;P2 增结构化候选检索查询
```

- **零 LLM 隔离**:`internal/rules` 与 `internal/agents` 中的校验节点由 golangci-lint depguard 兜底,禁止 import LLM 相关包。
- **schema 单一出处**:RequirementSpec/BuildDraft 只在 `internal/schemas` 定义,字段变更回写设计方案 §四.2。

## 8. 测试与验收

- **用例 A 端到端**:dev UI 手动演示为主;可另写脚本驱动一轮对话。
- **Pass@k 而非单次**(工程实践指引 §六.1):含 LLM 的端到端用例单跑一次通过不算数,同配置跑 3–5 次全过才算稳定。
- **轨迹 + 最终状态双验证**(§六.3):既看报告是否全 pass,也确认选件真实来自 DB 候选(非幻觉 SKU)。
- **回归**:提示词改动跑一遍用例 A 当回归(§二.3);P1 golden set 不受影响(校验逻辑不变)。
