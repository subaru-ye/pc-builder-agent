## A1 取消级联 ×2:通过

- **早期取消**:confirm 后立即 `POST .../runs/{id}/cancel`,3 秒内落 `interrupted` 终态。SSE 重放序列:`run.started → requirement.confirmed → run.progress → assistant.completed → run.cancelled → run.completed`;`run.completed` payload(base64)解码为 `{"status":"interrupted"}`。
- **工具阶段取消**:confirm 后等 12 秒再取消,`run.progress` payload 为 `{"label":"正在检索兼容配件","sequence":2,"stage":"remote_progressing"}`,证明取消时已进入检索工具阶段;序列同样合规。
- 全库 `agent_runs` 无 `running` 残留(count=0);session `active_run=null`;取消后会话可继续发消息(http 202)并可再次 confirm。
- 限制:buildsvc 不输出取消轮询专有日志,证据以行为终态与 SSE 序列为准。

## 新发现(记录,不阻断)

1. **中断 run 不落用量指标**:两个被取消的 build run 的 `model_calls/tool_calls/tokens` 均为 NULL——取消路径不写 `CompleteRun` 统计列,成本核算会系统性低估取消 run 的实际消耗。
2. **wind-down 后收口效率低**:8000 对照中,工具阶段被截断后模型连续 7 轮未输出合规最终 JSON,8 轮打满后走额度耗尽兜底。弱模型对收口指令的契约遵循不足;候选改进方向(另行提案,不在本批改):收口轮反馈中附上一次解析失败的具体原因。
3. **穷举型任务成本形态**:诱导二 31.4 万 tokens/8 轮打满是 runstats 应盯的重成本样本;全局上限兜底有效,无失控。
