# Spec：Screening 提示词保守精简与配对验证

## 执行状态

本文件仅定义待实施实验。本轮不改实际提示词、不生成精简候选、不启动模型测试、不替换生产版本。后续明确启动本 spec 后再形成候选与执行计划。

## 目标与假设

在保持当前合同和历史失败防线的前提下，减少 Screening 静态主提示词的重复表达，提高阅读和维护清晰度，并实测输入 token、费用及延迟是否改善。

历史工作台所见主提示词约 8,025 字符。字符数本身不是缺陷，也不等于模型 token 数；约 20% 的压缩仅作为探索目标，不作为必须达到的验收门槛。为达到字数而删除必要约束不可接受。

本实验只尝试一个保守候选。结果可能是“可替换”“保留原版”或“证据不足”，不预设精简一定成功。

## 现有证据与限制

- [证据落库修复](screening-v2-evidence-grounding-fix.md)最终开发/校准批次抽取 26/26、多轮 7/7、关键字段错写 0、否决项 0；提示词和守卫共同调整，不能据此识别提示词单因素收益。
- [模型对比结果](../eval/requirement-v2/模型对比结果-20260924.md)记录同条件模型实验、缓存与用量。小样本不支持模型通用排名，也不证明压缩提示词后的表现。
- 已有认证 holdout 曾被查看并用于诊断；修复后未完成新的独立保留集验证。已暴露题目不能重新称为盲测。
- 当前工作树及运行环境可能已变化。执行前冻结实际基线，不直接把历史目录或当前编译提示词当作新实验的运行原文。

## 范围

### 纳入

- 审阅并精简 `internal/agents/pipeline/screening_requirement_state.go` 的静态主提示词 `requirementStateInstruction`。
- 合并重复规则、缩短冗余句式、合并语义相同的例子，保留必要反例与边界。
- 逐段说明删改内容、理由和对应合同/失败案例；提供完整原文 diff。
- 固定模型、守卫、题库与判卷口径的基线/候选配对评估。
- 保存运行时静态原文与内容版本，记录质量、成本、延迟及限制，关联工作台迭代记录。

### 不纳入

- 不改变 JSON 输出协议、schema、字段定义、授权合同、守卫、reducer、readiness 或 policy 逻辑。
- 不修改格式纠偏提示词、动态状态视图、会话上下文、缓存策略、重试策略、模型参数或模型选型。
- 不精简 Builder 提示词，不进行多因素消融或批量候选搜索。
- 不修改题目、金标、manifest、grader、gates，不通过放松门槛获得通过。
- 不在本 spec 内重建盲测集或完成完整发布认证；相关独立验证按评估治理另行规划。

## 精简原则

先建立规则清单，将基线段落对应到合同、防线和已知失败；再只删除不增加语义的信息。每项删改必须回答“为何冗余”和“哪项证据检查其未被削弱”。

| 必须保留的语义 | 防退化重点 |
|---|---|
| 输出字段与操作合同 | 输出合法、可解析；模型理解与程序执行职责边界不变 |
| 证据标签及建议接受 | 本轮明确给值与接受既有建议区分；无提案、询问、拒绝不产生授权 |
| 要求强度 | 明确表达不等于 must；不可妥协约束与普通偏好区分 |
| 默认值和来源 | 程序默认不能照抄成用户事实；证据原话和来源仍可核验 |
| 已有件与准确型号 | 类别与型号独立并存；记录型号不等于撤销已有件；无依据不能清空 |
| 事实、购买要求与参考建议 | 商品提及、报价、欲购型号和已拥有配件不能混写 |
| 需求更新与会话边界 | 修改、撤销、冲突、多轮上下文与能力范围不退化 |

优先处理同义复述、反复出现的禁止项和相似例子；关键规则只出现一次时不得以“程序也会校验”为理由删除。保留模型正确表达的指导，不能让守卫通过丢弃输出掩盖召回损失。

每个候选保存：完整基线/候选原文、内容哈希、字符数、段落级 diff、删改理由、关联历史案例和候选代码身份。静态主提示词与完整动态请求分开计量。

## 实验合同

### 1. 基线与候选身份

- 冻结执行时的基线代码、主提示词原文/哈希、模型精确 ID、provider 配置、reasoning、超时、重试、格式纠偏上限、缓存行为、题库/评分器/门槛、split 与 repeats。
- 基线与候选只允许主提示词文本不同。代码提交和编译二进制哈希因此可以不同；须核对源码 diff 证明其他行为代码及配置一致，不能要求二进制哈希相同。
- dirty 工作树必须有可恢复的准确源码快照和差异说明；仅记录 HEAD 不足以证明实验身份。不能明确隔离非提示词变化时不执行单因素实验。
- 不直接覆盖现役提示词。后续使用隔离候选版本与既有 runner，避免为一个实验建设新执行平台。

### 2. 评估范围与执行纪律

- 开发集 + 校准集，基线与候选各 repeats=3；使用同一冻结题目集合，模型层与确定性层分开报告。
- 正式配对需重新执行基线与候选，历史 26/26、7/7 仅作背景，不替代这次控制臂。旧输出 replay 可用于判卷核对，不能用于测量新提示词行为。
- 先做既有离线合同测试与数据校验；通过后才按显式实验计划运行两臂。不在实现候选时自动发起 live。
- 预算提案：每臂最大 400 次模型请求，两臂总上限 800；实际调用以 runner 为准。该数值是待执行计划的上限建议，不是本轮执行授权，费用估算须根据届时费率和基线用量确认。
- 每臂独立新产物目录，先保存计划、静态提示词快照与身份，再发请求；保留首跑、失败、中断和超限结果，不覆盖旧目录、不挑最好成绩。
- 顺序执行，记录运行时间、顺序、缓存状态及 provider 波动。顺序与缓存可影响延迟/费用，因此单次两臂观察不构成严格因果证明。
- 不因候选失败自动继续生成候选或重跑。额外复核必须有新计划，保留前次记录；严重错写/否决问题可提前终止并记录原因。

### 3. 质量与防退化

完整报告至少包含：

- 抽取与多轮任务的 Pass³、各题每次重复、操作 precision/recall、turn signals、最终状态。
- 关键字段错写、禁用操作、重复追问、否决项及 provider 失败。
- reducer/readiness/policy/ui-contract 的确定性检查，不能和模型层平均成一个分数。
- 原冻结门槛逐项 PASS/FAIL/不可评估；不以局部通过替代总门槛。
- 历史防线案例的实际行为和断言，包括 `cv-fps-progressive`、`cv-composite-9000-start`、`cv-owned-model-flow` 及已有件/建议授权边界。执行时逐一核对冻结题目，而非仅检查名称。
- 所有新退步题及差异；不能只复测已知 bad case。

### 4. 效率计量

分别报告静态字符数、实际完整请求 token、非缓存输入 token、缓存输入 token、输出 token（含实际可获得的 reasoning 用量）、模型请求数、provider 成功率和 p50/p95 延迟。

费用使用执行时可核对费率，附日期与计算口径；区分目录价估算、实际账单和免费额度。用量缺失标记未知，不用字符数推算实际收费，不承诺压缩 20% 就节省 20% 费用或延迟。

缓存命中差异、动态上下文和额外纠偏请求均写入限制。小样本不夸大显著性；复用既有配对比较规则，不一致对不足时只报告观察。

## 替换与停止标准

| 结论 | 条件及后续 |
|---|---|
| 可考虑替换 | 身份可比、无新增失败/重复退步、关键错写与否决项为 0、冻结门槛均通过；删改理由清楚，维护收益成立 |
| 保留原版 | 新增失败、授权/证据防线退步、召回下降、靠守卫丢弃掩盖错误，或未通过冻结门槛 |
| 证据不足 | 基线自身异常、身份不一致、产物/用量缺失、provider 波动或关键指标不可评估；不认定精简成功 |

以现有成功基线为预期，目标保持抽取 26/26、多轮 7/7，同时不能用 Pass³ 汇总掩盖其他断言或重复退步。若本次新基线未复现历史表现，先报告差异并分析，不能挑选重跑直到通过。

成本和延迟未明显下降不自动否定维护收益，但必须明确写出“仅证明可读性/维护收益，效率收益未证实”。字数减少也不能抵消质量退步。

替换条件是后续行为合同，本轮不触发替换。开发/校准集不退化不等于泛化或发布验证完成；已暴露 holdout 不作盲测证据。涉及独立验证和发布时，须使用另行锁定、未用于调优的保留集并遵守原认证流程。

## 工作台记录

- 提示词迭代单独标为“保守精简实验”，展示基线/候选原文 diff、删改理由、字符与 token 的区别、关联运行及结论。
- Screening 将这两臂归入“提示词精简验证”这一明确实验批次，不能混入不同模型对比或既有修复验收；具体目的分类在实施时沿用现有注册机制。
- 验证前显示“待验证”，执行失败或结果不完整如实保留；不把候选存在当作已发布版本。
- 与[失败案例闭环 spec](evaldesk-bad-case-analysis.md)关联历史防线及新增退步；该工作区尚未实施时，复用既有迭代记录、逐题证据和对比入口，不阻塞实验存证。
- 记录主提示词单因素前后变化；只要代码或配置也变动，就明确组合变化并停止单因素归因。

## 验收标准与交付物

1. 仅一个保守候选，完整 diff 与每类删改理由可审阅；输出合同、历史失败防线及其他行为代码不变。
2. 基线/候选静态原文与完整身份可恢复；旧产物不覆盖，未知内容不补造。
3. 配对质量报告覆盖全开发/校准题目、各次重复和全部冻结门槛；新增退步、错写、否决项和不可评估均可定位。
4. 字符、实际 token、缓存、费用与延迟分别报告；不存在未经测量的节省比例。
5. 工作台可从迭代记录进入两次运行、原文 diff、逐题差异和关联案例；发布与独立验证状态准确。
6. 交付实验计划、候选审阅说明、两臂冻结产物、配对报告、替换/保留/证据不足的决定及限制。未执行部分明确标记未完成。
7. 若后续决定替换，保留原文与基线身份作为回退点，并验证最终实际加载的原文哈希与通过测试的候选一致；工作台展示更新不得冒充模型行为验证。

## 后续执行顺序

**冻结基线 → 规则与 bad case 对照 → 起草一个候选和 diff → 离线检查 → 明确配对执行计划与预算 → 两臂运行 → 核对退步与效率 → 记录决定。**

失败案例工作区可以独立实施，提示词精简也可以独立形成候选；两份 spec 通过证据关联，不捆绑执行。
