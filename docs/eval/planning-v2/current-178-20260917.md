### c5 目录误报根因与检索修复（2026-09-18，零模型调用）

对 r2 报告 C123-005 全部 search 调用做离线复核，修正此前一处误判：step2 批量子查询并非返回空数组（先前解析把 `planning_action` 响应口径看漏），每个子查询都返回了 8 个候选——但全部是该品类价格最低的 8 件，与查询词无关。根因确认：

2. **修复**（`internal/planning/runner.go`，不改价格排序语义）：价格排序响应新增 `query_matched_count`（本品类 query 命中总数）与 `keyword_hits`（命中候选，最多 8 个，按价格序）；relevance 路径不变。工具说明同步增加：命中者未进当前页不代表目录没有；`query_matched_count=0` 时换通用规格词重查，仍为 0 才可断言该品类缺少该规格。

### 约束修订（替换原"服务端不得静默改写 draft"的绝对口径）

> 服务端不得静默改写 draft。但预算门检测到超预算时，服务端可执行确定性替换：候选只能来自本地目录（有报价、有规格），只动未锁定品类，替换后容量/性能档位不降，必须重新通过全部校验规则；每次替换在 Issues 与 reply 中显式标注（换成什么、为什么、依据是什么）。除此之外的任何 draft 字段仍不可由服务端修改。

保留的禁令：不引入目录外候选（external 注册候选无报价，天然排除）；不碰用户 must/锁定件/用途相关容量（已有件按品类核账的替身、must 品牌、must 静音与外观对应品类全部锁定；含 active must 约束的 free.* 字段无法程序映射到品类，求解器整体停用）；不改 rationale 语义（替换理由以独立 issue 追加，draft 其余字段原样保留）；unknown 与兼容性仍以校验规则为准（替换组合必须 `OverallStatus=pass` 且零缺价）。

### 求解器设计

- **触发**（`budgetFixDue`）：终局交付（ready/proposal/带已评估 draft 的 clarify）超 must 预算硬上限（复用 `budgetCeiling()`，new_purchase 口径取新增采购合计），且预算门回环已耗尽（`gates.budget>=2`、总门耗尽或进入最后两轮）或模型已用 price_asc 核验过目录低价（证据前置门放行路径）。
- **档位不降判定**（`tierNotLower`）：按品类用 canonical 规格可程序证明的字段——电源功率、主板 M.2 槽位与内存频率上限、散热类型与散热能力/冷排、内存容量/代际/频率（容量从型号文本解析，与 grade.go `memoryCapacityGB` 同一局限）、SSD 容量与接口形态；任一关键字段缺失视为不可比，保守拒绝。canonical 规格不含 CPU 核心数与 GPU 显存，这两类档位无法程序证明，**不参与替换**。
- **搜索**（`searchBudgetFix`）：对每个未锁定槽位枚举严格更低价有报价候选（价格降序=最小降幅优先），品类按最大可省额降序贪心 + 回溯（后缀省额剪枝、20 万节点上限），首个"总价回到上限内且重新通过全部校验"的组合中选——解的总降幅贴近超支额、改动最小。每次组合校验走 `validate.New(snapshotResolver).Evaluate`，纯内存、零模型请求。
- **无解时**（`minBudgetSacrifice`）：在未锁定槽位的更低价候选（不限档位）中找省额最小且能单笔覆盖超支的牺牲方案，以独立 issue 交付"把 X 从 A 降为 B 可省 Y 元压回预算，需用户确认"。
- **留痕**：找到组合 → 改写 draft（仅 selection 被替换槽位）→ 重新 evaluate → 清除已被解决的"超预算待取舍"旧议题（窄文本特征识别）→ 每笔替换以独立 issue 标注（旧→新、价格、省额、档位依据、校验通过）；交付 proposal（由 finalize 依校验与剩余议题决定是否升 ready）。reply 走 finalize 既有 issue 串联路径包含标注全文。
- **接线点**：`runner.go` Run 循环中 `deliveryGate` 之后、交付核验反馈分支之前——门回环路径完全不变，求解器只接手门放行/耗尽后的超预算终局。
