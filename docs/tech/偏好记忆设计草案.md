# 装机偏好记忆设计草案（第一、二阶段）

> 状态：**草案，非冻结合同**。2026-09-27，分支 `codex/memory-foundation`。
> 第一阶段建立独立持久化基座（表 + 域类型 + 读写）与评估场景草案；
> 第二阶段（同日）交付**用户显式保存的最小闭环**：从当前会话保存偏好，之后可查看、改正、删除。
> 自动提取、模型召回注入、Builder 接入与评估金标**均未确定**，
> 待 jev-v2 与 Builder 工具层相关分支合并后按最终代码再定（两分支截至本草案均未合入）。

## 目标与非目标

- 目标：跨会话记住"用户装机偏好"，作为新会话的**待确认建议**；来源可追溯；可冲突更新、撤销与删除。
- 非目标：不建腾讯 TencentDB-Agent-Memory 式完整 Memory Hub（无 L2 场景层、L3 画像层、团队共享、检索融合）；
  不做自动注入提示词；不做偏好的自动提取上线；不改 `RequirementState` v2 会话合同。

参考借鉴（仅概念，非照搬）：L0 原始对话 + L1 原子记忆的分层思想 → 本项目原始消息在
`web_messages`，`web_sessions.requirement_state` 是带 MessageID/Quote 溯源的会话级投影；
本阶段新增 L1 原子偏好存储。
腾讯项目中记忆过期/删除机制本身尚未展开，本阶段将撤销与删除语义显式定义为自己要解决的问题。

## 概念边界：会话需求 vs 长期偏好

| | 会话需求（已有） | 偏好记忆（本阶段新增） |
|---|---|---|
| 载体 | `RequirementState`（schema v2，Scope 仅 session/temporary） | 新表 `owner_preference_memories` |
| 生命周期 | 单会话 | 跨会话，直到冲突更新/撤销/删除 |
| 临时例外 | 支持（Scope=temporary，保留覆盖前值） | **永不入库**——临时/不确定陈述不升级为长期记忆 |
| 优先级 | **用户确认的当前需求始终最高** | 召回结果只是建议，不得自动成为硬约束 |

偏好记忆表没有 Scope 字段；写入链路接入时必须核对原始 RequirementState，拒绝 temporary 和
uncertain 内容。当前独立存储层只能校验传入的 evidence 标签，无法自行证明原始会话的 scope。
升级为长期偏好还须有用户明确表达（evidence=stated）或明确接受建议（accepted_proposal）。

## 记忆归属

- **owner 维度**：复用现有 `owner_id TEXT`（与 `product_user_owners` 对齐）。匿名期产生的记忆挂在匿名
  owner 上，账号认领后随 `Principal.Owners` 多 owner 解析自然可达，无需迁移数据。
- **subject 维度（本人 vs 代配对象）**：每条记忆带 `subject`。保留值 `self` 表示用户本人；
  其他值为具名代配对象标签（如朋友）。召回必须显式传 subject，本人与朋友的偏好互不可见、互不混用。
  与会话 `recipient` 自由文本的稳定映射（含 subject 的创建/合并界面）**待定**，本阶段只在存储与查询层隔离。
- 记忆默认私有于 owner，不实现任何共享；多账号间不互通。

## 记录模型

一条 L1 原子记忆 = `(owner_id, subject, field)` 上的一条用户表达：

- `field`：受控词表，沿用 `RequirementFieldKeys`（偏好向：brand_pref.*、noise_pref、size_pref、appearance 等）
  及 `free.*` 自由条目，与 reducer 同规则校验。
- `value`：JSONB 值，与 RequirementField.Value 同为 RawMessage。
- `strength`：prefer | must。**存储层保留用户表达的强度；召回出口一律降级为"建议"**——
  召回 API 命名与文档即合同，注入合同（是否、如何进入初筛提示词）待合并后另定。
- `evidence`：本阶段仅允许 `stated`（用户明确说过的）与 `accepted_proposal`（用户明确接受的）。
  `inferred`（推断偏好）的准入与失效策略**待定**，默认不允许写入。
- 来源：`source{kind: chat|edit, session_id, message_id, quote}`——哪次会话哪条消息的原话，
  与 RequirementSource 同口径；`quote` 必须非空。
- 时间：`created_at / updated_at`（记录时间）+ `observed_at`（证据观察日期，易失事实必填）。
- **易失事实**：价格、现货、时效性规格不属于稳定偏好。若调用方写入此类信息必须置
  `volatile=true` 并带 `observed_at`；召回按新鲜度窗口过滤，过期即不可复用（宁可重新问，
  不拿旧价格当事实）。窗口默认值**待定**，阶段内由调用方显式传入。

## 生命周期语义

- **写入**：`CreatePreferenceMemory`。同一 `(owner, subject, field)` 至多一条 active
  （DB 部分唯一索引兜底），因此没有"多条并存再打分"的复杂度。
- **冲突更新（用户改主意）**：`SupersedePreferenceMemory`，单事务：旧 active → superseded（墓碑保留、
  永不再召回），插入新 active 并回指 `supersedes`。新旧 value 相同则拒绝（改主意重申不是变更）。
  历史链保留审计能力，但召回只看 active。
- **撤销（别再按这个来）**：`RetractPreferenceMemory`：active → retracted，墓碑保留，不再召回。
  语义是"收回这条偏好"而非"替换为新值"。
- **删除（忘掉这条）**：`DeletePreferenceMemory` 物理删除该 owner/subject/field 的全部记录，
  包括旧值和墓碑；撤销则保留审计痕迹。原始会话消息独立存储，不随偏好记忆删除，
  用户若要求连原话一起删除，需另走会话删除流程并验证其覆盖范围。
- 所有三类变更都强制 `owner_id` 匹配，跨 owner 操作一律 not found。

## 召回原则

1. 召回是唯一出口：`ActivePreferenceMemories(owner, subject)` + 纯函数 `FilterPreferenceSuggestions`
   （剔除过期 volatile）。只返回 active、只返回指定 subject。
2. **召回结果只是待确认建议**：后续注入方（待合并后确定）必须把建议呈现给用户确认，
   确认后以当前会话需求（RequirementState）为准；未确认的建议不得进入硬约束/规则引擎。
3. 当前会话中用户明确表达的需求永远优先于任何历史记忆；冲突时以当前为准，必要时反向触发记忆更新。
4. 召回条数上限与字符预算（对齐"注入上限"思想）**待定**，本阶段先给保守 LIMIT。

## 已实现（第一阶段：独立基座）

- `internal/schemas/preference_memory.go`：记录类型、词表/证据/来源校验、易失新鲜度与召回过滤纯函数。
- `internal/store/preference_memory.go`：Create / Supersede / Retract / Delete / Active 读写方法，

- 针对性测试：schemas 纯函数单测；store 集成测试走既有 `PG_TEST_DSN` 临时库模式，

## 已实现（第二阶段：用户显式保存闭环）

写入路径只有一条：**用户在当前会话显式保存**。请求体只允许 `field` 与 `subject`；
值、强度、证据、来源一律由服务端从会话需求状态提取，客户端不可传值。

- 核验链（`internal/product/preference_memory.go`）：会话归属（ownerForSession）→ 字段在词表且
  当前 active → evidence 为 stated/accepted_proposal（uncertain、inferred、缺失一律拒绝）→
  scope 非 temporary（临时例外永不入库）→ 来源 kind=chat 且消息真实存在（`WebMessageByID`
  限定同会话）、role=user、quote 是消息原文子串。面板编辑值（kind=edit，无消息行）不可直接保存，
  需先在会话里说明再保存。本人(self)与代配对象由用户显式选择，不从 recipient 推断。
- 幂等与改主意：同字段同值重复保存返回 unchanged（不产生新记录）；值变化构成 supersede（旧记录
  墓碑、新 active 回指）；并发写命中唯一索引时由 `ErrPreferenceIdentityConflict` 触发一次重读重试。
- 删除：`DeletePreference` 物理删除整条链（含墓碑），跨 owner 未命中统一 404。
- HTTP（`internal/producthttp/preference_memory.go`，窄接口断言、无能力降级 503）：
  `POST /api/v1/sessions/{session_id}/preferences`、`GET /api/v1/preferences`（多 owner 汇总，
  本人 self 在前）、`DELETE /api/v1/preferences/{preference_id}`（要求幂等键）。
  新 Problem 码：`preference_not_savable`、`preference_invalid`、`preference_unavailable`；
  openapi.yaml 已同步并重生成前端客户端。
- Web UI（`web/src/components/preferences-panel.tsx`）：右栏"需求状态"Tab 底部新增
  "跨会话偏好记忆"区——从当前需求选择字段与归属对象（本人/具名代配对象）保存；
  列表按本人在前分组展示原话与日期；删除按钮。改正方式：在会话说明新偏好后再次保存同一字段。
- 测试：服务层（生命周期/幂等/改主意/权限/来源伪造/temporary/uncertain/缺失证据拒绝）、
  HTTP 层（归属 404、schema、幂等键、503 降级、problem 形状）、store 层（身份查询、owner 列表、
  跨会话消息核验）。

## 已实现（第三阶段：跨会话召回 → 用户确认 → 写入当前需求）

召回是**用户显式触发**的：新会话中用户打开偏好面板、选择归属（本人 self 或具名代配对象）后载入建议；
不向初筛提示词或 Builder 自动注入，模型评估金标未冻结。

- **收口第二阶段边界**：
  1. 稳定偏好白名单 `schemas.StablePreferenceFields`（brand_pref.cpu/gpu、noise_pref、size_pref、
     appearance）：预算、已有件、用途、一次性价格/规格与未分类 `free.*` 不得保存为长期偏好；
     保存与召回确认两侧服务端同时执行，UI 仅镜像预过滤。扩充属于显式产品决策。
  2. 保存正向要求 `scope == "session"`（空 scope 与 temporary 一并拒绝），不再只做反向排除。
  3. DELETE 幂等语义澄清：`Idempotency-Key` 当前仅作请求标记、未实现请求级幂等——重复删除得到
     404（表示已删除或不存在）。API 合同、404 文案（"删除已生效，无需重试"）与前端（404 按成功处理）
     已如实对齐，后续若引入通用幂等存储再升级。
  4. UI 文案不再承诺"自动出现"：明确为"打开面板、选择归属并逐项确认后才写入当前需求"。
- **召回建议**（`PreferenceSuggestions` + `GET /api/v1/sessions/{session_id}/preferences/suggestions?subject=`）：
  只读该身份可访问（Principal.Owners 全集）、指定 subject 的 active 记录；只出白名单字段；
  剔除超出新鲜度窗口（产品侧保守默认 7 天，可调，非模型合同）的易失记录；
  当前会话已生效的字段不出现在建议中。同字段跨 owner 同值去重为单一建议；
  不同值标记 `conflict` 并列全部选项，由用户挑选或忽略，服务端不代选。
- **确认写入**（`ConfirmPreferences` + `POST .../preferences/confirm`，要求幂等键）：
  逐条记忆服务端重读核验（active、subject 一致、白名单、未生效、未过期、同请求去重）后，
  经既有 `EditRequirement` 入口落账——revision 校验与指纹幂等全部复用；跳过项逐条返回稳定原因码。
  写入以面板编辑（kind=edit）口径落账，历史原话保留在记忆来源中，**不伪装成本轮用户消息**，
  也不声称本轮 stated 证据。确认前建议只读、不产生任何状态变化。
  幂等键语义（实现=测试=OpenAPI 合同一致）：指纹按"本次将写入的编辑内容（含 expected_revision）"
  计算、只记录成功写入——同键同内容重放不重复写入（applied 为空，各项按当前状态给出 skipped 原因）；
  同键不同内容返回 409 幂等冲突；首次失败未落指纹，同键重试正常执行。
- **召回 UI**：自定义归属把输入的名称作为真实 subject 传递（选择器占位值 custom 不参与请求）；
  切换归属或修改名称即清空已载入建议与勾选，不展示上一归属的内容；
  建议逐项展示 must（必须满足）/prefer（尽量满足）强度；确认成功后建议列表随最新需求刷新。
- 测试：字段准入（白名单保存+确认两侧）、scope 正向校验、过期事实不进建议、跨 owner/subject 隔离、
  多 owner 冲突不代选、当前需求优先（建议排除 + 确认跳过双层）、确认前不生效、重复请求一致、删除重试稳定 404、
  确认幂等键三态（同键同内容重放/同键不同内容冲突/首次失败重试）、UI 自定义 subject 传递与强度展示（组件测试）。
