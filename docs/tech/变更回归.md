# 提示词与逻辑变更回归

当前产品链路默认使用 `python scripts/eval/planning/run.py --out artifacts/<新目录>`，执行冻结 123 件目录的离线机制集；指定 suite 可重放保存的真实回答。场景、结果、数据库隔离方式和本轮已用完的真实调用额度见[当前目录有限验收](../eval/planning-v2/current-123-20260915.md)。下文 `evalchange` 是保留的历史执行器对照流程，不能替代当前产品链路验收。

目标：修改后能直接看到哪些题的结果或输出发生变化、是否出现退步、失败证据是什么、模型调用和已知 token 增加多少。入口为 `cmd/evalchange`，比较和独立复核实现在 `internal/evalsuite`；实际执行沿用 `cmd/eval`。实测结果见[运行记录](../eval/运行记录.md)。

已有产物也可通过[本机评估工作台](本机评估工作台.md)在 `/eval` 只读查看：中文运行列表、条件变化、原成绩与统一复核、单题逐轮证据和调用/token 变化。工作台复用本节严格对照逻辑，跨题库另按冻结内容与期望不变的共同题观察比较；不运行模型、不覆盖记录、不自动升级基线。

## 日常使用

从仓库根目录执行。真实运行仍需现有模型配置和 `PG_DSN`；数据库必须提供与基线完全相同的目录及价格快照。只查看计划或比较保存记录时不连接数据库、不读取模型 key。

```bash
# 指向你明确选择的历史运行；不会自动挑一轮高分作为基线。
BASE=artifacts/eval/20260909-134447-3770035618

# 先看范围、固定模型、旧成绩的当前复核结果；零调用。
go run ./cmd/evalchange -baseline "$BASE" -max-calls 300

# 改完提示词或逻辑后，显式构建、实跑、对照。
# PG_DSN 应指向与 BASE 一致的评估库，不能因为日期相同就假定目录相同。
go run ./cmd/evalchange -mode run -baseline "$BASE" -max-calls 300

# 已有两次运行时，直接生成新对照报告；零调用。
go run ./cmd/evalchange -mode compare -baseline "$BASE" -candidate artifacts/eval/<候选目录>
```

退出码：0 表示当前题目全部通过且没有新增失败；1 表示仍有失败（包括限额耗尽后的未执行题）；2 表示条件、证据、完整性或工具错误。使用 `go run` 时 Go 外层会将非零退出转为失败状态；需要精确区分 1/2 的自动化应先编译再调用二进制。

每次真实回归在 `artifacts/evalchange/<时间>-run-<唯一后缀>/` 保存独立程序、构建输入摘要、执行目录和对照报告。`runs/<时间>/` 内仍是标准的 cases/meta/results/report 四件套，加 `source.json`。`*-comparison-*/report.md` 用于阅读，`comparison.json` 保存逐题原成绩/复核成绩、失败断言、改变的输出全文以及调用、token、耗时。

## 执行流程

1. 选择已保存的基线运行，先离线复验其题目、记录、模型和快照。规划模式不调用模型；有与二进制对应的源码清单时列出文件变化。当前尚无经过验证的源码到题目依赖映射，所以统一全量执行，不自动缩题；“影响了哪些题”来自执行后的观察，不把文件名推测当成已验证影响。
2. 明确触发真实回归，固定基线的题目、价格快照、模型及 Harness 参数。构建并标识本轮实际程序，保存工作区变化与运行证据；不改产品配置、不自动切换模型、不自动覆盖基线。支持调用上限，耗尽明确记未完成，不能把未执行题当通过。
3. 用同一版判卷规则复核两侧，逐题输出原成绩、复核成绩、通过次数、失败断言及证据、输出变化、调用/token/耗时差异。原因区分“观察到的失败”与“待确认的根因”，不把断言编号当作因果证明。
4. 报告和机器可读结果写入新目录。新增失败或重复通过数下降应使回归检查失败；只有失败变少但仍有失败时也不能宣布全绿。小样本变化表示需要调查，不自动证明提交或模型的因果效果。

## 判卷可信度

新判卷版本须独立检查实际候选成员及品类、冻结目录规格重建的兼容性、所选 SKU 对应的报价。不能仅相信 Harness 的 Succeeded 字段、已保存的 pass 报告或自洽的合计。缺少必需证据单列，不能按正确处理。新旧判卷版本显式记录，历史运行继续按原版本重放；当前规则对历史重新评分另列结果，不覆盖首跑。

当前版本为 `independent-v2`；空版本保留历史 A/N 判卷。A6 检查实际候选及品类，A10 检查兼容性和保存报告，A7 重建报价，E1 标记缺证据。兼容重算复用领域规则，只独立于结果声明，不声称有另一套独立规则引擎。改变判卷规则或重算语义时必须显式演进 grader version 并保留旧版分支，不能仍叫 v2 却悄悄改变旧运行的重放；题目版本和判卷版本分别记录。

不同源码的比较独立于现有单变量消融，保留同题、同模型、同快照和同 Harness 配置要求。题目、模型或价格同时变化时拒绝混作代码回归。历史基线只有启动 Git commit/dirty 和二进制哈希时，不声称能恢复该二进制的精确源码。

新入口在构建前后核对本仓库 `cmd/`、`internal/` 下 Go 源文件及 go.mod/go.sum 的摘要，发现构建期间变化则停止；保存的实际程序 SHA256 必须与 runner 元数据一致。该清单保守包含未编译的测试文件，仅是构建输入摘要，不是完整源码备份，也不是自动因果定位。当前项目没有 Go 嵌入资源；以后出现 go:embed 会要求先扩展采集器。第三方依赖由 go.sum 锁定；供应商隐藏路由、服务修订、网络延迟和缓存状态不能由这些记录证明不变。

## 自动化与额度

提交和 PR 自动运行零模型的题库校验、判卷器反例测试和报告测试。真实模型评估由明确命令触发，先展示范围及上限；不在不可信 PR 上注入 API key，不将 `.env`、凭据或原始用户反馈上传为 CI 产物。先完成本机入口及实测，再声明远程自动运行能力。Judge 仍只作诊断，不参与自动回归门禁。

工作流在 `.github/workflows/eval-offline.yml`，覆盖当前可直接运行的 v1.1–v1.5；v1 两道旧追问题须从历史产物恢复，不能用当前内容修改旧哈希。工作流文件已提供，远端是否运行应以实际 Actions 记录为准。

调用上限为模型与 Embedding 合计的**逻辑调用数**，不包含适配器内部 HTTP 重试，不能当作精确账单上限。只有上游返回 usage 的请求才计入已知 token，报告同时给覆盖数；缺记录显示未知。逐题结果立即落盘；上限耗尽时保留未执行题的 RUN 记录，意外中断造成缺记录则拒绝形成完整回归结论。

## 更完整的生产设施补在哪

| 设施 | 操作位置 | 当前边界 |
|---|---|---|
| 判卷、冻结证据、重复运行 | `internal/evalsuite`、`cmd/eval` | 已支持当前题库；完整产品交付仍由产品/Web 测试补充 |
| 修改前后的结果及调用对照 | `cmd/evalchange`、本设计 | 已提供本机入口；不做自动因果定位、自动选模或升级基线 |
| 提交时自动检查 | `.github/workflows/eval-offline.yml` | 零模型检查；定时真实跑测、远端可信密钥及评估数据库尚未配置 |
| 用户问题回流 | `internal/product`、`cmd/feedbackexport` | 已有负反馈与待审核导出；题目期望仍人工复核，见[回流设计](反馈与评估回流.md) |
| 线上长期监测 | `internal/evalmetrics` 与服务运行层 | 只有已有指标采集基础；全链路 trace、线上分布/延迟/费用告警和长期看板尚未完整建立 |

后续应根据真实使用量补线上监控和可信定时评估；当前少量自用反馈期间，先用这个回归入口持续验证每次改动。

完整目录快照不包含语义向量索引版本；目前只能查看实际返回的候选变化，不能证明两次索引内容完全相同。将索引指纹纳入环境身份属于后续增强，若正在重建向量，应将该轮标为数据/检索实验，不能据分差推断纯提示词效果。

## 验证要求

- 判卷反例：目录存在但未给模型的 SKU、错品类、兼容性 fail 却宣称交付、伪造 pass 报告、自洽但与真实选件不符的报价、缺证据。
- 比较反例：不同题目/快照/模型/机制、缺重复、改写原文或分数、缺用量，不得生成误导的胜负和成本。
- 报告须覆盖新增失败、恢复、持续失败、分数相同但输出改变、调用增减；错误保留，不自动升级基线。
- 最终用真实保存产物完成零模型复验，再执行当前代码的固定条件真实回归，保存可读的逐题变化报告；基础测试、静态检查和必要集成验证通过。
