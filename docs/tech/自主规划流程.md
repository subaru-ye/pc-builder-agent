# 装机 Agent 自主规划

2026-09-10 起，产品默认使用 `BUILD_HARNESS_MODE=planning`。`v2` 和 `legacy` 仅用于显式历史诊断，不自动回退。原 Harness 2.0 的预算下界、候选硬筛选和固定修复轨迹不再是产品准入条件。

## 会话与执行

用户消息 → Screening 一次调用返回 operations、reply、next_action → 服务端合并需求草稿 → 首次需求确认 → Builder 工具循环 → 保存方案或正式配置。

已有件品类与准确型号由同一 reducer 原子联动：准确型号自带的 category 同步补入 existing_parts；取消一个品类或清空品类数组，同步移除对应 owned_parts，保留其他配件与数量。仅撤回型号保留已知品类，备选不改变当前字段。联动与直接操作使用同一修订、消息来源及历史，临时操作保留关联字段 previous；derived_from 标识这次联动，恢复时不覆盖后来直接更正的型号。该元数据由服务端生成，聊天和面板使用相同处理，不增加模型调用；旧会话仅在新的有效编辑时更新，读取与刷新不改写历史快照。

未解决方案结束前的复核：模型返回带问题列表的 proposal，且尚有工具阶段和工具额度时，服务端也会把实际交付核验反馈给模型一次。模型自行决定追加检索、调整或保持未解决方案；同一运行不因重复 proposal 强制耗满往返。有效完整方案仍直接交付，明确 collect/clarify 正常结束。该复核使用原有最多 8 次模型往返与 24 次工具执行额度；未解决运行可能增加一次复核及其自主修复调用，不增加独立总结模型。

需求确认过后，明确的升级/重新选配指令由 Screening 返回 `next_action=plan`，在同一运行内直接继续 Builder，不再反复确认执行方向。`collect` 用于讨论或必要追问，`confirm` 用于首次核对或仅记录的新草稿；面板编辑仍只更新草稿。服务端仅允许已确认过需求的会话进入这条聊天续跑路径；没有首次确认时，即使模型误给 plan 也仍展示需求核对。

Screening 输入包含全部常用字段、自由字段及撤销墓碑，以及服务端读取的当前正式配置、报价、配件名称、上一方案摘要和最近一条助手回复。配置不是用户已购件，助手回复仅帮助理解指代，不是新需求证据。旧用户消息不重新用于提取；free.* 不得只落库却遗漏于下一轮模型输入。预算充足不表示可超预算，“其他配件尽量不动”保留为 prefer。

`ContinueScreeningRun` 锁定会话和当前 running run，校验修订号后原子保存新需求及本次执行确认，转为 build/change 并交给 Builder；保留同一 run_id 和请求幂等键。只在最终交付成功时追加正式版本，历史配置与关联需求行不修改。运行观测记录实际送入 Screening 的状态及执行上下文，`build_input` 记录补齐基础配置后的实际执行输入。

常用字段和 `free.<稳定编号>` 同时生效，后者逐条保存原文、来源、强度、状态、撤销和备选。未说明字段保持未知；模型假设保存在方案的 assumptions 中。界面编辑复用同一 reducer 和修订校验，不增加模型调用。确认不依赖预算、分辨率等固定必填字段；确认前后都可以继续对话。

执行输入 `PlanningInput.schema_version=2` 携带完整当前需求状态、原配置和上一方案；聊天续跑另附带 `request`（来源消息编号、类型、本轮原话），便于理解即时执行目标，不写成额外偏好。HTTP 与 A2A 使用同一输入，不再转换为固定必填 RequirementSpec。旧记录按读取适配，旧配置及需求快照不批量改写。旧草稿仅在用户确认时切换执行协议。

## 有界工具循环

每次 Builder 最多 8 次模型往返、24 次工具执行。第 8 次只整理结果。一次运行最多 3 次外部搜索、6 次网页读取。无结果、截断、缺价、目录不可用、规格未知和兼容性失败都返回给模型，不按用户偏好提前退出，也不指定模型必须照抄的修复配置。

- search_local：本地型号、规格检索和分页；过滤仅由模型本次查询指定，可自行放宽。
- search_local_batch：一次提交1至8个独立本地查询，参数为 `queries:[{query?,category?,offset?,limit?},...]`，沿用 search_local 的排序与分页。每个实际子查询分别计入24次工具上限，剩余额度不足时返回已执行 results 及 pending_queries，不增加执行预算；阶段耗时同时记录整个批次与本地子查询，两者不能相加计算总耗时。模型可用批量查询节省往返，为 evaluate 和自主修复留出时间，不强制所有请求批量检索。
- search_semantic：复用现有 embedding 与 pgvector；命中表示相关，不证明规格。
- search_web：复用 SerpAPI，仅查询装机技术资料，优先官网规格、兼容性/BIOS支持、安装指南和知识文章；不查询具体价格、优惠、库存或购买信息，查询不依赖固定 SKU 映射。
- read_page：公开 HTTPS 网页正文，默认 HTTP 优先；动态空壳可升级浏览器，模型也可明确指定读取方式。支持相关词定位和分页，完整有界正文进入方案快照；read_evidence 续读不联网。限制大小、重定向和超时，拒绝私网地址及登录/访问验证内容；详见[网页读取与补库策略](网页读取与补库策略.md)。
- read_evidence：按编号展开已保存的来源，不重新联网。本地search_local的sources按候选编号给出 `{id,field,status}` 索引，链接、时间与完整原文按需读取，避免同一商品的多个字段反复携带相同元数据。上一方案的提示上下文每条来源最多携带240字短摘录，完整证据仍保留。相关词窗口定位到命中词，而非长段落开头；小窗口的前文长度受窗口大小约束，避免命中资料却没有展示目标事实。
- register_candidate：正文中存在的型号、逐字段来源和摘录。未提供证据的规格不进入已核验参数；非 canonical 属性另存 attributes。新注册候选不接收网页价格，price_cny 保持 null，误传的价格及报价来源字段会清除并反馈原因；本地价格快照继续使用，历史方案/版本不批量改写。冲突和未知项随候选保留。

  规格来源映射支持完整路径 `specs.socket` 和历史短键 `socket`，归一后仍逐项核对正文摘录。两种键同时存在且内容不一致时返回冲突，不静默选择。注册结果返回实际保存的 candidate（含 specs、attributes、unknown），不能只返回注册编号而隐藏被剔除字段；注册成功不等于核验通过。工具反馈附带剩余模型/工具往返及检索额度，最后一轮仍仅用于整理结果。
- evaluate：用本地/会话候选快照计算价格和运行原兼容性规则。已有件只有准确型号、数量对应后才从采购金额中扣除。

工具可比较不满足当前要求的备选，但不能改变用户的 must 或保留件。已发现的兼容性冲突、缺价、关键未知和未解决 must 保存在 proposal；不得伪造通过。达到交付条件后沿用版本流程产生正式配置。

本地检索反馈 new_count、previously_returned_count、seen_in_scope 和 scope_category，表示首次检索返回数、重复返回数及该品类已经检索返回的覆盖数（不含初始样本，含语义检索命中）。query 只影响相关性排序，不缩小品类总数；重复搜索仍返回候选，服务端不强制跳过或替模型决定换平台。初始输入另附 owned_candidates，按当前 active owned_parts 的品类和完整型号匹配本轮目录，保留多个同名候选、规格及缺价 null；简称和未匹配项保持空 matches。该上下文不修改用户需求、不把已有正式配置当成已购，也不自动核销采购金额；金额仍由 evaluate 按最终选择和数量核验。

## 证据、存储与产品

迁移 `00016_planning_proposals.sql` 新增 session_proposals、共享 search_quota，并在 builds 增加 candidate_snapshot。候选和证据只属于当前会话，不写入全局商品库或个人画像。方案关联需求修订、父配置、校验、问题、候选及证据；正式配置保存同一候选快照，分享、导出和后续改单从该快照读取。

A2A 数据部分 `pc_builder.planning_result` 与 HTTP Session.proposal 区分 collect、clarify、proposal、ready、technical_fault。追问或方案没有新版本仍是正常完成；技术中断也保留已取得的进度。右侧可切换待解决方案与已确认配置，来源按需展开，刷新从服务端恢复。

### 自动交付与持久化

`model_outcome` 保留模型原始意图，`outcome` 为最终业务结果，`delivery.status` 为服务端交付核验：not_applicable / unresolved / eligible / delivered / stale。完整且无实质待解决问题的 proposal 和 ready 使用同一核验路径：真实兼容性、完整报价和有效必须条件评估满足后自动交付。用户未表达的静音等未知偏好不影响交付，软偏好的取舍保留在选型说明；用途评估不等于性能实测。必要追问必须输出 clarify，不能只藏在回复文本中。

proposal 问题列表为空但缺少交付依据时，在现有 Builder 往返上限内反馈具体缺项；修正后重新核验，不累计已经解决的旧问题。达到上限仍未解决时保存具体候选和问题，不以通用“等待确认”代替原因。

迁移 00017 为 session_proposals 增加正式配置关联。方案、版本、需求快照、关联信息、助手回复和运行完成状态通过一个事务保存；run_id 幂等，同一运行并发或重复完成只生成一版。保存时锁定当前会话并比较需求 revision；需求已改变则保存 stale 方案，不生成版本或覆写当前需求。`build_version` 只在实际保存后返回，右侧自动展示新版本。会话摘要可提供 `status_label`，表示“方案待完善”等阶段内细分状态。

历史方案只读适配，不在 GET 或刷新时调用模型、升级版本或修改 JSON。继续选配使用当前需求修订，不批量转换历史方案；用户原有配置与已确认需求不改写。正式版本候选快照附带 assessments、assumptions、reply，保留当时的取舍依据。

### 素材参数与来源展示

Screening 在同一次调用中更新稳定 free.* 条目；素材参数属于工作负载事实，不是屏幕分辨率，也不重复写入 notes。后续更正复用已有条目编号；跨字段重复内容由模型发出同轮 set/remove 操作原子处理，保留其他信息与历史来源。没有新增总结模型，也没有素材关键词替换规则。

来源附带 candidate_id、field、kind 与获取日期。初始样例直接入选时也读取已有本地证据；这只是数据库查询，不消耗模型或外部搜索额度。界面按当前配件与评估引用筛选主来源，同链接合并；其他资料在次级折叠区保留。catalog 是本地库已有资料，search 是搜索摘要，page 是已读取正文；本轮调用数与资料获取时间分别展示，旧来源不伪装为本轮联网。

SerpAPI 的交互路径与 Python 后台采集都先原子预留同一 PostgreSQL 月额度。后台通过 `cmd/searchquota` 预留；计量失败不发搜索请求。失败请求保守占用预留，避免超额；后台采集启用策略和全局发布门禁保持独立。

## 观测与验证

结果记录 model_calls、tool_calls、search_calls（尝试）、search_requests（已预留并发出的搜索）、page_calls、tokens、duration_ms 和 stage_ms。现有模型指标同时保留 Screening 用量。普通请求不强制外部搜索，复杂需求会增加时间；不与原先提前退出的流程承诺相同延迟。

离线测试入口：`go test ./...`，真实临时数据库用 `PG_TEST_DSN=... go test ./internal/producthttp -run TestPlanningProposalPersistentWorkflow -v`。浏览器使用 `TestPlanningBrowserServer` 与 `web/e2e-requirements/planning.spec.ts`；模型轨迹为明确标注的离线 oracle，HTTP、工具、规则、价格与存储均使用实际实现。

显式真实冒烟：`PLANNING_LIVE=1 go test ./internal/agents/pipeline -run TestPlanningLiveBounded -v -timeout 10m`。固定当前 Screening/Builder，零自动重试，最多 12 次模型请求和一次 Builder（最多 3 次搜索），产物在 `artifacts/planning/live-smoke.json`。不发布用户配置，不运行全量评估。历史 v1.5 分数不代表新流程验收。

本轮测试结果、累计用量与未验证部分见[自主规划验收](../eval/自主规划验收.md)。

本轮不建设跨会话长期偏好、全市场采集或来源可信度知识库。公开网页可读性、噪声实测覆盖和模型推理仍存在不确定性；需通过实际候选与待解决问题呈现，不能把不确定性转换成用户需求不合理。
