# 本项目评估现状与差距分析

> 历史分析：本文描述评估集建立前的观察或建议，不是当前进度声明；现有能力见[Runner 设计](../../tech/评估Runner设计.md)，未完成工作见[路线图](../../product/路线图.md)。
> **口径说明**
> 盘点日期:2026-09-06。本文把《深入理解 AI Agent》2.0 版第 7 章的方法论([01-Agent的评估方法论精读.md](01-Agent的评估方法论精读.md))逐项对照本项目的评估现状,结论按「已命中 / 部分命中 / 缺失」三档标注,每条附代码或文档证据。
> 本文只做事实盘点与差距定位;落地建议见 [03-评估体系落地建议.md](03-评估体系落地建议.md)。
> 项目侧口径以 `docs/tech/系统架构.md`、`docs/tech/开发约定.md`、`CLAUDE.md` 权威文档表为准;文中代码行为以盘点日为准。

**一句话结论**:本项目已经无意识地命中了Agent 的评估的两个关键设计(确定性验证器、提示词入 Git + 回归纪律),验证器深度在同类项目里属于前列;但评估体系整体停留在 **n=1 端到端冒烟 + 50 组单元级 golden** 的水平,可靠性口径(Pass^k)、失败归因、轨迹前缀回归、生产回流闭环四项全部缺失——按书中标准,当前评估能回答"做得到吗",不能回答"稳定吗、为什么错、这次改动有没有用"。

## 一、被评对象:三段流水线 + 确定性校验环

按Agent 的评估"评估对象是模型 + Harness 组合体"的口径,本项目被评的 Harness 由以下部件构成:

| 部件 | 说明 | 证据 |
|---|---|---|
| 初筛 Agent(低价档) | 自然语言 → RequirementSpec / ChangeRequest JSON;预算缺失时一句话追问;brand_pref 禁止推断 | `internal/agents/pipeline/prompts.go`(`screeningInstruction`)、`pipeline.go`(模型档位装配) |
| 生成 Agent(旗舰档) | RequirementSpec → BuildDraft;八品类强制检索、SKU 必须来自工具返回、预算弹性区间、语义软偏好两路检索 | `internal/agents/pipeline/prompts.go`(`builderInstruction`)、`internal/buildharness/planner.go` |
| 确定性校验 + 修复环 | pass / review / warning 三态;unknown 可消除时定向回馈换件;最多 3 轮(`maxLoopRounds`);交付时回写 `build_state` | `internal/agents/pipeline/validator.go`、`internal/buildharness/harness.go` |
| 改单预处理 | swap_part / adjust_budget / change_constraint 三类意图;锁定品类;超范围降级为整单重生成 | `internal/agents/pipeline/changes.go` |
| 可独立开关项 | `BUILD_HARNESS_MODE`(v2/legacy)分流;Trace 可选(nil → noop);语义检索仅在有软偏好 query 时触发(无显式禁用开关) | `internal/buildharness/types.go`、`cmd/buildsvc/main.go`、`internal/buildharness/planner.go` |

## 三、差距清单(按影响排序)

1. **评估样本 n=1**。用例 A 是唯一被反复执行的端到端用例,且人工演示一次即判。按Agent 的评估统计口径,任何"改动后变好/变坏"的结论都在噪声带宽内;提示词回归纪律(§8)实际约束力接近于零。——对应方法论:统计显著性、Pass^k。
2. **无可靠性口径与否决项清单**。装机单是有硬约束的业务交付(书中"支付/退款类"场景),应报 Pass^k;而"SKU 编造、预算越界、锁定品类被改、交付兼容性冲突、报告参数编造"这些一票否决行为没有成文清单,部分(报告编造)甚至无法被现有校验发现。——对应方法论:Pass^k、否决项、"做对了但说错了"。
3. **信息告知层零断言**。校验只查 BuildDraft 终态;报告中价格合计是否等于 selection 求和、rationale 是否引用语义命中词、已有件是否标注——书中数据显示这类失败可占全部失败的三分之一,且被终态检查完全掩盖。——对应方法论:τ²-bench 四层验证、communicate_info。
4. **无失败归因体系**。失败分析靠人读日志,无分类表、无结构化记录、无首错定位约定;根因归错的风险真实存在(如把零件库缺字段导致的 review 记成模型问题)。三段流水线每段输出结构化 JSON,首错定位条件极好,只欠方法论落地。——对应方法论:失败归因、根因 vs 后果。
5. **改单场景未建成轨迹前缀回归**。冻结 build_state + ChangeRequest + 断言"锁定品类一字不差、只动解锁品类、预算重新落区间"是用例 C/D/E 素材的自然延伸,是最便宜也最直击改单纪律的一层回归。——对应方法论:轨迹前缀回归、可接受动作集合。
6. **评估环境不可钉死**。评估时无法固定历史快照日期,零件库与价格更新后新旧结果不可比——库存漂移会伪装成模型退化,恰是书中"先检查评测系统本身"要防的第一类失真。——对应方法论:评估环境五要素(可重置)、先查评测系统。
7. **无生产回流闭环**。P10 指标只出不进:validation.round、harness.completed 等事件已落 JSONL,但没有"负反馈 → 归因 → 回归用例"的管线;工作台也没有点踩/负反馈 API。——对应方法论:评估集三来源、可观测性闭环。
8. **消融与选型缺工具**。SCREENING_MODEL / BUILDER_MODEL 双档异构组合从未被对照评估;语义检索(用例 F)的真实贡献、修复环的边际价值均无法量化——特性开关不全,消融实验做不了。——对应方法论:消融基础设施、异构组合验证、模型替换实验。

## 四、可复用资产盘点(差距不是从零补)

| 资产 | 对评估体系的价值 | 位置 |
|---|---|---|
| golden 50 组(含故意错配、`-update` 基线开关) | 确定性验证器的单元级评估集,已验证"任一字段缺失输出 unknown 不崩溃" | `internal/rules/testdata/golden/`、`internal/rules/golden_test.go` |
| `cmd/validate` CLI(退出码冻结 0/1/2) | 评估 runner 的确定性校验后端可直接复用 | `cmd/validate/` |
| `cmd/p10report` 门禁报告 | "评估结果 → 汇总报告 → 门禁"的现成格式参照 | `cmd/p10report/` |
| `SnapshotByDate` store 方法 | 固定快照日期开关的现成接缝,无需新增查询 | `internal/store/store.go` |
| buildharness 四接缝(Planner / Repairer / Eval / Trace) | 消融开关与假模型注入的天然位置;现有 `harness_test.go` 的 `fakeModel` 脚本化输出就是"无 LLM 评估"的雏形 | `internal/buildharness/types.go`、`harness_test.go` |
| evalmetrics JSONL + fingerprint | 生产回流管线的数据源头,脱敏纪律已合规 | `internal/evalmetrics/metrics.go` |

| 用例 C/D/E 对话脚本(v1→降 500→v2→换 A 卡→v3) | 轨迹前缀回归用例的现成剧本 | `docs/tech/版本快照与增量改单.md` |

## 五、结论

- **不需要从零建评估体系**:确定性验证器、golden、脱敏指标、CLI 骨架、快照查询接缝都已存在,缺的是把它们串成"评估集 × 多种子 × 验证器矩阵 × 归因 × 回归"的 runner 与纪律。
- **最深的差距不在工具而在口径**:n=1 与无否决项清单,使现有提示词回归纪律和 P 系列验收的实际推断力远低于其表面严格程度。
