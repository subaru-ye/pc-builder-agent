### c5 目录误报根因与检索修复（2026-09-18，零模型调用）

对 r2 报告 C123-005 全部 search 调用做离线复核，修正此前一处误判：step2 批量子查询并非返回空数组（先前解析把 `planning_action` 响应口径看漏），每个子查询都返回了 8 个候选——但全部是该品类价格最低的 8 件，与查询词无关。根因确认：

2. **修复**（`internal/planning/runner.go`，不改价格排序语义）：价格排序响应新增 `query_matched_count`（本品类 query 命中总数）与 `keyword_hits`（命中候选，最多 8 个，按价格序）；relevance 路径不变。工具说明同步增加：命中者未进当前页不代表目录没有；`query_matched_count=0` 时换通用规格词重查，仍为 0 才可断言该品类缺少该规格。

### preserved_other_parts 条件性不可满足：根因与修复（2026-09-18，零模型调用）

r2 C123-001 step3（"直接把CPU升级为Ryzen 7 5700X，其他配件尽量不动"）硬门失败 `preserved_other_parts`。根因链：

1. **事实**：模型把 CPU 5500→5700X（+510 元）后总价 7891 超出 7500 硬上限，为压回预算将内存 32GB DDR4-3600（1759 元）砍成 16GB DDR4-3200（569 元，-1190 元）——牺牲剪辑用途容量而非最小替换。目录核实：最便宜的 32GB DDR4 就是已选款，**不存在更便宜的 32GB 同容量替换**。
2. **预期不可满足**：v1 已花 7381/7500（余量 119 元），CPU 差价 510 元；`preserve_other_parts` 对非 CPU 逐件 DeepEqual，而预算 `budget_ceiling` 是硬门。任何非 CPU 改动都违反前者，不改必超后者——**两条硬门在该 v1 组合下矛盾**。唯一通过路径是模型在 confirm 时恰好留下 ≥510 元余量，属于运气而非行为。
3. **修复（三处）**：
   - **评分侧**（`internal/planningeval/grade.go` + `types.go`）：新增 `preserve_essential_parts` 预期，把"尽量不动"按实质分解为可判定硬不变量——GPU 槽位不变 + 内存容量不降级（容量从冻结 SKU ID 形态 `mem-*-<GB>-<MTS>` 启发式解析，目录 specs 无容量字段，已验证覆盖全部 14 款内存 ID）。同品类更便宜替换（电源/机箱/散热器）仍允许。`TestPreserveEssentialPartsAllowsCheapSwapsButNotCapacityCuts` 覆盖四形态（换便宜电源过、容量升过、容量砍败、GPU 变更败）。
   - **套件侧**（`prepare_current_live_178.py`）：r3 生成器对 C123-001 把 `preserve_other_parts` 换成 `preserve_essential_parts`，provenance 说明依据；离线 replay 套件不动（旧套件仍用逐件相等口径，recording 不重评）。
   - **提示词侧**（`internal/planning/runner.go`）：evaluate 文档与 `budget_alternatives` 反馈注记追加最小替换策略——"替换优先同品类且容量或性能档位不降，不得为压预算单方面削减与用途相关的容量或档位（如内存容量、显卡档次），无法两全时交付 proposal 留待用户取舍，不要擅自砍容量后直接交付"。
   - `delivery_quality.py` 硬门分类同步加入 `preserved_essential_parts`（事实正确门）。

验证：`go test ./internal/... ./cmd/...` 全过；冻结 mechanisms 套件离线 replay 10/10（一次性 pgvector 容器，用后即删）；r3 重新生成后 plan-live 零调用校验通过。C123-001 step3 至此从"条件性不可通过"变为可判定：合法的最小替换交付可过，擅自砍容量仍判败。r3 真实模型验证需用户授权。
