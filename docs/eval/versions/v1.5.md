# 评估集 v1.5：需求确认前的多轮对话

2026-09-09 冻结，50 个场景：原 v1.4 的 40 题原样保留，新增 10 段 L5 对话。新增场景由开发者依据明确的产品规则设计，属于人工设计的合成用例，不冒充真实用户反馈；期望在实测之前确定，不由待测模型的答案生成。

| L5-310 | 用户撤回预算后重新询问，不能拿旧金额继续生成 |

## 执行与判卷

对话 fixture 使用 `turns` 数组，每轮固定用户输入和独立 `expect`；不与顶层单轮 `input/expect` 混用。一次执行包含整段对话，只有每轮均正确才通过，`-seeds 3` 重复整段对话三次。每次执行使用独立会话，回填真实前轮回复，不能把期望或假定助手回答喂给模型。

使用产品的 `NewProductScreening`、`BuildScreenInput` 和 `ParseScreeningResult`，复用最多 6 条消息、4000 字的上下文边界及产品需求字段规范化。需求单形成后，历史消息使用产品实际的确认提示，不把助手 JSON 当用户信息。这里覆盖需求确认前的多轮初筛，未模拟配置生成、数据库持久化、浏览器或完整产品状态流转。

产品按真实运行类型传入 `has_build`，尚无配置时使用单一需求草稿协议；聊天中的确认提示不能使模型擅自切换成改单。分辨率须来自用户信息，已撤回预算失效，后来的明确采购口径覆盖此前说明。字段来源识别仍是保守规则，不等于任意自然语言理解。

每轮保存模型原文、程序判出的缺失字段、发送上下文与用户来源；规范化需求单前的文本另存 `guard_text`，`text` 为有效需求载荷或追问。重放重新核验上下文及规范化过程，并逐轮重判；缺轮、串题、偷偷加入答案或更改早先输出均不能沿用原通过结果。

缺失协议版本、字符串 `"1"` 和空 notes 数组可作有限格式规范化，不改预算和型号。非法草稿 JSON 最多要求模型重试一次，每次原文保存在 `model_attempts`；`model_text` 为最后一次，调用与 token 均计数。格式重试不会把错误业务值改成标准答案，最终仍由原断言判卷。

S1–S4 继续沿用。新题可用 `spec_fields` 精确检查用途、静音/尺寸偏好、采购口径、弹性、已有品类及型号数量；未声明的字段不对旧题追溯加严。S0 检查对话轮数完整性。报告将多轮对话通过数单列，不能把一段对话的多轮当成多个独立用例。
