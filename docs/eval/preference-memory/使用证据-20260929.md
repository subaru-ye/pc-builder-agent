## 二、召回漏斗(口径冻结)

分母采用双口径,分别回答两个不同问题,不得混用:

- **口径 A(入口可发现性)**:分母 = 存在 active 白名单偏好的 owner 的新会话数。
  回答"有历史可召回的用户里,多少人触达了召回入口"。
- **口径 B(建议接受率)**:分母 = 实际载入建议并返回非空的会话数。
  回答"看到建议的用户里,多少确认/忽略/弃置"。

漏斗层级与事件映射:

| # | 层级 | 口径 | 现有设施可观测性 | 走查记录方式 |
|---|---|---|---|---|
| 1 | 建议可得(owner 有 active 偏好 × 新会话) | A 分母 | 可:偏好表 SQL | 服务端复核 |
| 2 | 入口触达(打开偏好记忆区) | A | **不可观测**(无日志/事件) | 主持人计时+观察 |
| 3 | 归属选择(选 self/具名) | A | **不可观测** | 记录选择与纠错次数 |
| 4 | 载入建议(点击载入) | A→B | **不可观测** | 计时 |
| 5 | 建议非空返回 | B 分母 | 部分:服务端知道,但不外显"被当前需求排除 N 条" | 记录建议条数(只记数) |
| 6 | 逐项动作:确认/忽略/冲突中选择 | B | 部分:确认产生编辑指纹但与手动编辑不可区分;删除可从表推导 | 逐项记录动作类型 |
| 7 | 确认生效(applied>0,进入需求) | B | 部分:state 变化可查,归因不可区分 | 服务端复核+人工记录 |

## 三、判定问题(走查汇总前必须先回答)

1. **未行动 ≠ 拒绝**:用户没点"采用"就离开,不能计为"拒绝建议";
   汇总时单列"弃置"(无动作)。
2. **空建议歧义**:载入后 0 条建议,可能是"无历史"也可能是"全部被当前需求
   排除"(服务端静默排除,用户不知道自己有被排除的历史)。走查中主持人从库
   复核排除数;这是未来入口文案的一个已知信息缺口。
3. **确认写入不可归因**:服务端无法区分"确认偏好写入"与"手动编辑同值"。
   真实试用若要自动统计层级 6/7,需一次性的最小事件(本阶段零流量,不加;
   见第五节预留口径)。
4. **冲突是边缘构造**:多 owner 冲突的自然路径是"两个匿名身份先后被同一账号
   认领",真实占比未知;走查中作为受控变体(约 1/3 被试),汇总单列,不并入
   主漏斗。
5. **具名归属的输入摩擦**:自定义归属需手输名称(最多 40 字),输错即召回空;
   记录纠错次数,不记名称本身。
6. **首次保存是漏斗前提**:层级 1 之前还有"用户是否保存过偏好"。走查显式
   引导保存(保存体验非本阶段重点,但记录自发发现保存入口与否)。

## 四、隐私最小口径

- 不记录:来源原话(quote)、偏好值(value)、代配对象名称(subject 记二元
  self/具名)。
- 记录:字段类别(field 名属于白名单五项之一,不构成个人偏好内容)、动作类型、
  计数、耗时、主持人脱敏后的误解备注。
- 服务端复核 SQL 只 SELECT 计数与类别列,不读取 `source`、`value` 列。

## 五、真实试用出现时的最小观测(预留口径,零新基础设施)

若未来开放真实试用,不建新设施,按以下纯查询口径汇总(全部复用现有表):

- 保存/改正/删除量:`owner_preference_memories` 按 status/field/subject 二元聚合。
- 召回触达与确认归因:**不可得**——需要届时作为独立产品决策加最小事件
  (一个 `preference.recall` / `preference.confirm` 事件,字段仅
  field 类别+subject 二元+动作),本文只登记需求,不实现。

## 六、结论与建议(当前证据状态)

- **入口改动(折叠区前移/自动提示)**:证据不足。决定门槛(预设,避免事后
  合理化):走查中口径 A 的层级 2(入口触达)自发率 < 50%,且被试在任务卡
  明确提到"你上周说过要安静"仍找不到入口,才支持入口前移;否则维持现状。
- **归属选择改动(自动带出历史 subject 列表/搜索)**:证据不足。门槛:纠错
  率(输错名称导致空召回)或"不知道该选什么"出现于 ≥1/3 具名变体被试。
  自动推断 subject(从 recipient)仍不做——无通道、无误推断样本,安全优先。
- 任何入口改动必须保持三条不变量,改动后回归 `cmd/evalpreference` 基线。
