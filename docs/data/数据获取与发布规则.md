# 数据获取与发布规则

> 状态：数据维护 强制规则。最后更新：2026-09-16。
>
> 本文使用“必须 / 禁止 / 应当 / 可以”表达约束。实现细节见[数据管道 数据获取与发布管道设计](../tech/数据获取与发布管道.md)。规则冲突时，以来源许可、数据正确性、历史可复现和 last-known-good 安全为优先。

## 1. 总原则

1. **来源先于结论**：事实值必须先有来源和证据，再进入 canonical 数据。
2. **具体型号先于芯片常识**：AIC 显卡、主板、机箱、散热器和电源以具体产品规格为准。
3. **未知优于猜测**：无法消歧或证据冲突时写 `unknown/null` 或隔离，不让模型补齐。
4. **候选与正式隔离**：未通过全部门禁的网络响应、模型输出和模糊匹配只能进入工作区或 quarantine。
5. **低风险可自动，高风险不覆盖**：符合本规则的低风险变化可以自动发布；异常保持 last-known-good。
6. **发布必须可复现**：来源版本、输入哈希、适配器版本、Diff、风险规则和发布决定缺一不可。
7. **历史不可改写**：价格快照、发布批次和已使用 SKU 不物理覆盖或删除；修复通过新批次表达。
8. **合法访问**：遵守许可证、服务条款、robots、访问频率和账户权限，不绕过技术限制。
9. **主链零模型**：常规采集、标准化、裁决和发布禁止调用大模型。
10. **本机自动化不冒充在线服务**：电脑关机期间不运行；下次开机补跑，不承诺 24 小时在线。

## 2. 来源等级与自动化权限

| 等级 | 来源 | 正式用途 | 自动发布权限 |
|---|---|---|---|
| A | 厂商官方具体型号规格页、说明书、官方结构化规格 | 关键字段首选 | 精确身份、确定性解析和全部门禁通过后，可进入 `active_core` |
| B | 经授权官方 API、许可明确且有 schema 的开放数据库 | 候选、价格或规格，按许可范围使用 | 低风险字段可发布；新 SKU 默认最多 `catalog_only` |
| C | 锁定版本的社区数据集、芯片数据库 | 候选和非关键字段 | 默认最多 `catalog_only`，不得覆盖具体型号关键字段 |
| D | 条款允许低频访问的公开零售页、媒体页、人工记录 | 价格候选或辅助交叉验证 | 只能按价格规则进入观察表；不能单独支撑关键规格 |
| E | 模型常识、搜索摘要、论坛转述、无来源文本 | 无正式用途 | 禁止发布 |

使用 B/C/D 级来源时必须登记许可证或条款 URL、版本、署名要求、robots 处理和访问频率。来源等级不是正确性保证；字段仍需经过 schema、身份和冲突检查。

来源只有同时满足以下条件才能启用自动采集：

- 已进入 `sources.registry.json`，用途和字段范围明确。
- 条款/许可证允许相应用途，或已获得明确授权。
- 无需绕过零售站登录、验证码、风控或付费墙；经审核的结构化 API 可以使用独立 API Key。
- 已确定频率、并发、超时、退避和停用条件。
- 有 fake HTTP 夹具和页面结构变化检测。
- 能在不记录 Cookie、Authorization 和个人数据的情况下运行。

首个已批准实现仅为固定映射的 AMD CPU 具体型号页：每周串行、最大 1 请求/秒，不搜索全站、不发现新 SKU；robots 与条款可见文本摘要变化即停用。NVIDIA 服务条款明确禁止 robot、scraper、crawler 和自动数据提取，因此不得为本项目建立 NVIDIA 自动页面适配器。

## 3. 各品类关键字段证据

以下字段影响错误级兼容判定，进入 `active_core` 前必须满足证据门槛：

- CPU：socket、支持芯片组、是否有核显、TDP。
- GPU：具体板卡长度、TDP、具体板卡供电接口。
- 主板：socket、芯片组、内存代际、板型、M.2 插槽数。
- 内存：代际；频率属于 warning 字段但仍应记录来源。
- SSD：M.2 或 2.5 英寸形态。
- 电源：额定功率、PCIe 供电接口数量与类型；纯 ITX 安装另记录 ATX/SFX/SFX-L 外形和机身长度。
- 机箱：显卡限长、风冷限高、支持板型、冷排尺寸；纯 ITX 机箱另记录支持的电源外形和电源限长。
- 散热器：风冷/AIO 类型，以及对应高度或冷排尺寸。

证据门槛：

- A 级具体型号来源且字段可确定性定位时，可以作为关键字段的自动发布证据。
- 没有 A 级来源时，两个相互独立的 B/C 级来源数值一致，可以形成候选；新 SKU 自动晋级最多到 `catalog_only`，进入 `active_core` 需要人工例外批准。
- 只有一个 B/C/D 来源时只能进入 `catalog_only` 或 `candidate`。
- 芯片级数据不得覆盖具体板卡、具体主板、具体散热器或具体电源字段。
- 已发布 SKU 的关键字段发生变化时，即使新值来自 A 级来源，也必须隔离，避免页面重构或修订版误绑定自动改写兼容性。

## 4. 型号匹配规则

正式匹配必须同时核对：

- 品牌和规范化型号。
- 厂商 part number 或其他稳定产品标识（来源提供时）。
- 容量、显存、套条数量、颜色等影响价格或规格的变体。
- OC、SUPER、Ti、XT、XTX 等型号后缀。
- V2、Rev. 1.1、2024 等修订版。
- 区域型号。

禁止行为：

- 只按模糊相似度自动合并。
- 把公版 GPU 数据写到任意 AIC 板卡。
- 把同系列不同容量、颜色或修订版共用一个价格。
- 上游查到多条时任选第一条。
- 页面标题相似但稳定标识不同仍自动绑定。

模糊匹配可以给出排序候选，但必须由精确字段规则或人工确认完成绑定。无法确认的项可以长期停留在 quarantine，不得为了维持自动化率降低门槛。

## 5. 价格规则

### 5.1 来源边界

项目不接入京东联盟 API。自动价格来源只允许：

- 条款和 robots 允许低频自动访问，且无需登录、验证码或绕过限制的公开零售/品牌官方商城页面。
- 许可和权限明确的结构化价格源。
- 人工提供的规范 CSV 例外输入。

官方建议零售价可作为 `msrp` 观察值，但不能冒充中国市场实时成交价。普通搜索摘要和大模型回答永远不能进入价格观察表；结构化购物响应只有在来源完成真实 canary、精确身份与双商家门禁后才能形成 `search_listing`，且不得解释为库存或成交价。SerpApi Baidu Shopping 在 2026-08-27 的真实 canary 未通过，因此当前不得形成正式 observation。

### 5.2 可以采纳的报价

- 商品明确可售，且与正式 SKU 的型号和变体完全一致。
- 标明来源、商品 URL、店铺、采集时间、币种和价格类型。
- 普通用户在页面明确条件下可获得的含税商品价。
- 结构化来源返回价格时记录接口/字段和响应哈希。
- 页面解析器能够区分商品价、划线价、会员价、订金和月供。

### 5.3 禁止采纳的报价

- 二手、拍卖、租赁、订金、预售尾款或分期月供。
- 必须搭售整机/套餐才能获得的拆分价。
- 仅特定地区、内部员工、私域或不可验证身份可获得的价格。
- 缺货、下架、型号不明、登录后才显示或未登记搜索摘要中的价格。
- 大模型推测、币种猜测或根据历史趋势生成的价格。

会员券、跨店满减和短时活动价可以作为观察值，但默认不作为配置快照选中价；若选用，必须在 `price_type` 和用户展示中明确条件。

### 5.4 多来源选择与异常处理

1. 过滤不合格、缺货和变体不一致的观察值。
2. 优先自营、品牌官方旗舰店或已登记的可信零售商。
3. 有三个及以上合格报价时，选择最接近中位数的实际报价，不构造平均成交价。
4. 只有一到两个来源时按来源优先级选择，并保留其他观察值。
5. 相比上一选中价变化不超过 25%、无分布异常且全部门禁通过时，可以条件自动发布。
6. 单 SKU 变化超过 25% 时隔离该 SKU并沿用上一正式值；异常数达到 `max(3, ceil(本批合格 SKU 数 × 10%))` 时隔离整批。
7. 部分安全更新按 SKU 合并，未覆盖项保留原观察日期，禁止用新发布日刷新旧价格年龄。
8. 唯一来源失效、解析结构变化或自动访问许可不明确时，来源保持 disabled/quarantine；不得切换到搜索摘要或模型回答补齐。
9. `search_listing` 至少需要两个不同商家或目标主机精确匹配才可参与选价；公开展示必须说明其不代表库存。

所有公开展示继续称为“参考价”，显示快照日期；过期状态不能被新鲜但低质量的来源掩盖。

### 5.6 同日不可变批次

迁移 00018 允许同日多个快照，以 `snapshot_id` 唯一绑定批次。默认读取最新日期、最大 ID；新配置的报价保存 ID，后续详情、分享、导出按该 ID 读价格元数据。历史只有日期的配置沿用当日首批次，不批量改写。显式按日期评估仍表示首批次；比较同日修订必须指定批次 ID。

四列 CSV 同日冲突仍默认报错，显式 `importprices -revision` 才新增批次。P12 发布使用 release/run/hash 保证重试幂等。发布日不改变观察日；原快照不删除、不刷新价格年龄。降级迁移遇同日多批次会失败，不能以删历史数据来完成降级。

## 6. 模型使用规则

自动风险分类和 `publish --policy auto` 禁止调用大模型，也禁止调用带自动模型 fallback 的代码路径。

人工显式运行时，模型可以：

- 从本次保存且许可允许处理的官方页面或 PDF 中抽取字段候选。
- 生成别名候选和商品匹配候选。
- 将结构差异翻译成审核摘要。
- 标记潜在冲突、异常值和缺失证据。

模型禁止：

- 自主浏览后直接提交事实值而不保存原始来源。
- 使用训练知识填补价格、尺寸、供电、插槽或性能分。
- 修改正式 catalog、parts、prices、styles、release 或数据库。
- 在证据冲突时自行选择“更合理”的值并隐藏冲突。
- 把模型置信度当作来源可信度或自动发布依据。
- 在模型失败时自动换供应商继续发布主链。

模型输出必须进入 quarantine，使用固定 schema，并记录 provider/model/schema 版本；每个字段要能定位到原始快照。后续必须由确定性规则重新确认或人工批准，且发布 manifest 明确 `model_used=true` 和 `decision=manual`。

合法 JSON 不等于事实正确。至少执行以下语义校验：

- `Recommended PSU`、`Minimum PSU` 不得映射为 GPU `tdp_w` 或板卡功耗。
- L/W/H、长/宽/高必须按页面标签映射，不能按数值大小猜测。
- “月供”“订金”“到手价”和“标价”不得映射到同一价格类型。
- 页面未出现目标标签时必须为 unknown/null，不能用邻近数字补位。
- evidence 摘要的标签、数值和单位必须与候选字段一致。

## 7. 网络访问、原始数据与安全

- API Key、Cookie、Authorization、签名参数和个人账户信息只进入环境变量或凭据存储。
- 日志、manifest、Git Diff 和模型记录不得包含凭据。
- 原始响应必须计算 SHA-256；可记录脱敏后的 ETag、Last-Modified 和 Content-Type，不记录认证头。
- 优先使用 ETag/Last-Modified 条件 GET；没有条件请求时用内容哈希避免无变化发布。
- 自动重试仅限明确幂等 GET，使用有限指数退避和随机抖动。
- 登录页、验证码页、风控页被误识别为商品页时必须失败。
- 401、403、429、robots 或条款变化必须停止该来源，不能切换代理、账户或备用未登记页面。
- 不得绕过验证码、代理封禁、付费墙、地区限制或访问频率限制。
- 原始页面默认不提交 Git；许可证允许且复现确有需要时另行评审。

## 8. 风险分类与发布

### 8.1 自动发布的必要条件

自动发布必须同时满足：

- 来源已启用且条款/robots 状态有效。
- SKU 和变体精确匹配，所有变化由确定性适配器产生。
- 关键字段有足够证据且无来源冲突。
- 不包含已发布关键字段变化、隐式删除、跨品类移动或异常空值。
- 不包含价格跳变、批量异常或大规模退休。
- canonical、coverage、规则 golden、导入预检和敏感信息扫描通过。
- review 之后输入哈希未变化。
- 数据主链运行中 `model_used=false`。
- 数据库事务、release manifest 和 last-known-good 切换能作为一个可恢复发布过程完成。

### 8.2 自动晋级

- 新 SKU 只有 A 级具体型号证据、关键字段完整、身份精确、价格新鲜且全部门禁通过时，才可自动进入 `active_core`。
- B/C/D 来源或价格不满足核心池要求时，安全数据最多自动进入 `catalog_only`。
- 证据冲突、身份不确定或 schema 不完整时保持 `candidate`/quarantine。
- `retired` 必须是显式状态；单批退休超过 5% 或来源突然消失时不得自动发布。

### 8.3 发布原子性

发布器必须 fail-closed：

1. 在临时目录构建完整不可变 release。
2. 校验输入输出哈希、门禁和上一 release 关系。
3. 通过 PostgreSQL advisory lock 执行 Go 单事务导入。
4. 数据库成功后原子切换 `current.json`；失败则数据库回滚、指针不变。
5. 只对指纹变化项执行增量 embedding；embedding 失败时按实现定义回滚整个发布或保持新数据不可推荐，不能出现表面成功的部分状态。

历史 release v1 只含八类 parts，必须继续可验证、导入和回滚；新 release 使用 v2，把八类 parts 与 `evidence/fields.jsonl` 分别哈希后再生成联合输入哈希。parts、publication 和 evidence 必须在同一数据库事务提交，任何 evidence 非法或元数据冲突都整体回滚。

自动任务禁止执行 Git commit、push 或部署。Git 继续管理代码、schema、来源规则和 seed；本机不可变 release 与 `data_publications` 记录日常运行事实。

## 9. 维护频率与运行恢复规则

| 任务 | 目标频率 | 自动化边界 |
|---|---|---|
| 数据健康与过期检查 | 每天 | 只读检查与报告（`pcdata health`） |
| `active_core` 规格 | 每周 | 确定性采集；安全批次可自动发布 |
| `active_core` 价格 | 按批次按需 | 当前无自动价格来源；买手/人工批次按需更新，超龄 SKU 如实展示 stale，不定期空跑 |
| 失败来源重试 | 每周一次错峰 | 只重试幂等 GET，不绕过限流 |
| 上游数据集版本检查 | 每月 | 报告新版本，不静默改 lock |
| 新 SKU 发现 | 每月或新品发布时 | 只写 candidate；满足严门槛才晋级 |
| 官方规格核验 | 每周增量 | 确定性适配器；关键字段变化隔离 |
| 性能分刷新 | 月度或季度 | 取决于来源许可和版本 |
| embedding | 每次正式发布后 | 只重算指纹变化项 |

上表是维护目标频率，不代表已安装自动调度：2026-09-21 起项目不再运行本机定时任务，每一行都需要维护者显式执行对应命令。

单个 `failure_mode=isolate_source` 来源失败时，其他来源仍可完成，run 标为 `partial` 且 last-known-good 不变；本机 checkpoint 文件是恢复权威，数据库 `source_checkpoints` 只作可观测投影。

人工运行必须：

- 拒绝同一工作区并发；文件独占锁之外，发布再使用数据库 advisory lock。
- 使用绝对项目路径和固定环境配置。
- 启动前按 Compose service 名检查 `postgres`；`redis` 仅用于可选通知，不依赖 container name，也不阻塞发布主链。
- 保留 run manifest 的 `profile`、`trigger`、`scheduled_for` 字段以兼容历史记录，新记录 `trigger` 使用 `manual`。

## 10. Last-known-good 与降级

- 来源失败、页面变更、条款变化、网络中断、模型辅助失败或数据库不可用时，保持上一正式 release。
- 失败来源不得由低等级来源自动替代。
- 价格来源失败时继续显示上一参考价和增长后的 stale 年龄。
- 某个 SKU 隔离不应阻塞其他互不依赖 SKU 的安全发布。
- 同一 SKU 的关键字段和价格必须来自一致的发布视图，不能混用半个新批次。
- 恢复后从固定原始哈希或重新采集开始；不得继续消费不完整临时文件。
- 每次回滚必须产生新的发布/运维记录，不删除失败 run。

## 11. 质量指标

- `active_core` 错误级字段证据覆盖率：100%。
- `active_core` 价格覆盖率：100%。
- `active_core` 价格平均年龄：按批次节奏管理，目标 ≤30 天；不满足时如实展示 stale，不得用低质来源刷新时间戳掩盖。
- 自动错误匹配：0 容忍；发现后必须补回归夹具。
- 无来源正式字段：0；合法 unknown 不计为违规。
- 发布失败导致正式数据部分更新：0。
- 主链运行模型调用次数：0。
- 无变化运行产生新 release：0。
- 错过计划后下一次开机补跑成功率：100%（基础设施可用时）。
- 稳态人工维护：连续四周平均 ≤30 分钟/周。

这些指标不能通过扩大模型权限、降低证据门槛、隐藏 stale/unknown、忽略隔离项或自动更换来源来达成。
