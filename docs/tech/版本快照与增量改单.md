# 版本快照与增量改单

> 本文维护不可变版本、ChangeRequest、锁定与差异导出。结构化字段以 `internal/schemas` 为准，数据库以编号迁移为准；默认选配策略见 [Harness](Agent-Harness-2.0.md)。

## 1. 目标与范围

- **范围内**:迁移 00004(requirements/builds);`schemas.ChangeRequest`;版本落库挂进校验节点交付分支;改单状态块(代码维护);锁定的确定性校验;`cmd/builds` CLI(list/diff/export)。
- **关联模块**:卡片操作由 Web 预填自然语言草稿；A2A 与 Redis 负责传输和会话恢复，跨会话画像仍未实现。

## 2. 库表(编号迁移 00004)

```sql
CREATE TABLE requirements (
    id         BIGSERIAL PRIMARY KEY,
    session_id TEXT NOT NULL,
    spec       JSONB NOT NULL,          -- 初筛产出的 RequirementSpec 原文(或代码派生版,见 §4)
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE builds (
    id             BIGSERIAL PRIMARY KEY,
    session_id     TEXT NOT NULL,
    version        INT  NOT NULL,       -- 会话内 1 起递增,由代码派生(parent.version+1)
    parent_id      BIGINT REFERENCES builds(id),        -- NULL = v1
    requirement_id BIGINT NOT NULL REFERENCES requirements(id),
    change         JSONB,               -- 产生本版本的 ChangeRequest 原文;v1 为 NULL
    draft          JSONB NOT NULL,      -- BuildDraft 全文(selection + rationale)
    validation     JSONB NOT NULL,      -- ValidationReport
    quote          JSONB NOT NULL,      -- Quote(含 snapshot_date,报价绑定快照日期)
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (session_id, version)
);
```

- 版本号是**代码真值**:落库时取会话最新版本 +1;模型自报的 `build_ref` 仅存于 draft 内,交付文本与 diff 一律用 DB 的 `vN`(开发约定)。
- down:按依赖顺序删两表。

## 3. 版本落库挂点(校验节点交付分支)

- `decide` 裁决为交付(pass/review)后,校验节点在同一确定性代码路径调 `store.SaveBuildVersion`(单事务:必要时插 requirements 行 + 插 builds 行,返回版本号)。
- **落库失败要响不静默**:交付文本改为如实报告"配置有效但版本落库失败:{err}"并出栈,不展示假成功。
- store 包维护**运行时写路径**:版本表是业务核心状态,归 store 合理;parts/prices 仍只读。
- session_id 取 ADK 会话 ID(InvocationContext);console 与 dev UI 天然每会话一棵版本树。

## 4. ChangeRequest 解析与增量重生成

- `internal/schemas` 维护 `ChangeRequest` 严格解码(字段口径见代码契约;单次请求只承载一类意图,intent 与对应必填字段联动校验)。
- **初筛 Agent**:会话已有版本(状态块存在)且用户消息是改单请求时,产出 ChangeRequest JSON(仍写 `requirement_spec` 状态键);超出三类意图 → 降级为输出新 RequirementSpec 整单重生成并向用户说明。下游确定性代码按"能否严格解码出 intent 字段"区分两种载荷。
- **派生需求单由代码计算**:adjust_budget → 基版本需求 budget_cny+delta;change_constraint → constraint_patch 字段覆盖;swap_part → 复用基版本 requirement_id 不插新行。派生失败(基需求解不动等)如实报错。
- **锁定语义(冻结)**:
  - swap_part:解锁集 = {swap.category},其余全部硬锁定;
  - adjust_budget / change_constraint:硬锁定 = `locked_categories` 显式项;提示词纪律"改动最少品类,其余保持原 SKU 一字不差"。
- **锁定是确定性校验**(FR-402 100% 正确率不靠提示词):校验节点比对新 selection 与基版本 selection,硬锁定品类 SKU 有变 → 按 fail 回喂定向修复,计入轮数;锁定件导致兼容性 fail 时按既有熔断纪律如实交付失败,不自动解锁。

## 5. 改单状态块(代码维护、显式注入)

- 校验节点每次交付时把结构化状态块写入 `build_state` 状态键(JSON):`{version, build_id, selection, total_cny, snapshot_date, budget_cny, budget_remaining_cny, history: ["v1 ¥7791", ...]}`;预算解不出记 null 不崩。
- legacy 生成侧可使用 `{build_state?}` 状态注入；默认 Harness 显式接收基版本与锁定输入——**绝不让模型翻历史自己统计**(开发约定);生成 Agent 改单时基版本 selection 从状态块取。
- 该状态块由 Redis 会话热上下文保存,字段新增当"改表结构"级别对待(开发约定)。

## 6. cmd/builds CLI(回放 / diff / 导出)

- `list -session X`:版本树回放(version/parent/created_at/合计/意图摘要)。
- `diff -session X -from 1 -to 3`:逐品类文本 diff(不变 | old→new + 单价差)+ 合计差 + 预算变化;纯 Go 确定性生成,直连 DB 读。
- `export -session X -version N [-o file.md]`:Markdown 配置单——需求摘要、配置表(品类/SKU/品牌型号/数量/单价)、合计 + **快照日期**、校验结果摘要、**免责边界**(报价为 snapshot_date 快照参考价非实时;兼容性结论基于收录参数,下单前请以官方规格页复核;不构成购买建议)。

## 7. 提示词增量

- 初筛:改单 SOP(判定是否改单 → 归类三意图 → 产出 ChangeRequest;超范围降级整单重生成并告知)。
- 生成:改单模式纪律(锁定品类照抄基版本 SKU 一字不差;目标品类候选由 Harness 准备；legacy 可用两路检索工具;预算以状态块中新预算为准)。
- 静态前缀冻结不动,状态块走消息尾部注入(开发约定);提示词改动后跑固定模型评估集与相关 Live 回归。

## 8. 验收

1. **用例 C/D**:console 单会话脚本「8000 元 2K 玩黑神话」→ v1 →「降 500 优先砍哪」→ v2 →「换成 A 卡」→ v3;`cmd/builds list` 见三版本树,v2/v3 未涉及件与基版本 SKU 逐一相同(锁定正确),`diff -from 1 -to 3` 正确。
2. **用例 E**:`export -version 3` 产出 md,人工核对含快照日期与免责边界。
3. **用例 A 回归**:整单生成端到端 pass 不回归。
4. 质量门:gofmt / build / vet / test(含 store 版本读写 PG 集成测试)/ lint 全绿。
