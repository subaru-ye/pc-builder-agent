# Spec：评估工作台失败案例分析与修复闭环

## 执行状态

已按明确启动指令完成只读接口、版本控制下的人工索引和“失败案例”工作区，并通过本机离线与浏览器验收。仅读取已有冻结证据，不修改历史产物、不启动模型评估。实施与验证记录见[本机验收](../eval/evaldesk-bad-case-validation-20261008.md)；独立保留集和发布验证不在本次完成范围。

## 目标

将分散在运行详情、运行对比、提示词迭代和修复文档中的证据串成：

**发现失败 → 查看实际与期望 → 确认根因 → 关联修改 → 验证效果 → 保留回归历史。**

用户应能在工作台回答：问题发生在哪道题、哪次重复、哪一轮；此前为何修改；修改涉及提示词还是代码；哪些测试支持修复有效；还有哪些未验证的范围。

## 现状与依据

- Screening / Builder 已按测试目的和实验批次组织运行；详情有逐题、逐次重复、逐轮证据与冻结输入、期望。
- 运行对比能展示改善、退步、持续失败；提示词迭代已展示原因、具体调整、验证效果、依据和关联运行。
- 当前没有独立案例入口，也没有结构化的“问题—修改—验证”关联；代码修复不能仅靠提示词历史承载。
- [证据落库修复](screening-v2-evidence-grounding-fix.md)记录了 `cv-owned-model-flow` 无依据撤销已有件的根因、提示词与守卫修改、回归测试和两批运行。这是首批闭环样例。
- [工作区改版](evaldesk-workspaces.md)说明当前页面能力与边界；Builder 当前仅覆盖 `policy` / `ui-contract`，不覆盖真实选件质量。

## 范围

### 纳入

- 增加“失败案例”工作区，位于导航“验证”分组。
- Screening / Builder、逐题证据、运行对比、提示词迭代到案例详情的关联入口。
- 已保存运行的失败断言、否决项、逐轮观测、冻结题目及证据完整性。
- 根因、处理状态、提示词和代码修改、回归测试及验证运行的人工审阅索引。
- 历史案例保留、再次失败提示、跨版本证据的可比性说明。
- 运行级问题独立展示，包括延迟、provider 失败、预算和门槛不可评估；不伪造对应题目。

### 不纳入

- 不在工作台直接修改代码、提示词、题目、金标、评分器或门槛。
- 不增加启动、重跑、重判或发布按钮；不自动调用模型分析根因。
- 首期不增加浏览器中的记录编辑、数据库、账号、任务分派或通知系统。
- 不迁移旧产物，不补造缺失提示词原文或历史验证结果。
- 不接入 planning-v2 的 Builder 输出质量评估；后续按该评估体系单独扩展。

## 信息架构

### 1. 案例列表

默认展示未归档范围的「待处理」目录，分别提供「已验证修复」「历史与模型探索」「证据待补齐」和全部分类。后端对全量原始记录归类，每条只归入一个分类；同题的不同断言、重复运行和冻结版本按分类组织为一个入口，运行级记录按层/指标归组。目录组织不把跨版本记录合成同一根因，不自动认定历史问题已修复。

每行只显示场景、对象/层与题号、记录/运行/版本数量、一个明确结论及时间。历次通过与失败、模型身份、断言和人工处理依据进入详情；不在主列表并排显示「通过／未通过」。主要筛选只保留对象、类型和搜索，实验目的、历史表现、归档和验收范围默认折叠。旧 `bad_status=all` 仍进入默认待处理目录，全部历史须显式选「全部分类」。

固定索引的可选 `reference` 声明验收参考准确目录、显示名称和来源依据；不自动选择最新模型运行。后端复用冻结身份比较，仅在完整 manifest/gates、判卷、范围、重复次数、运行语义与证据一致时，投影同题全部重复或相同运行指标的冻结成绩。参考通过不自动更新人工状态、不作跨模型或跨代码修复归因，也不代表今日代码重新评估。参考已通过和未评估记录归入历史；缺少同版本验收或冻结证据归入待补齐。人工待验证优先，不能因不同模型参考通过就收起。概览给出唯一处理结论和原因，验证/历史分区可进入参考证据。

本机全量目录核对见[目录清单](../eval/evaldesk-case-inventory-20261009.md)。`bad_bucket` 保存分类，`bad_group` 保存归组目录；分组内可切换原始稳定 ID，旧 `bad_id` 链接继续有效。反向关联入口也按组去重。

列表分“题目案例”和“运行级问题”，运行级延迟超标不能显示为某道题行为失败。未通过、已跳过、门槛不可评估和证据不完整分别标注。

### 2. 案例详情

按阅读顺序展示：

1. **问题概览**：场景、表现、处理状态、适用版本及证据完整性。
2. **实际与期望**：输入/前置状态、冻结期望、实际操作与回复、失败断言；优先定位失败重复和轮次，其他重复可切换。
3. **根因分析**：结论、已确认/待确认、证据链接和仍未知的部分。
4. **修复记录**：为什么改、改了什么、代码身份、提示词原文 diff、回归测试及来源文档。
5. **验证结果**：修复前后逐题结果、重复稳定性、整批退步项、冻结总门槛及未验证范围。
6. **出现历史**：各实验/运行中的出现与验证记录，保留修复前失败。

长原始观测、技术身份与源文件摘要默认折叠，但均可核对。缺失内容显示“未记录”，不从当前题库、当前源码或邻近运行补填。

### 3. 现有页面入口

- 对象页在对应实验中提供“查看失败案例”，携带对象、实验和运行上下文；总门槛问题与本侧题目失败分开。
- 逐题详情提供“查看案例与修复记录”；没有人工分析时标为“未审阅”，同时展示历史表现与可核对的验收参考，不生成虚构修复记录。
- 提示词迭代显示“关联案例”，链接到对应失败证据；案例详情反向链接到提示词版本与 diff。
- 代码修改直接关联完整提交/审阅记录，不要求该提交必须改过提示词。
- 运行对比的改善、退步题目可进入对应案例。

新工作区沿用 `area` 导航；案例、选中出现记录、修复记录和验证对通过 URL 恢复。入口只传稳定 ID，不接受客户端传入文件路径。返回时恢复筛选与所选记录。

## 证据与关联合同

### 案例身份

单次题目失败证据至少由 `run_id + layer + case_id + repeat + assertion` 定位，轮次只有实际保存时才记录。

同一冻结题目版本以 manifest 身份、层和题号识别。题号相同但内容版本不同，不能自动视为同一问题；跨版本关联由人工审阅说明内容差异。不同失败断言也不能只因题号相同就合并根因。

人工问题记录有独立稳定 ID，可引用多个出现记录及修复尝试。未审阅失败仍有可浏览入口；无需先写根因才能查看。

### 首期审阅索引

采用版本控制下的固定 JSON 索引 `docs/eval/bad-case-reviews.json`；复用现有 `prompt-iterations.json` 的读取、校验与说明展示模式，避免建立另一套服务。已录入首批五个审阅问题。

记录的最小内容：

| 内容 | 必须表达的含义 |
|---|---|
| 身份 | schema 版本、问题 ID、题目/运行级类型、对象、标题与摘要 |
| 出现记录 | 准确运行身份、层/题号/断言，或运行级 metric；可选 repeat/turn |
| 分析 | 根因文字、确认状态、来源依据、审阅时间 |
| 修改 | 修复尝试 ID、完整代码提交、可核对的提示词内容版本/快照、调整说明 |
| 回归测试 | 测试名称与证据；仅新增测试不等于已经执行通过 |
| 验证 | 明确选择的基线/候选运行、范围、结论与限制 |

代码提交不等于提示词内容版本；dirty 运行不能仅凭提交还原。无法匹配的引用显示缺口，不自动找最近运行替代。

Go 端负责从冻结报告、逐题证据和审阅索引提供投影；Next.js 只组织展示，不重算 Pass^k、门槛、显著性或发布结论。比较复用现有接口；如当前接口缺少必要身份检查，在共享后端补齐，不能在页面另造评分逻辑。

## 状态与结论

处理状态以人工审阅记录为准，验证事实以明确关联的冻结产物为准，两者独立展示。

| 状态 | 条件 |
|---|---|
| 未审阅 | 有失败证据，无已确认根因；不等同于现役方案未修复 |
| 已定位 | 已确认根因，并有可核对依据 |
| 待验证 | 已关联修改，尚无满足约定范围的验证记录 |
| 验证通过 | 人工确认所选验证满足该问题的验收条件，显示实际覆盖范围 |
| 再次失败 | 后续指定回归候选再次触发同一问题；保留原修复和验证记录 |

换模型探索臂、消融或旧版本重判中的失败不自动撤销当前方案的修复状态；分别记录实验上下文。用户选择新回归候选作为验收依据后，才更新当前处理结论。

“验证通过”至少要求目标案例所有适用重复通过，相关断言/否决项无退步，验证身份可核对。只通过局部题目时标注“该案例验证通过”，仍展示整批未通过项；不能升级为“整体通过”或“可以发布”。未跑 holdout 明示“未完成独立保留集验证”。

## 可比性与数据边界

- 严格前后比较须核对题目版本、评分器、门槛、split、重复次数和运行语义。要判断某项修改的效果，还需核对模型配置及其他代码变化。
- 同题号不同内容、不同 grader、live 与 replay 混用等情况，仅并排展示证据与差异，不给因果改善结论。
- 同时改提示词和代码时，明确“组合修改”，不把结果归因于提示词单因素。
- 已暴露 holdout 可展示既有失败证据，但不能把针对该题的修复结果当独立泛化证明；转回归和新增盲测需单独版本化治理。
- 案例关联不会改变任何冻结结论。归档、缺文件、哈希异常和引用不存在均可见，读取失败提供重试，不显示为零失败。
- 复用现有 loopback、GET-only、固定路径与文件大小限制；索引文本作为数据渲染，不执行命令，不返回凭据或隐藏思维链。

## 首批审阅范围

优先串联证据落库修复中的四类问题及二次撤销授权修复，依据准确提交、文档和运行记录逐项核对。

首个完整样例为 `cv-owned-model-flow`：首轮修复运行中的无依据撤销，关联 `f7290a5c8ce75e22eb63f454446af178b39fa810`、`TestPrepareRemoveExistingPartsRequiresRemovalEvidence`，对照 `screening-fix-live-devcal-r3-20260924` 与 `screening-fix2-live-devcal-r3-20260924`。展示组合修改、多轮 6/7 → 7/7、关键字段错写 2 → 0，以及未运行 holdout 的边界。

该问题在 Kimi/GLM 模型实验中再次失败时，展示为相应实验臂的观察，不据此认定 Flash 修复失效。延迟门槛等运行级问题进入独立分组，不能伪造题目根因。

### 全量历史关联补齐（2026-10-09）

首批5条记录只整理出3个已验证场景，不能表示全部历次修复。现已逐项登记62个旧合同失败题的实现来源、旧观测显式重判及最终候选验收，覆盖 reducer/readiness、Screening 采集、确认/Builder 门禁与 UI 合同；与首批场景重叠后，已验证入口共62个。详见[全量核对清单](../eval/evaldesk-case-inventory-20261009.md)。

历史验收使用 `validation_kind=historical`，要求人工登记修复来源、旧观测来源报告完整SHA-256一致、重判与候选完整manifest/gates/grader和冻结题目相同、候选代码身份干净且目标全部适用重复通过。此口径只确认历史修复合同在冻结候选中满足，不放宽既有严格配对条件，不宣称同模型改善、单因素因果或今日代码复测。详情明确显示运行模式、重复次数与模型身份差异。

认证已登记的两项保留集用途捕获失败与一项确认夹具问题已单列待处理，不能被开发/校准验收关闭；加上跨模型验证缺口，待处理共4项。未归档运行指标另有10个后续可比验收缺口，不是10个独立未修复题目。换模型探索与全部冻结失败仍保留，认证NO-GO不变。

## 验收标准

1. 用户从任一对象页能进入相关失败，并看见冻结输入、期望、实际行为和具体失败重复；未评估项不计为行为失败。
2. 首批样例能双向跳转“案例—提示词 diff/代码修改—回归测试依据—前后运行”，所有数字与原始报告一致。
3. 案例修复验证、整批总门槛、发布验证三个结论可区分；历史失败、部分验证和再次失败均保留。
4. 纯代码修复、未标注根因、缺失历史原文、dirty 身份、未知引用和跨版本不可比均有明确展示，不自动归因。
5. 多次重复和同题号跨版本不会错误合并；新模型诊断不会静默更改现役方案的问题状态。
6. URL、返回、刷新、筛选和归档可恢复；读取错误可重试；已有六个工作区不退化。
7. 复用现有设计 token、行与分隔线；1440/768/375 宽度、深浅主题无横向溢出，键盘可用，axe 严重/关键问题为零。
8. 后端投影/身份校验、索引校验及前端关键闭环有针对性测试；本机真实产物抽查无外部请求、无模型调用、无产物修改。

## 实施顺序与依赖

实施按“核对最小索引与身份 → 后端只读投影 → 案例页与双向入口 → 真实证据及 UI 验收”完成。首期为可浏览闭环，不建设浏览器编辑或评估调度。

[提示词保守精简 spec](screening-prompt-conservative-compression.md)可引用本页案例作为防退化依据；实验本身不依赖本工作区先完成。该实验的工作台展示若本页未实施，可先复用现有提示词迭代与运行对比。
