# 服务与状态

> 本文维护 A2A 服务边界、Redis 会话与缓存、版本快照与增量改单。结构化字段以 `internal/schemas` 为准，数据库以 `db/migrations` 编号迁移为准；模型角色配置见[技术选型 ADR-007](技术选型.md)。

## 1. A2A 服务边界

初筛消费方(`cmd/host`/`cmd/api`)与 `cmd/buildsvc` 之间保持**单跳**：初筛/产品进程只持有低价档 Screening 模型与 buildsvc 的 agent card URL;生成、规划循环、Store、Embedder 全部留在 buildsvc。循环留在服务进程内,不把生成与校验拆成跨服务循环。

- 根 Agent 名 `pc_build_service`,经 `adka2a.NewExecutor` + `a2asrv` 挂载;客户端用 `remoteagent.NewA2A` 作为 Sequential 的第二个子 agent。
- **contextID 映射**:执行器 `toInvocationMeta` 取 `sessionID = reqCtx.ContextID`;客户端每轮从上一条远程事件元数据复用同一 `contextID`,build_state/会话按 contextID 在服务端跨轮持久。
- **只传结构化载荷**:`BeforeRequestCallbacks` 把消息 parts 替换为唯一一条 RequirementSpec/ChangeRequest(或 planning 输入)JSON 文本,丢弃对话全文与推理;`ContextID` 不动。
- **schema 校验双端**:host 发送前试解记日志,buildsvc 的 ingest 入口节点把干净 JSON 写入 state;严格解码只有 `internal/schemas` 一份定义。
- **控制面/数据面分离(F2)**:planning 完整产物(含证据全文)按 run 归档在 PostgreSQL `planning_artifacts(run_id, session_id, payload)`;A2A 只回控制面(outcome/delivery/issues/reply/draft/quote/validation/计量)。产品按 run_id 读回重载荷,`session_proposals.result` 与传输副本中的证据正文降为 240 rune 预览。终态事件镜像进 `run_events`,不受 Redis 24h TTL 限制。
- **取消与超时**:产品侧 run 有 10 分钟上下文约束;buildsvc planning 循环每轮开头轮询取消标志(a2a-go 服务端执行与请求 ctx 分离,断连不会取消生成)。
- 设计取舍:单跳拆分是 A2A 学习目的,非性能需要;多 Agent token 开销数倍,如实定位。

buildsvc 监听 `BUILDSVC_ADDR`(默认 `:8081`),消费方读 `BUILDSVC_URL` 解析其 well-known agent card。

## 2. Redis 会话与缓存

`internal/redisstore` 提供 ADK `session.Service` 的 Redis 实现 + query 向量化缓存装饰器。业务版本由 PostgreSQL 持久化;跨会话用户画像不在当前实现范围。

### 会话

- 配置 `REDIS_ADDR` 时,host 与 buildsvc 注入共享 Redis SessionService;未配置时降级 `session.InMemoryService()` 并告警一行,保证无 Redis 的 CI / `go test` 仍可跑。host 保存对话与远程 contextID,buildsvc 按 contextID 保存 build_state;key 按 appName 隔离。
- **key 设计**(前缀 `pcb:sess`):`pcb:sess:{app}:{user}:{sid}` 整体保存会话 JSON(state+events);app/user 级 state 独立键。`List` 用 `SCAN MATCH`。
- **TTL**:会话键统一 `REDIS_SESSION_TTL`(代码回退 24h,`.env.example` 示例 720h),`Create` 与每次 `AppendEvent` 时滑动刷新,活跃会话不因 TTL 掉线。
- **行为契约**:`Get` miss 必须返回 error(runner 靠 error 判断“不存在再 Create”);`AppendEvent` 对 `Partial==true` 直接 return nil,持久化前 trim `temp:` 前缀 StateDelta;state 三层作用域(app/user/session)按官方 `sessiontestsuite` 校验。
- 恢复链路:进程重启后按同一 sessionID `Get` 恢复对话历史 + 远程 contextID 元数据,下一轮改单在同一 contextID 续上。

### embedding 缓存

- 装饰器实现 `EmbedOne(ctx,text)`,包住真实 embedding client;key `pcb:emb:{identity_hash}:{sha256(text)}`,identity 为 provider、endpoint host、model、dimensions。命中直接返回,未命中写回并设 `REDIS_CACHE_TTL`(默认 7 天)。日志命中/未命中各一行。
- 正确性依据:同一模型身份配置 + 同一 query 文本 → 同一向量。降级:无 Redis 时装饰器不启用。
- **LLM 结果缓存明确不做**:`GenerateContent` 是流式,每轮请求带增长的对话历史,多轮命中率约 0;成本控制沿用模型分档 + 循环熔断 + token 预算。

## 3. 版本快照与增量改单

### 版本树(迁移 00004)

`requirements` 保存 RequirementSpec 原文;`builds` 保存 `version`(会话内 1 起递增)、`parent_id`(NULL = v1)、`change`(产生本版本的 ChangeRequest)、`draft`、`validation`、`quote`(绑定快照日期)。UNIQUE(session_id, version)。

- **版本号是代码真值**:落库取会话最新版本 +1;模型自报 `build_ref` 仅存于 draft,交付文本与 diff 一律用 DB 的 `vN`。
- 版本落库挂在校验/交付节点交付分支,单事务插 requirements(必要时)+ builds。**落库失败要响不静默**:如实报告“配置有效但版本落库失败”。
- 修改产生子版本,不覆盖旧配置;旧 build 按已保存的 SKU、价格和快照回放。

### ChangeRequest 与锁定语义(冻结)

- 单次请求只承载一类意图:swap_part / adjust_budget / change_constraint,`internal/schemas` 严格解码并联动校验;超出三类意图 → 降级整单重生成并向用户说明。
- 派生需求单由代码计算:adjust_budget → 基版本预算+delta;swap_part → 复用基版本 requirement_id;派生失败如实报错。
- **锁定**:swap_part 解锁集 = {swap.category},其余品类 SKU 硬锁定;adjust_budget/change_constraint 硬锁定 = `locked_categories` 显式项。锁定是确定性校验:硬锁定品类 SKU 有变 → fail 回喂定向修复;锁定件导致兼容性 fail 时如实交付失败,不自动解锁。
- 提示词纪律“改动最少品类,其余保持原 SKU 一字不差”;生成 Agent 改单时基版本 selection 从程序注入,绝不让模型翻历史自己统计。

### cmd/builds CLI(回放 / diff / 导出)

- `list -session X`:版本树回放。
- `diff -session X -from 1 -to 3`:逐品类文本 diff + 合计差 + 预算变化;纯 Go 确定性生成。
- `export -session X -version N [-o file.md]`:Markdown 配置单——需求摘要、配置表、合计 + 快照日期、校验摘要、免责边界(报价为快照参考价非实时;兼容性结论基于收录参数,下单前请以官方规格页复核)。
