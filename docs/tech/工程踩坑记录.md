# 工程踩坑记录

本文件沉淀可复用的工程经验，不是运行日志或待办清单。协作规则见 [AGENTS.md](../../AGENTS.md)，工程边界见 [开发约定](开发约定.md)。以下首批记录来自现有代码、测试、修复文档和已核对的工作台问题，不代表本次重新执行了历史模型评估。

## 维护方式

- 每项记录现象/触发、根因、正确处理、验证依据、适用范围。
- 根因尚未确认时明确标为推测；测试未执行、历史原文未保存、泛化未验证分别说明。
- 同根因持续更新一项；长分析、实际运行和待办分别链接到 change、评估证据和路线图。
- 不记录凭据、私人数据或整段请求日志，不把计划中的修复写成已完成。

## 评估分类有记录，切换后却显示全空

- **现象/触发**：从真实调用的模型实验切到“程序回归”，分类有记录，但结果与实验列表为空。
- **根因**：测试目的与执行方式是独立过滤条件，切换目的仍保留旧 `live` 条件；程序回归记录是确定性执行，没有交集。
- **正确处理**：切换目的清除旧执行方式和所选结果；显式冲突 URL 展示筛选原因与恢复入口，不呈现全空分数占位。共享筛选逻辑同时覆盖 Screening / Builder。
- **验证依据**：`web/e2e-evaldesk/reqv2.spec.ts` 中“从真实调用切换程序回归清除旧筛选”和“选配按目的展示全部批次”覆盖切换、冲突深链与刷新恢复；实现见 `SideWorkspace`。
- **适用范围**：所有具有组合筛选的列表。分类数量必须说明其统计范围，不能把未命中筛选解释成没有产物。
- **详情**：[工作区改版](../changes/evaldesk-workspaces.md)。

## 后端摘要缺字段，被误读为没有评估结果

- **现象/触发**：运行记录存在，旧服务未返回 `layer_scores`，两对象页面显示零记录或无结果。
- **根因**：前端用缺失的摘要字段判断本侧是否评估，将协议缺口与真实零覆盖混淆。
- **正确处理**：摘要直接投影冻结报告；兼容旧服务时从详情补齐。详情读取失败明确报错并可重试，不填零、不靠摘要文字反解析分数。
- **验证依据**：`web/e2e-evaldesk/reqv2.spec.ts` 中“旧服务缺少目录分层摘要时从详情补齐两侧结果”和“分层详情读取失败显示错误”覆盖兼容与失败路径；实现见 `web/src/lib/evaldesk/reqv2.ts`。
- **适用范围**：前后端协议升级和旧产物兼容。未知、未评估、零分、读取失败是不同状态。
- **详情**：[工作区改版](../changes/evaldesk-workspaces.md)、[Web 客户端](Web客户端.md)。

## 当前提示词、代码提交与历史模型效果混为一谈

- **现象/触发**：只有当前编译提示词，却被当成历史运行使用的原文；或把同批提示词与守卫修改后的提升全部归因于提示词。
- **根因**：内容版本、代码身份、运行时证据和效果验证是不同对象。dirty 运行不能仅凭 HEAD 还原；哈希不能还原未保存原文；提示词与代码共同变化不能识别单因素效果。
- **正确处理**：区分当前编译原文、Git 提取静态原文与运行保存原文，保存内容指纹和准确关联；缺失则标“未记录”。列出所有共同变动，引用冻结运行数字，不从时间相邻自动归因。
- **验证依据**：`docs/eval/prompt-iterations.json` 的 `6c533be` / `f7290a5` 记录明确组合修改和未跑 holdout；相关代码/测试见 `internal/evaldesk/reqv2_prompt_versions.go`、`internal/evaldesk/reqv2_prompts_test.go` 与 `web/e2e-evaldesk/reqv2.spec.ts`。
- **适用范围**：提示词迭代、模型实验、修复效果分析。开发/校准通过不等于独立泛化或发布认证通过。
- **详情**：[工作区改版](../changes/evaldesk-workspaces.md)、[证据落库修复](../changes/screening-v2-evidence-grounding-fix.md)。

## 记录已有配件型号时，模型无依据撤销已有件

- **现象/触发**：`cv-owned-model-flow` 中，模型记录型号的同时发出无依据 `remove existing_parts`；修复首跑记录 2 次关键字段错写。
- **根因**：已有配件类别与准确型号被错误理解为互斥事实；撤销操作缺少本轮明确意图的证据约束。
- **正确处理**：提示词明确类别与型号独立并存，记录型号不代表撤销；守卫要求本轮撤销意图与已有件对象证据，缺证据时降级为观察，不擅自删除。
- **验证依据**：`TestPrepareRemoveExistingPartsRequiresRemovalEvidence` 位于 `internal/agents/pipeline/screening_requirement_state_guard_test.go`；历史两批冻结运行记录多轮 6/7 → 7/7、关键字段错写 2 → 0、最终否决项 0。
- **适用范围**：需求状态写入与已有配件授权。该结果是提示词加守卫的组合修改，开发/校准验证；未完成新独立保留集验证。
- **详情**：[证据落库修复](../changes/screening-v2-evidence-grounding-fix.md)。

## Windows Docker Desktop 损坏 socket 与快速启动

- **现象/触发**：历史本机记录中，Docker Desktop 启动崩溃，unix socket 报“cannot be accessed”，Windows 层无法删除相应损坏文件，关机开机后反复出现。
- **根因**：2026-07-26 / 27 的历史排障记录将该重复故障关联到 Windows 快速启动（`HiberbootEnabled=1`）保存的异常 socket 状态；这不是所有 Docker 启动故障的通用结论。
- **正确处理**：先确认日志、损坏 socket 的实际路径及 Docker Desktop WSL 发行版，再处理明确的故障文件；必要清理应在对应发行版中进行，不能用任意 Windows 路径批量删除。该历史场景还需处理快速启动造成的复发条件，而不只是删一次文件。
- **验证依据**：迁入此前保存的 2026-07-26 / 27 本机排障笔记，原文未附独立日志或回归测试；本轮未重现故障、未修改系统设置。
- **适用范围**：该 Windows / Docker Desktop 历史环境。新版环境须重新核实，不执行无关 WSL 操作或默认关闭系统功能。
- **详情**：[本地运行与部署](../ops/本地运行与部署.md)的排障表；普通命令执行与路径保护见根 `AGENTS.md`。

## 模型端点宣称兼容，但不支持项目所需 Responses API

- **现象/触发**：配置一个只提供 Chat Completions 的兼容端点后，ADK 模型调用与预期接口不匹配。
- **根因**：当前 `internal/modelprovider/factory.go` 使用 ADK `openaimodel`，Chat 装配依赖 Responses API；“OpenAI 兼容”不保证具备本项目所需接口与认证方式。
- **正确处理**：核对 provider 加载与实际请求合同，按供应商提供 Responses 路径和选项；不能仅修改 Base URL 就假定 Chat Completions 端点可用。是否进行真实可用性探测取决于任务授权。
- **验证依据**：`internal/modelprovider/config.go` 的兼容服务限制，以及 `internal/modelprovider/factory_test.go` 中 `TestNewChatResponsesRequestProviderOptions` 等请求合同测试；本轮仅核对代码，未执行新探测。
- **适用范围**：当前 Chat 模型装配，Embedding 单独遵守其接口合同。依赖升级或更换适配器后重新核对。
