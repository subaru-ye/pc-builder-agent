# 动态需求状态栏

当前需求面板展示本次装机会话中系统正在采用的信息，并直接驱动追问与配置生成。服务端 `RequirementState` 是唯一真值，前端只展示和提交编辑；生成仍复用既有 `RequirementSpec`、Screening 与 Builder。

2026-09-10 界面调整：当前需求摘要常驻聊天顶部，详细字段、来源和修改历史独立展开；桌面配置详情常驻右栏，包含配置、校验和版本，宽度控制在 360–480px。桌面会话列表在首页与会话页持续显示，个人设置统一放在列表底部；窄屏从顶栏打开会话列表，配置使用独立抽屉。新建对话显式创建服务端空会话，不调用模型。

## 使用与边界

- 随对话补充预算、预算口径、用途、分辨率、已有件、品牌、静音、外观、尺寸、装机对象和补充说明，面板持续显示当前值与本轮变化。
- 未说明字段显示未知；`RequirementSpec` 为兼容生成链填入的 any、预算弹性等默认值不会反向写成用户偏好。可选未知字段不会阻塞生成或触发重复追问。
- 可在面板纠正值、明确必须或尽量满足、撤销记录，并按需查看来源消息与修改历史。临时例外保留覆盖前值，恢复操作重新采用原要求。
- 讨论备选单独记录，不直接修改当前要求；含糊冲突只追问相关字段。撤销留下标记，下一轮不会因为旧消息还在历史中而恢复旧值。
- 需求不足时为收集中的草稿，充分时等待确认。确认后再次修改会形成待确认的新草稿；原配置与历史版本保持不变，确认才触发新配置生成。
- 仅保存本次会话记忆，刷新从 PostgreSQL 恢复。“帮朋友装机”、一次预算和临时例外不写入账号资料或跨会话画像。

## 状态与接口

`internal/schemas/requirement_state.go` 定义字段、操作和 reducer。每个字段保留 value、status（unknown/active/removed/conflict）、strength（must/prefer）、scope（session/temporary）与来源。kind 区分 fact（用途或已有事实）、context（补充说明）、constraint（配置条件）；evidence 区分明确表达与待确认信息。来源包含 chat/edit、用户消息 ID 和对应原话。临时覆盖保留 previous；备选、最新变化和历史分别存放。旧字段缺少 kind 时保持未分类，不从历史或关键词反推。

只有本轮原文可作为聊天操作的证据，消息 ID 由服务端绑定，模型不能伪造来源。Screening 适配器逐项校验模型操作，把无法可靠结构化的信息保留为 observations（原文、关联字段、原因、来源），可靠操作继续提交；不能因单个字段有疑问丢失整轮。reducer 对最终可应用操作集合保持原子校验，界面编辑也使用同一 reducer。没有出现的字段保持原值。`RequirementStateSpec` 只投影 active 字段；removed、unknown、conflict 和备选均不作为已生效条件进入 Builder。尚未解决的原文通过独立 requirement_observations 传递，明确不是用户确认的偏好或通过核验的硬条件。

`web_sessions.requirement_state` 保存草稿。confirm 原子冻结 `confirmed_requirement_state`、`confirmed_requirement` 和 `confirmed_at`。现有 requirements/builds 版本记录不被草稿编辑修改。迁移 `00013_requirement_state.sql` 为旧会话保留 NULL，避免从旧模型输出或程序默认值反推用户表达。

Session 同时返回当前状态、确认快照、`missing_fields` 和 `requirement_status`：

| 值 | 含义 |
|---|---|
| collecting | 必要信息仍待补充或存在冲突 |
| ready_to_confirm | 信息充足，等待首次确认 |
| confirmed | 当前有效需求与最近确认快照一致 |
| modified | 当前有效需求已不同于最近确认快照，原配置保持不变 |

`PATCH /api/v1/sessions/{session_id}/requirement-state` 提交 `expected_revision` 与 `operations`，要求 Idempotency-Key。聊天和界面编辑共用 reducer，界面编辑保存一条可读用户来源消息，返回完整 Session。版本冲突或正在运行的任务返回 409，客户端重新读取真值后再编辑。详细线格式以 [OpenAPI](../api/openapi.yaml) 为准。

编辑幂等性使用完整操作集合的 SHA-256 指纹；相同文字的“讨论备选”与“采用要求”不能混为同一个请求。确认先在数据库事务内处理已完成请求的重试，再核验当前草稿投影并冻结快照。旧会话没有可溯源状态时继续使用原表单和会话流程；增量编辑接口明确拒绝从空状态覆盖旧需求。

`requirement.updated` 在状态持久化后发送完整状态，必要信息充足时另发 `requirement.ready`；前端不从 SSE 文案推断业务状态。刷新、断线重连与编辑完成都重新读取 Session，沿用 [SSE 协议](../api/SSE事件协议.md)。

## 模型、候选与约束强度

新会话复用已有 Screening 模型与运行入口，输入当前服务端状态和本轮用户消息，输出增量操作。语义归类、表达强弱、否定、临时例外和备选理解由这次模型调用承担，不再用后端自然语言关键词白名单复判。无需每轮另调用总结模型，也不让模型从旧消息重算被撤销或修改的值。代码仍校验 JSON、字段、枚举、数值范围、本轮原文来源和合法状态操作，并负责合并、缺失追问、生成投影、revision 和界面编辑。

`RequirementSpec` 使用可选 `constraint_strengths`（字段路径到 must/prefer）、`requirement_semantics`（字段语义）、`requirement_details`（当前有效 appearance/recipient）和 `requirement_observations`（待确认原文）。外观直接通过 requirement_details 参与已有单次语义检索，不拼接进 notes，以免污染说明的分类和来源。Builder 收到用途事实、说明和待确认原文，用于选择配件及说明证据边界。预算弹性默认值只属于执行参数；Builder 输入标明是执行默认、明确要求还是旧数据来源未知，不把默认 0.1 说成用户同意超支。

默认 Harness v2 将明确的软品牌、板型偏好用于稳定排序，保留其他可行候选；必须品牌、板型继续走确定性过滤。锁定件和明确换件指令仍优先约束候选，软偏好不能取消兼容性或预算检查。评估 A5 同步区分明确的软品牌与必须品牌，历史缺少强度标记的记录不变。

用途事实和补充说明即使原强度为 must，也不自动成为需要商品证明的硬过滤。例如“剪4K视频”保留在生成输入中，不因目录没有“剪视频”的统一证明字段而停止。明确为 constraint 的自由文本硬条件，以及硬静音、硬外观，目前缺少统一目录证明契约时返回 `data_unavailable / requirement_evidence_missing`，指出具体待核验字段并保留要求。缺少分类的旧 must notes 若与当前用途 titles 完全相同，可按现有结构识别为用途；其他旧文本只确认是用途说明还是具体配置条件，不强迫用户降低要求强度。

型号、品牌、尺寸等已有结构化硬条件继续执行候选过滤、已有件锁定与规则校验，筛空返回明确业务原因。自由文本条件自动核验尚未实现，不能用兼容性 pass 或语义命中冒充满足；legacy 遇到带强度标记的新需求仍在交付前明确停止并提示使用默认 v2。

未保存配置时，Harness 的结构化业务原因跨 A2A 传递，由产品层按受控原因生成中文说明并持久化到聊天摘要。用户能看到哪项待核验、需求已保存、原配置仍保留，并继续在聊天或面板补充；模型原始错误和内部参数不直接进入摘要。

## 调用量

| 动作 | 模型与 Embedding 影响 |
|---|---|
| 聊天更新需求 | 复用本轮 Screening；不新增独立总结调用 |
| 需求归并、追问、刷新、来源与历史 | 0 次模型、0 次 Embedding |
| 面板编辑或撤销 | 0 次模型、0 次 Embedding |
| 软品牌/板型候选排序 | 0 次模型、0 次 Embedding |
| 必须静音/外观无证据而停止 | 0 次 Builder、0 次 Embedding |
| 确认生成 | 继续使用既有 Builder 上限与语义检索策略；不增加生成模型调用上限 |

真实模型冒烟必须显式固定当前项目模型并设置小规模上限。离线测试和保存运行重放不调用真实模型；旧运行的 tokens 属于历史测量，不能算成本次用量。

初版历史冒烟固定 `deepseek-v4-flash-0731`，累计 4 次 Screening、0 次 Builder、0 次 Embedding，6,135 tokens；随后视频表达局部修复的历史调用另见[验收记录](../eval/动态需求状态栏验收.md)。这些不是本次语义与约束调整的调用量。本次默认离线重放，0 次真实模型、0 次真实 Embedding，不改模型配置，也不反复运行全量真实评估。

## 验证与后续

启用本版需执行 `go run ./cmd/migrate up`，然后重启产品 API 与 Web。迁移只增加会话草稿/确认快照及编辑请求指纹列，不回填旧用户偏好，也不修改已有配置版本。

后续的需求语义与约束调整没有新增数据库迁移；上线时 API、buildsvc 和 Web 需使用相同版本，以获得结构化失败原因及新字段展示。本次只在独立测试服务完成验证，未切换用户主服务。结果见[需求语义与约束验收](../eval/需求语义与约束验收.md)。

离线回归覆盖预算修改保留其他字段、已知信息不重问、撤销不复活、must/prefer、备选隔离、临时例外恢复、帮别人装机的会话范围、界面/聊天同 reducer、刷新恢复、确认快照与配置版本保护。保存真实对话可复用 v1.5 L5 题目与 `artifacts/eval/20260909-134447-3770035618`，重放应复制到新目录，保留历史产物。具体本次执行结果进入评估记录，不能仅凭 fixture 或历史通过率宣称当前真实模型已通过。

长期记忆仍未实现：跨会话偏好提取与明确授权、个人/他人装机对象隔离、偏好失效和冲突处理、长期记忆查看/删除均留待后续产品设计。本版只保留会话 scope 与 recipient 扩展点，不建设跨会话画像或知识库。
