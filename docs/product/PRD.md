## 2. 产品概述

### 2.1 定位与价值主张

**一句话**:对话式装机助手——用户说清预算和用途,得到保证兼容、带日期化报价、可多轮修改的装机配置单。

三支柱用户价值:

1. **兼容保证**:每份配置单都经过规则引擎逐项硬校验(插槽/内存代数/限长限高/电源余量等),这是纯 LLM 配单工具(如 Newegg AI)翻车的反面。
2. **日期化诚实报价**:总价绑定报价快照日期,用户明确知道价格的新旧,而不是拿到一个来历不明的数字。
3. **可迭代改单**:"降 500 优先砍哪""换成 A 卡"直接改,未涉及的部件不动,每次修改留版本可回看。

### 2.2 问题与机会

现状分三类:手动攒机工具(PCPartPicker、中关村模拟攒机)有兼容检查但无对话能力,用户仍需自己懂硬件;纯 LLM 工具(Newegg AI、各类套壳站、直接问 ChatGPT)能对话但预算分配失衡、知识过时、幻觉搭配,不可直接照买;真实需求大量流向 B 站/贴吧的人肉配单。"对话理解意图 + 规则引擎硬校验 + 快照报价"三者兼备的产品在国内是空位。详细论证见[产品调研](../装机Agent产品调研.md) §一、§五。

### 2.3 学习项目立场声明

1. 项目目的 = 技术栈学习(ADK 多 Agent、A2A、PostgreSQL/pgvector/Redis 记忆基座)+ 可自证的产品质量,学习目标验收对照见设计方案 §九。
2. 本文**不包含**商业化、增长、运营、收入等内容;路线图只规划功能与技术演进。
3. 产品质量必须可以由开发者本人 + 小样本真人验证,不依赖流量型指标。

### 2.4 产品原则

后续一切功能取舍以下列原则为依据:

1. **LLM 不裸配单**:兼容性与核算的最终判定权属于规则引擎,LLM 只负责理解意图与解释结果,且解释不得与规则判定矛盾。
2. **诚实优于全能**:价格只承诺快照日期透明;不校验的项必须写进免责边界,与用户明说,而不是假装覆盖。
3. **修改优于重来**:用户迭代以增量改单为默认路径,未涉及部件保持锁定;每次修改产生新版本,历史可回放。
4. **每个选择可解释**:每个部件附选件理由;报告能说清"为什么过 / 为什么不过 / 为什么判不了(unknown)"。
5. **范围克制**:SKU 覆盖宁窄勿滥,收录的部件必须字段完整到可跑校验;新想法先进 backlog,不直接扩当前范围。

## 3. 目标用户与使用场景

### 3.1 用户画像

| 画像 | 装机小白 | 半懂哥 | 帮配者 |
|---|---|---|---|
| 动机 | 想要一台能打游戏/干活的主机,不想被坑 | 有自己想法,想验证 + 抠性价比 | 给亲友配单 / 社区答题,追求效率与说服力 |
| 知识水平 | 分不清芯片组与插槽,预算与期望常冲突 | 懂大件参数,对长尾兼容(限长/供电接口)没把握 | 熟练,但重复劳动多、懒得手打配置单 |
| 典型开场白 | "8000 块想玩黑神话,帮我配一台" | "7500F + 4070S 这套帮我看看,内存想上 6000" | "帮我表弟出个 5000 的单子,要白色机箱" |
| 核心痛点 | 不敢信 AI 也看不懂参数,怕买回来点不亮 | 手动查兼容表费时,价格信息零散 | 每次都从头写,方案没有版本、不好分享 |
| 信任来源 | 逐项校验报告 + 人话解释 | 校验细节、性价比数字、可指定偏好 | 报告可导出/分享,拿去能服人 |

帮配者是分享/公开链接功能(阶段 1)与社区反馈(阶段 3)的天然用户,MVP 阶段不为其单独开发功能。

### 3.2 核心场景

| 编号 | 场景 | 触发 | 期望结果 | 主要功能模块 |
|---|---|---|---|---|
| S1 | 预算游戏机首配 | "8000 元 2K 玩黑神话" | 一轮对话内得到全部通过校验的配置单与报告 | F1/F2/F3/F5 |
| S2 | 生产力/AI 推理主机 | "剪视频 + 跑本地模型" | 预算分配偏 CPU/内存/显存,理由说明与游戏机不同 | F1/F2/F3 |
| S3 | 预算调整 | "降 500 优先砍哪" | 增量改单,给出砍在哪、损失什么,新版本可与旧版对比 | F4/F3 |
| S4 | 旧件升级 | "SSD 和机箱还能用,其他换" | 登记已有配件,只配缺的,校验时纳入旧件参数 | F1/F2/F3 |
| S5 | 配置单分享求评 | 帮配者把单子发给别人 | 导出物含报价日期与免责,他人可读可信(阶段 1 起支持分享图/链接) | F6 |

### 3.3 非目标与边界

**永久非目标**(不做,写明理由):

- 下单/交易/比价跳转 —— 电商链路不是学习目标,且引入实时价格承诺,违背原则 2
- 水冷定制方案(分体水冷等)—— 兼容性长尾极深,不可规则化
- 笔记本 / 品牌整机推荐 —— 与 DIY 装机是不同的数据与决策模型
- BIOS 版本支持、内存 QVL 级校验 —— 明确进入免责边界,与用户明说
- 实时价格承诺 —— 永远采用快照模式,阶段 2 只提升快照新鲜度,不改承诺口径

**暂缓项**(进 backlog,未排期):

- 外设(显示器/键鼠/耳机)推荐
- 多用途混合的加权优化(MVP 只处理单一主用途)
- 峰值功耗 / 瞬时负载建模(现有功耗校验为估算 + 余量系数)

## 4. 用户旅程与用户故事

### 4.1 端到端旅程(七步)

| # | 步骤 | 用户目标 | 系统行为 | 信任关键点 |

## 5. 功能需求

### 5.1 功能全景

按用户旅程排序的七个功能域 + 远期 Epic:

- **F1 对话式需求收集** → **F2 配置单生成** → **F3 校验与核算报告** → **F4 增量修改与版本管理** → **F5 报价快照** → **F6 导出与分享** → **F7 偏好记忆(远期)**
- Epic:E1 独立 Web 客户端、E2 价格半自动化、E3 多平台 SKU 扩展、E4 社区反馈闭环

全部功能条目(FR)的优先级与阶段映射见 §5.9 总表。优先级定义:**P0** = 缺了产品承诺不成立;**P1** = 核心体验;**P2** = 增强。

### 5.2 F1 对话式需求收集

多轮对话收集预算、用途(游戏@分辨率帧率 / 生产力 / AI 推理)、尺寸/静音/品牌偏好、已有配件,产出结构化需求单供用户确认(结构见设计方案 §四 RequirementSpec)。关键行为:只追问缺失的关键字段,不机械过问卷;发现预算与期望冲突时主动消解(给"降预期或加预算"选项);已有配件登记后进入后续校验。涉及条目:FR-101~104。

### 5.3 F2 配置单生成

按用途模板分配预算(游戏机显卡优先、生产力 CPU 优先),从零件库检索候选并组合成完整草案,每件附一句理由。用户的明示偏好(品牌/尺寸/静音)是硬过滤条件;"安静的""白色海景房"等模糊表达通过语义检索映射到参数过滤(机制见设计方案 §三、§六 pgvector 用途)。涉及条目:FR-201~204。

### 5.4 F3 校验与核算报告

配置草案必须通过规则引擎校验才能呈现为正式方案;校验不通过时系统自动换件重试(有最大轮数),而非把错误方案丢给用户。报告的信息结构:兼容性逐项结果 + 功耗余量 + 总价 vs 预算 + 性价比。三种判定的产品含义:**错误** = 方案不成立,必须解决;**警告** = 可接受但需知情(如电源余量偏低);**unknown** = 数据不足以判定,诚实展示而非冒充通过。校验覆盖的类别:插槽/芯片组匹配、内存代数与频率、显卡限长、散热限高、电源功率与供电接口、板型、存储槽位、亮机条件、散热能力(具体规则条目与阈值见设计方案 §五,本文不复制)。免责边界(BIOS 版本、内存 QVL 等)必须随报告同屏展示。涉及条目:FR-301~305。

### 5.5 F4 增量修改与版本管理

自然语言改单("换 A 卡""降 500""要更安静"),解析为换件/调预算/改约束三类意图;未涉及部件保持锁定;每次修改产生新版本,形成版本树,任意两版可看 diff。超出三类意图的复杂请求降级为整单重生成并向用户说明。涉及条目:FR-401~403。

### 5.6 F5 报价快照

所有价格来自带日期的快照;配置单与导出物强制展示快照日期;总价与预算的差额是报告的固定字段。阶段 2 起提供价格过期提示(快照年龄超阈值时标注)。涉及条目:FR-501~503。

### 5.7 F6 导出与分享

MVP 提供 Markdown 导出(含全部大件、报价与快照日期、免责边界);阶段 1 提供分享图与公开链接,面向帮配者的传播场景。涉及条目:FR-601~603。

### 5.8 F7 偏好记忆(远期)

跨会话沉淀用户长期偏好(品牌倾向、静音、颜值),下次会话自动带入并可查看/清除。属阶段 3,当前仅占位。涉及条目:FR-701。

## 6. 信息架构与交互框架

### 6.1 核心对象模型(产品视角)

```
用户画像(阶段 3)
   └─ 会话 ── 需求单(确认后定稿,可被后续修改请求更新)
                 └─ 配置单版本 v1 ─ v2 ─ v3 …(树形,记录父子关系)
                       ├─ 校验报告(与版本一一对应)
                       └─ 报价(绑定某一日期的报价快照)
```

要点:配置单版本是不可变的——修改产生新版本而非覆盖;报告与报价从属于版本;报价引用快照而非孤立数字。对应的技术实现(表结构)见设计方案 §六,本文不复制。

### 6.2 界面信息架构(目标形态,阶段 1 落地;MVP 用 ADK dev UI 承载)

- **对话区**(主):追问、确认、改单请求的输入与回复
- **配置单卡片区**:当前版本的大件卡片(件名/价格/理由),修改后高亮变化项
- **校验报告区**:逐项结果 + 功耗/总价/性价比摘要 + 免责边界(固定可见,不可折叠隐藏)
- **版本时间线**:v1→vN 可点选回看,任意两版可 diff
- **导出入口**:Markdown / 分享图 / 公开链接(按阶段解锁)

### 6.3 关键交互

- **改单入口**:MVP 仅自然语言;卡片上的直接操作(如点击某件"换这个")是否提供,列为开放问题 OQ-3
- **版本回看**:只读,回看旧版本时明确标注"非当前版本"
- **免责呈现**:报告区固定展示 + 导出物必含;措辞见 OQ-4

## 8. 技术方案概述

三 Agent 流水线:初筛 Agent(LLM,收集需求)→ 生成 Agent(LLM + 检索,出草案)→ 校验核算 Agent(纯规则引擎,零 LLM,最终判定);Agent 间以 A2A 协议传结构化消息;记忆基座为 PostgreSQL(零件库/版本树)+ pgvector(语义选件)+ Redis(会话热上下文)。完整架构、schema、规则表、表结构见设计方案 §三–§六;实现栈(Go + ADK-Go + a2a-go + 百炼 Qwen)见[技术选型](../tech/技术选型.md)。

产品需求 → 技术能力映射(防两文档脱节的锚点):

| 产品需求 | 技术承载 |
|---|---|
| 兼容保证(FR-301~305) | 规则引擎(设计方案 §五),LLM 无判定权 |
| 增量改单与版本(FR-401~403) | ChangeRequest 消息 + builds 版本树(设计方案 §三.4、§六) |
| 模糊语义选件(FR-203) | pgvector 语义检索(设计方案 §六) |
| 报价诚实(FR-501~503) | prices 只增快照表 + 版本绑定 snapshot_date(设计方案 §六) |
| 需求结构化(FR-101~104) | RequirementSpec schema(设计方案 §四) |
| 会话连续与成本(NFR-07) | Redis 热上下文与结果缓存(设计方案 §六) |

反向约束:国内电商无公开价格 API → 快照报价是产品决策而非技术妥协;开源数据集字段缺失客观存在 → 报告三态中的 unknown 是产品级承诺而非实现缺陷。
