# ADR-007 模型供应商适配与成本控制

> 状态:已接受并实现（2026-08-12）。本 ADR 不改变核心 schema、A2A、产品 API、数据库或 Web 功能。

## 背景

原工程在 host、buildsvc 和 embedparts 三处分别装配百炼客户端，默认模型、Key 与 Base URL 易漂移；产品初筛还可能回灌完整 ADK 历史，生成 Agent 又主动调用一次与 Loop 相同的校验工具。这些做法增加了供应商切换成本、输入 Token、模型往返和重复计费风险。

## 决策

统一使用 `internal/modelprovider` 装配三个独立角色：

| 角色 | 默认供应商 / 模型 | 默认思考 | 说明 |
|---|---|---|---|
| screening | bailian / `qwen3.7-plus` | none | 产品 API 使用无 ADK 历史回灌 Agent |
| builder | bailian / `qwen3.7-plus-2026-05-26` | none | 该固定版本 Responses 实测 low 返回 400；none 的工具调用正常 |
| embedding | bailian / `qwen3.7-text-embedding` | 不适用 | 当前固定 1024 维 |

支持 `bailian`、`mimo` 和 `openai_compatible`。通用兼容端点必须实现 OpenAI Responses `/responses`，不兼容只有 Chat Completions 的服务。MiMo 暂不支持 embedding；MiMo builder 暂只允许 `reasoning.effort=none`，因为思考模式的多轮工具调用建议完整回传 reasoning history，而当前 ADK 适配无法保证无损保留该结构。

配置优先级为角色专用配置、供应商配置、百炼旧变量。服务启动只做静态校验，不探测或消费模型额度；联网验证必须显式执行 `cmd/modelcheck`。任何额度、鉴权、限流或协议错误都明确失败，不自动切换供应商或模型。SDK 自动重试默认 0，防止响应丢失后重复计费。

百炼 Responses 请求默认发送 `x-dashscope-session-cache: enable`；该私有头不会发送给 MiMo 或通用端点。两项能力与当前官方契约一致：[百炼 Responses API](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)支持 Session cache 和 `reasoning.effort`；[MiMo Responses API](https://mimo.mi.com/docs/en-US/api/chat/responses)支持 function calling，并可用 `reasoning.effort=none` 关闭思考。

## 成本与延迟约束

- 产品初筛只读取数据库中同类 screening/change run 的最近 6 条稳定消息，总长度最多 4000 Unicode 字符；build 交付、工具事件和 A2A 内部事件不得进入。
- “换成 A 卡/AMD 显卡”与“换成 N 卡/NVIDIA 显卡”等无歧义表达走纯规则 ChangeRequest，并锁定其余七类；否定、含糊或具体型号继续交给模型。
- builder 不再持有 `validate_build` 自检工具。Loop 中的确定性 validator 是唯一最终判定，仍最多驱动三轮修复。
- 两类检索工具常规使用 `top_n=5`，允许范围 1..8；越界显式报错。
- 无依赖的八品类检索提示模型在同一响应中并行发出多个 function call，并禁止已有足够候选后重复同条件检索；实际并行程度仍取决于供应商模型。
- embedding Redis key 同时包含 provider、端点 host、model 和 dimension 的摘要，避免跨供应商误命中。
- 只有设置 `P10_METRICS_DIR` 时才写脱敏指标；记录 provider、role、model、Token 分类、耗时、cache 状态与安全错误类别，不记录正文、Cookie、token 或 Key。

## 配置示例

```dotenv
SCREENING_PROVIDER=bailian
SCREENING_MODEL=qwen3.7-plus
SCREENING_REASONING_EFFORT=none

BUILDER_PROVIDER=bailian
BUILDER_MODEL=qwen3.7-plus-2026-05-26
BUILDER_REASONING_EFFORT=none

EMBEDDING_PROVIDER=bailian
EMBEDDING_MODEL=qwen3.7-text-embedding

MIMO_API_KEY=
MIMO_BASE_URL=https://api.xiaomimimo.com/v1
BAILIAN_SESSION_CACHE=true
MODEL_MAX_RETRIES=0
```

角色可用 `SCREENING_API_KEY/BASE_URL`、`BUILDER_API_KEY/BASE_URL`、`EMBEDDING_API_KEY/BASE_URL` 覆盖供应商配置。MiMo 与通用端点没有隐式模型默认值，必须填写精确 Model Code。

## 验证与回滚

显式能力检查：

```powershell
go run ./cmd/modelcheck -role screening
go run ./cmd/modelcheck -role builder
go run ./cmd/modelcheck -role embedding
```

builder 检查会强制模型调用最小 `health_check` function；命令只输出 provider、role、model、耗时和安全错误，不输出请求或响应正文。若移除 builder 自检后真实 L1/L2 烟测不能稳定保存并通过确定性校验，只恢复该工具；供应商层、有界上下文和缓存隔离保留。

`qwen3.7-plus-2026-05-26` 的真实检查发现 `reasoning.effort=low` 返回 400 `InvalidParameter`，改为 `none` 后 function calling 通过。因此该精确 Model Code 在配置层有静态例外；不会先请求失败再运行时降级。其他百炼 builder 未显式配置时仍默认 low。

## 后果

收益是供应商切换集中、成本指标可解释、无自动付费回落、初筛上下文可控。代价是 Responses-only 端点约束，以及 MiMo 思考型工具调用和 embedding 暂不可用。账户余额与免费额度仍由供应商控制台人工确认，本项目不查询计费账户。
