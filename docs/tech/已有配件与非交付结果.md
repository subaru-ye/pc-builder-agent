# 已有配件与非交付结果

本契约适用于默认 Harness v2、初筛和评估；历史需求 JSON 仍可读取。新逻辑不改写旧题或历史成绩。

## 已有配件

`existing_parts` 保留品类列表；新增 `owned_parts` 数组，每项包含 `category`、`model`、`quantity`。型号必须来自用户提供的信息，程序按当前目录的完整型号或品牌加完整型号精确匹配，不模糊推断，不让模型编内部 SKU。数量默认 1，只有 SSD 支持多件；一批同品类只允许一个准确型号，复杂混用先追问。

新增 `budget_basis`：`new_purchase` 表示新增购买费用，`full_build` 表示整机参考总价。无已有件时省略沿用原整机口径；有已有件而未明确预算口径时先追问。有品类但无完整型号时先追问型号。已有件型号不在当前目录时说明资料不足，不替换成相似产品。

已匹配的已有件参与全部兼容性校验，并与用户锁定项一样不可擅改。冲突或不兼容时说明限制，不另购一个同品类配件冒充已有件。用户改变已有件需显式修改需求。

### 初筛输出核验

`screening_guard.go` 在 ADK 写入可见事件和 `requirement_spec` 前读取模型声明的已有品类、型号和预算口径，生成结构化缺失字段列表。已有品类缺型号、型号在用户原话中无对应文本，或者预算口径无明确表述支持时，输出只针对相关字段的程序追问。模型返回的半成品 JSON 也经过此检查；不因模型自行填上 `new_purchase` 就视为用户确认。

所有新装机需求采用内部草稿协议：模型只提取已知字段，未知型号、金额、用途、游戏分辨率或费用口径省略；程序检查必填项并生成直接问题。无已有件时不追问是否全新购买，游戏名称等可选字段缺失不阻止需求单输出。草稿在核验前不写入需求卡，也不发送给 Builder；字段齐全时继续走现有严格 schema。ChangeRequest 保留原协议；公共 RequirementSpec schema 和评估期望不变。

产品 API 单独传递与有界上下文同范围的用户消息，排除助手示例；多轮评估共用产品上下文构建和用户来源，单轮评估及 dev UI 未显式提供来源时从 ADK 请求的 user 内容取证。初筛调用以非流式结果核验，不提前转发未经检查的 JSON。程序确认尚无配置版本时使用独立草稿指令，需求确认提示不代表配置已保存；已有版本仍保留改单协议。

新需求中仅对非法 JSON 协议最多重试一次，缺失字段已形成安全追问时不重试；最后一次仍不合法则留给产品及评估原错误路径处理。协议缺失版本、字符串 `"1"` 和空 notes 数组可作有限规范化，不覆盖业务值。评估保存全部格式尝试原文并计入调用/token。模型直接输出自然语言时仍走原路径，不能声称原生结构化输出已被强制保证。

新需求草稿的第一个外层 JSON 必须完整闭合；外层截断时不能从内部 use_case 等对象捞出“需求”并产生无关追问。首次截断进入同一次格式重试，第二次仍截断则明确报协议错误，保留两次原文。通用历史 payload 提取逻辑不变，旧运行按原证据重放。

Builder 前置的已有件澄清也只询问 `MissingOwnedFields` 返回的缺口：已确认采购口径就不再问口径，已知型号就不再问型号，不要求未列为缺失的数量。新版澄清说明带 `explanation_version=1`；旧版 0 的精确文案仍可复验，不能靠任意改写说明混过非交付断言。

该核验是保守的文本约束：型号按字母数字规范化后核对原话，预算口径使用明确中文表达白名单；预算金额核对用户消息中的预算或金额表达，支持数字、千分位、千/万/k 和常见中文整数，缺少匹配则询问金额，不接受模型默认填值。显式撤回预算会使此前金额来源失效，后来的明确采购口径覆盖旧说明，同一消息内冲突仍追问；分辨率须有用户来源，不能照抄助手提供的选项。它不具备通用语义证明能力，不能完全区分历史金额、单件价格和当前预算。别名、生僻表达、同句撤回又给新值、模型漏提已有品类和复杂多轮更正仍需覆盖。准确 SKU 身份和兼容性继续由下游目录绑定核验。

报价保留 `total_cny`（整机已知参考价），增加 `purchase_total_cny`（需购买部分已知价）、`purchase_missing_count` 和每行 `owned` 标记。预算依据显式口径选择对应合计。已有件参考价未知不阻断新增采购预算，但须继续显示整机参考价缺失；需购买件缺价不能冒充完整报价交付。

## 非交付结果

结构化结果通过 `Decision` 区分 `clarify`、`catalog_infeasible`、`data_unavailable`、`search_exhausted`、`invalid_output`，同时记录原因码、缺失字段、适用范围及证据；成功仍使用 `Succeeded=true`，评估期望为 `pass`。底层接口错误仍返回 error，不能转成正确拒绝。

- `clarify`：指出缺少的已有件型号或预算口径，并实际提问。
- `catalog_infeasible`：仅在程序取得当前完整目录的确定性证据时使用。首版证明为各必需品类独立最低价之和仍超过预算上限；未知价格不当作正数参与无解证明。这个乐观下界不考虑更多兼容约束，因此只能证明当前目录及价格口径不可达，不能声称整个市场不存在。
- `data_unavailable`：当前目录缺少必要候选，或所需信息/价格无法核验。
- `search_exhausted`：有限次数/候选搜索未找到可交付方案，不是无解证明。
- `invalid_output`：模型输出或约束执行失败，不作为正确拒绝的替代品。

平台预算证明已接入默认 Harness 的候选准备阶段：对无已有件、无基版本、非改单的 general 整机，在完整目录上组合 CPU/主板/内存，仅排除已知的插槽、芯片组、内存代际冲突，并为无核显 CPU 计最低独显成本。其他必需品类取独立最低价；只有这一乐观下限仍高于预算上限，才返回 `catalog_infeasible/platform_budget_lower_bound`，无需模型选配。未知价格或无法解析规格时放弃证明，未知规格按可能兼容处理；最多枚举 50 万组，超限继续正常选配。该机制不解决已有件与改单的完整可达性证明。

用户说明明确该下限不是可交付报价、增加到下限也不保证配成，提供调整预算后重验、补充已有件完整型号及预算口径、补充可核验商品资料三种下一步。程序不自动改预算，不声称整个市场无解。评估 v1.4 的 `budget_adaptive` 单独接受这一有证据的非交付；搜索耗尽和普通错误仍失败，成功交付的硬断言不放宽。完整契约见[v1.4](../eval/versions/v1.4.md)。

非交付结果不保存配置版本。评估必须检查期望类型、原因、证据及未交付状态；不得仅以 `Succeeded=false` 判定通过。v1.1 原有 pass 题仍按原期望计分，新边界题另行冻结版本。

## 接口与展示

RequirementSpec schema_version 保持 1，以可选字段扩展；OpenAPI 和前端生成类型同步。需求表单可填写已有件准确型号和 SSD 数量，并选择预算口径。已有件勾选但信息未补齐时不能生成；后端仍独立检查，不能依赖前端校验。

报价落版本时保留完整参考合计、采购合计及 owned 行标记。工作台同时显示两种金额，预算差按选定口径计算；已有件不显示普通换件按钮。导出标注已有件和新增购买合计，现有版本列表中的 total_cny 继续表示整机参考价。

legacy 仅作显式诊断；对已有件请求在校验交付门禁处停止，不沿用旧的“任选同品类后标注已有”做法。非交付结果经现有消息链返回用户；没有新增专用 HTTP 结果类型或自动修改需求。
