# 评估集建立记录

> 更新:2026-09-08。本文记录评估集的建立方式与演进;设计依据见 [Runner 设计](../tech/评估Runner设计.md),方法论见 [Agent 的评估精读](methodology/01-Agent的评估方法论精读.md)。当前题库在 `internal/evalsuite/testdata/cases/`；正式版本由 `testdata/suites/` 清单固定题目及哈希。每次运行保存 `cases.json` 完整副本，当前版本见[评估集 v1.3](versions/v1.3.md)。本文只做人读摘要。

## 1. 评估集怎么建

### 用例契约

每条用例一个 JSON,按阶段分两类:

**build 阶段**(跑 `buildharness`,断言交付物):

```jsonc
{
  "id": "L1-001",
  "title": "8K 预算 2K 玩黑神话(基线)",
  "stage": "build",                        // 可省略,默认 build
  "requirement": { /* RequirementSpec,经 DecodeRequirementSpec 严格解码 */ },
  "change":      { /* 可选:ChangeRequest(DecodeChangeRequest) */ },
  "base_selection": { /* 可选:改单基线配置(DecodeBuildSelection) */ },
  "locked": ["gpu"],                       // 可选:锁定品类(A8 断言输入)
  "expect": { "outcome": "pass" }
}
```

**screening 阶段**(跑初筛 Agent,断言行为):

```jsonc
{
  "id": "L3-101",
  "title": "噪音偏好不得推断品牌",
  "stage": "screening",
  "input": "我想要一台安静的电脑打游戏,预算 8000,使用 2K 显示器",
  "expect": { "kind": "spec", "budget_cny": 8000, "cpu_brand": "any", "gpu_brand": "any" }
}
```

设计原则(Agent 的评估"任务定义层"):只锁**可独立复核的约束**,不写死期望配置单;参数即实例化,天然防"背答案"。

### 维度矩阵与分层

| 层 | 阶段 | 数量 | 覆盖维度 |
|---|---|---|---|
| L1 单轮整机 | build | 15 | 预算档(3k/8k/15k/25k)× 用途/分辨率 × brand_pref × noise_pref × existing_parts × ITX;含 2–3 条语义软偏好 |
| L2 改单/前缀 | build | 10 | 基线取自 L1 真实产物(生产轨迹回流的微缩版);换件 hint / 调预算 / 改约束 × 锁定品类组合 |
| L3 陷阱边界 | screening | 5 | 品牌推断陷阱 / 预算缺失追问 / 缺分辨率追问 / 显式品牌照抄 / 正常需求对照 |

L2 基线来自 2026-09-06 首跑(L1-001/005/006 的交付 selection),已通过全部规则与预算校验;锁定品类断言(A8)要求交付与基线逐字节一致。

## 2. 断言矩阵

### build 阶段（Runner 断言）

| # | 断言 | veto | 判定 |
|---|---|---|---|
| A1 | draft 结构完整 | 否 | 必填品类 SKU 非空、SSD 数量为正、GPU nil 或非空 |
| A2 | 交付结果符合期望 | 否 | `Succeeded` == expect.outcome |
| A3 | 快照口径一致 | 否 | quote 快照日期 == 钉死日期 |
| A4 | 预算窗口 | **是** | 合计落 `budget_cny × (1 ± budget_flex)` 闭区间;缺价记 data-error |
| A5 | brand_pref 满足 | 否 | 推断厂商/家族(CPUVendor/GPUFamily,与 planner 同口径)== spec.BrandPref |
| A6 | SKU 成员复验 | **是** | selection ⊆ 钉死快照候选 |
| A7 | 报价块完整 | 否 | 分项小计之和 == 合计 |
| A8 | 锁定品类复验 | **是** | locked 品类交付 SKU 与 base_selection 逐字节一致 |

### screening 阶段

| # | 断言 | 判定 |
|---|---|---|
| S1 | 输出形态符合期望 | spec 必须提取到合法需求单；clarify 必须是非空文本且不含 JSON/代码块 |
| S2 | 字段口径符合期望 | budget_cny / resolution / cpu_brand / gpu_brand 与 expect 一致(any = 不得填) |
| S3 | 追问缺失信息 | `expect.clarify_fields` 中的每个字段必须在回复中被询问；当前预算与分辨率用例已指定字段 |
| S4 | 不重复追问已知信息 | 仅对声明 `expect.forbidden_clarify_fields` 的新题生效；复述已知信息允许，要求用户重新确认则失败 |

例如缺预算用例使用 `"expect": {"kind":"clarify","clarify_fields":["budget_cny"]}`。S3 使用中文确定性近似规则，不调用 Judge；仅出现“预算”二字的陈述或询问无关内容不能通过。表达覆盖的限制与人工复核方式见 Runner 设计。

### 失败归因(规则级,记录在 results.jsonl 的 attribution 字段)

方法论建议通过相邻输出差异定位首错；当前实现只做断言到领域码的映射，首个映射项标为主因，不等于完成根因分析:

| 失败断言/信号 | 归因码 | 含义 |
|---|---|---|
| A4 | B2 | 预算违约 |
| A6 | B1 | SKU 溯源违规 |
| A8 | B4 | 锁定品类违规 |
| A5 | B8 | 交付违反 brand_pref |
| A7 | C1 | 报价块与告知不一致 |
| A2 + message 含 schema | B7 | 输出契约违约(多轮 schema 反馈未修) |
| A2 + 规则 fail | B6 | 校验反馈未定向修复 |
| RUN 错误(数据前提) | C2 | 数据前提不满足(data-error) |
| RUN 错误(其他) | C2 | 执行异常 |

归因码体系与 [落地建议 §四](methodology/03-评估体系落地建议.md) 的领域分类表一致,随归因案例迭代。

## 3. runner 机制与基线纪律

- **固定快照**:`-snapshot-date` 必填;候选(CatalogSource)、校验与报价(validate.Resolver)三个适配全部钉死同一批次,消除库存/价格漂移伪装的退化。
- **模型配置**:builder/screening 使用 `modelprovider` 独立配置；当前固定回归清空 `*_MODEL_CHAIN`。历史额度链结果单独标注，不能归属于新固定模型。
- **Pass@k / Pass^k**:`-seeds N` 每条用例重复跑 N 次（编号不传入模型采样参数）;Pass^k = 全部 seed pass 且零 veto;release 门禁用 `-seeds 3`。
- **replay**:`-mode replay -dir <产物目录>` 零模型调用；新产物从完整题目副本恢复锁定输入，可重判 A8 并检查重复记录完整性；screening 从保存的最终回复重新判 S1/S2/S3/S4，比较完整断言与归因。旧产物缺少原文时明确标注未复验，不能补出历史证据。详见[Runner 边界](../tech/评估Runner设计.md)。
- **评估不落库**:评估运行不经过 pipeline 交付层,不写 builds/versions 表。
