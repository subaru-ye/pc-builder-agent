## 3. S1-B01:优化后完整 Live Pass³

执行前置:

- 人工确认百炼防扣费开关、三个精确 Model Code 与剩余额度。
- PostgreSQL、Redis 为 healthy，迁移已完成。
- 不设置 `P10_SMOKE`；烟测模式不能作为封板矩阵。
- 单 worker、串行、Playwright retries=0。
- 任一额度、鉴权、限流或账单异常立即停止，不自动更换模型或供应商。

必须覆盖:

- L1:8000 元、2K 黑神话，确认后生成 pass v1。
- L2:安静显卡和白色海景房，语义理由正确且不推断显卡品牌。
- L3:在 L1 上降 500，预算、parent 和最少改动正确。
- L4:换成 A 卡，GPU 为 AMD，其余七类锁定不变。
- L5:信息不足时只追问，不生成 build，不调用远程 builder。
- L6:编辑需求卡后确认，最终配置采用编辑后的值。
- 刷新恢复、API 重启、diff、Markdown、分享、越权与撤销生命周期。

失败处理:

- 失败场景先定位根因并做最小修复。
- 修复后完整重跑该场景的三次连续样本，不能只补一个成功样本。
- 若修改影响公共主路径或其他场景，重跑完整 L1–L6 矩阵。

## 4. S1-B02:成本与延迟目标

2026-08-12 的优化后最小烟测仅包含 L1/L2 各一次:

| 指标 | 结果 |
|---|---:|
| 场景结果 | L1、L2 均 pass 并保存 v1 |
| 首个进度 | 6 ms / 9 ms |
| 总耗时 | 136639 ms / 116778 ms |
| screening 调用 | 2 |
| builder Responses 调用 | 23 |
| 输入 / 输出 Token | 165419 / 12857 |
| reasoning Token | 0 |
| cache 命中 Token | 132810 |

这组数据证明缓存和关闭 reasoning 已生效，但样本不足，而且耗时中位数约 126.7 秒、builder 工具轮次仍偏高。烟测之后已增加“无依赖品类并行 function call、禁止重复同条件检索”的提示，尚未用真实完整矩阵验证。

完整矩阵不达标时按以下顺序定位:

1. 检查每场景 prompt、output、cached、tool-use Token 和调用耗时。
2. 检查模型是否逐品类串行调用工具或重复相同查询。
3. 优先优化工具批次和确定性数据准备，不通过自动换模型掩盖问题。
4. 不设置可能截断 BuildDraft JSON 的激进 `max_output_tokens`。
5. 任何优化不得降低 12 条规则、预算、锁定品类和数据来源约束。

若目标在不牺牲正确性的前提下确实无法达到，必须单独记录实际分布、原因和新的可验证门槛，再由项目所有者明确裁定；不能在验收文档中静默改数值。

## 5. S1-B03:真人盲评

最低样本为 3 人，角色分别是:

- 装机新手。
- 了解硬件但不了解本项目者。
- 有实际配单经验者。

每人使用全新匿名浏览器上下文，独立完成需求输入、确认、生成、改单、diff、价格与免责查找、分享。主持人不解释界面，只有受试者明确卡死时才协助并记录位置。

六个维度继续按 0/1/2 评分:

1. 需求一致。
2. 配置完整。
3. 可信度。
4. 改单可控。
5. 可直接照买。
6. 分享可理解。

只保存 R1/R2/R3、角色类别、评分、匿名卡点和转述摘要，不保存姓名或联系方式。不得编造参与者、用开发者自测填补缺失样本，或把同一人重复测试算作多人。

目前缺少另外两位参与者属于外部协调问题，不是代码缺陷。可以继续开发阶段 2，但最终真人评分必须基于届时准备封板的产品版本；评分后若再修改主路径，原评分不再作为最终盲评证据。

## 7. S1-B06:race 验收结果

Windows 已安装 MSYS2 UCRT64 GCC 16.1.0，CGO 编译链可用。Windows 11 build 26200 下，Go 1.26.5 ThreadSanitizer 在测试进程启动时仍会因高地址虚拟内存保留失败而退出；该错误发生在测试代码运行前，不是项目报告的数据竞争。

2026-08-25 已使用官方 `golang:1.26.5` Linux 容器强制执行 `go test -race -count=1 ./...`，全部通过且未使用测试缓存。后续 CI race 仍作为持续门禁；若失败，按 P1 处理。
