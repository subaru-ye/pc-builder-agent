# 装机 Agent 自主规划

2026-09-10 起，产品默认使用 `BUILD_HARNESS_MODE=planning`。`v2` 和 `legacy` 仅用于显式历史诊断，不自动回退。原 Harness 2.0 的预算下界、候选硬筛选和固定修复轨迹不再是产品准入条件。

## 1. 会话与执行

用户消息 → Screening 一次调用返回 operations、reply、next_action → 服务端合并需求草稿 → 首次需求确认 → Builder 工具循环 → 保存方案或正式配置。

需求确认过后，明确的升级/重新选配指令由 Screening 返回 `next_action=plan`，在同一运行内直接继续 Builder。`collect` 用于讨论或必要追问，`confirm` 用于首次核对或仅记录的新草稿；面板编辑仍只更新草稿。服务端仅允许已确认过需求的会话进入这条聊天续跑路径。

未解决决策结束前的复核：模型返回带问题列表的 proposal，或已调用工具且本轮已有实际候选校验结果后返回 clarify 时，服务端把实际核验反馈给模型一次。提醒模型区分用户必须条件、软偏好和自己的执行假设，不指定替换型号或自动批准偏离必须条件。同一运行两类决策共用一次复核；该复核使用原有最多 8 次模型往返与 24 次工具执行额度，不增加独立总结模型。

`ContinueScreeningRun` 锁定会话和当前 running run，校验修订号后原子保存新需求及本次执行确认，转为 build/change 并交给 Builder；保留同一 run_id 和请求幂等键。只在最终交付成功时追加正式版本。运行观测记录实际送入 Screening 的状态及执行上下文。

Screening 输入包含全部常用字段、自由字段及撤销墓碑，以及服务端读取的当前正式配置、报价、配件名称、上一方案摘要和最近一条助手回复。配置不是用户已购件，助手回复仅帮助理解指代，不是新需求证据。旧用户消息不重新用于提取。

`kind=context` 的新值只能进入 notes、recipient 或 free.*，不能写入预算等固定执行字段；装机对象不参与硬件约束。Screening 遇到执行字段/分类不一致的操作时，保留原用户引用为 notes 观察，其他可靠操作仍应用；面板/API 对非法分类原子拒绝，不部分应用。旧误绑定记录不批量更改；用户明确编辑保存时可纠正分类。

Screening 对缺值输出作读取适配：当前字段没有有效值或冲突时，`set null`、未给 value 及全部型号为空的 owned_parts 只保留带来源的观察，不制造“必须条件冲突”，也不恢复已撤销值。空数组是明确清空，不能当作未知；显式 conflict、非空非法型号等仍接受原来源与冲突检查。

执行输入 `PlanningInput.schema_version=2` 携带完整当前需求状态、原配置和上一方案；聊天续跑另附带 `request`（来源消息编号、类型、本轮原话）。HTTP 与 A2A 使用同一输入，不再转换为固定必填 RequirementSpec。旧记录按读取适配，不批量改写。

## 2. 需求状态(动态需求面板)

当前需求面板展示本次会话系统正在采用的信息，并直接驱动追问与配置生成。服务端 `RequirementState` 是唯一真值，前端只展示和提交编辑。

- `internal/schemas/requirement_state.go` 定义字段、操作和 reducer。每个字段保留 value、status(unknown/active/removed/conflict)、strength(must/prefer)、scope(session/temporary)与来源；kind 区分 fact(用途或已有事实)、context(补充说明)、constraint(配置条件)。来源包含 chat/edit、用户消息 ID 和对应原话；临时覆盖保留 previous;备选、最新变化和历史分别存放。
- 只有本轮原文可作为聊天操作的证据，消息 ID 由服务端绑定，模型不能伪造来源。Screening 适配器逐项校验模型操作，无法可靠结构化的信息保留为 observations，可靠操作继续提交；reducer 对最终可应用操作集合保持原子校验，界面编辑也使用同一 reducer。
- `web_sessions.requirement_state` 保存草稿；confirm 原子冻结 `confirmed_requirement_state`、`confirmed_requirement` 和 `confirmed_at`(迁移 00013,旧会话保留 NULL,不从旧模型输出反推)。`RequirementStateSpec` 只投影 active 字段；removed、unknown、conflict 和备选均不作为已生效条件进入 Builder。
- Session 返回 `missing_fields` 与 `requirement_status`:collecting / ready_to_confirm / confirmed / modified(当前有效需求已不同于最近确认快照，原配置保持不变)。`PATCH /requirement-state` 提交 `expected_revision` 与 `operations`,要求 Idempotency-Key;编辑幂等性使用完整操作集合的 SHA-256 指纹，版本冲突或运行中任务返回 409。
- `requirement.updated` 在状态持久化后发送完整状态，必要信息充足时另发 `requirement.ready`;前端不从 SSE 文案推断业务状态。
- 语义归类、表达强弱、否定、临时例外和备选理解由 Screening 模型调用承担，不用后端关键词白名单复判；代码校验 JSON、枚举、数值范围、本轮原文来源和合法状态操作。无独立总结模型调用；面板编辑、撤销、归并、追问、刷新 0 次模型调用。
- 用途事实和补充说明即使原强度为 must,也不自动成为需要商品证明的硬过滤；明确为 constraint 的自由文本硬条件在缺少目录证明契约时返回 `data_unavailable / requirement_evidence_missing`,指出具体待核验字段并保留要求。缺分类的旧 must notes 若与当前用途 titles 完全相同，可按现有结构识别为用途；其他只确认是用途说明还是配置条件。
- 仅保存本次会话记忆，刷新从 PostgreSQL 恢复；“帮朋友装机”、临时例外不写入账号资料或跨会话画像。跨会话长期偏好提取、个人/他人装机对象隔离、偏好失效和冲突处理均留待后续。

## 3. 已有配件与预算口径

`existing_parts` 保留品类列表;`owned_parts` 数组每项含 `category`、`model`、`quantity`。型号必须来自用户提供的信息，程序按当前目录的完整型号或品牌加完整型号精确匹配，不模糊推断，不让模型编内部 SKU。数量默认 1,只有 SSD 支持多件；一批同品类只允许一个准确型号，复杂混用先追问。已有件品类与准确型号由同一 reducer 原子联动：取消品类同步移除对应 owned_parts,`derived_from` 标识联动，恢复时不覆盖后来直接更正的型号。

- `budget_basis`:`new_purchase`(新增购买费用)/ `full_build`(整机参考总价)。无已有件时省略沿用整机口径；有已有件而未明确口径、或有品类无完整型号时先追问。已有件型号不在当前目录时说明资料不足，不替换成相似产品。
- 已匹配的已有件参与全部兼容性校验，与锁定项一样不可擅改；冲突时说明限制，不另购同品类配件冒充已有件。
- `screening_guard.go` 在 ADK 写入前读取模型声明的已有品类、型号和预算口径，生成结构化缺失字段列表，输出只针对相关字段的程序追问；型号按字母数字规范化核对原话，预算口径使用明确中文表达白名单。该核验是保守文本约束，不具备通用语义证明能力。
- 报价保留 `total_cny`(整机已知参考价)、`purchase_total_cny`(需购买部分已知价)、`purchase_missing_count` 和每行 `owned` 标记；预算依据显式口径选择对应合计。需购买件缺价不能冒充完整报价交付。
- **非交付结果**:`Decision` 区分 `clarify`、`catalog_infeasible`、`data_unavailable`、`search_exhausted`、`invalid_output`,记录原因码、缺失字段、范围及证据。`catalog_infeasible` 仅在程序取得完整目录确定性证据时使用(各必需品类独立最低价之和的乐观下界仍超预算)；未知价格不当作正数参与无解证明，该下界只证明当前目录不可达，不声称整个市场无解。平台预算证明已接入候选准备阶段，最多枚举 50 万组，超限继续正常选配；程序不自动改预算。非交付不保存配置版本。

## 4. 有界工具循环

每次 Builder 最多 8 次模型往返、24 次工具执行；一次运行最多 3 次外部搜索、6 次网页读取。第 8 次只整理结果。无结果、截断、缺价、目录不可用、规格未知和兼容性失败都返回给模型，不按用户偏好提前退出，也不指定模型必须照抄的修复配置。

- `search_local` / `search_local_batch`:本地型号、规格检索和分页；过滤仅由模型本次查询指定，可自行放宽。`order_by` 默认 relevance,可指定 price_asc / price_desc 按精确十进制价格优先；缺价放最后且不删除。`price_range_cny` 提供所选品类候选的最低/最高已知报价及有价/未知数量，全未知返回 null 范围，不把它变为零元。批量一次提交 1-8 个独立子查询，每个分别计入工具上限，额度不足时返回已执行 results 及 pending_queries。
- `search_semantic`:复用 embedding 与 pgvector;命中表示相关，不证明规格。
- `search_web`:复用 SerpAPI,仅查询装机技术资料，优先官网规格、兼容性/BIOS 支持、安装指南和知识文章；不查询具体价格、优惠、库存或购买信息。
- `read_page`:公开 HTTPS 网页正文，默认 HTTP 优先；动态空壳可自动升级浏览器，模型也可显式指定读取方式。支持相关词定位和分页，完整有界正文进入方案快照。拒绝私网地址及登录/访问验证内容。
- `read_evidence`:按编号展开已保存来源，不重新联网。支持候选中已有的 `local:<候选编号>` 引用，返回本地商品快照及字段来源索引；本地检索的 sources 按候选编号给出 `{id,field,status}` 索引，避免重复携带相同元数据。
- `register_candidate`:正文中存在的型号、逐字段来源和摘录。未提供证据的规格不进入已核验参数；新注册候选不接收网页价格(price_cny 保持 null,误传的价格字段会清除并反馈原因)。规格来源映射支持完整路径 `specs.socket` 和历史短键 `socket`,两种键同时不一致时返回冲突。注册结果返回实际保存的 candidate(含 specs、attributes、unknown),注册成功不等于核验通过。本地候选缺规格时可传原编号及完全一致的身份，只提交待补字段；已知值冲突原子拒绝；补充后旧核验失效，需 evaluate 重新核验。
- `evaluate`:用本地/会话候选快照计算价格和运行原兼容性规则。自第二次成功核验起附带 comparison(same_selection/same_validation/same_quote),提示重复核验不能补齐缺项；每次仍执行真实核验，不缓存跳过。已有件只有准确型号、数量对应后才从采购金额中扣除。

本地检索反馈 new_count、previously_returned_count、seen_in_scope 和 scope_category;query 只影响相关性排序，不缩小品类总数。初始输入另附 owned_candidates,按当前 owned_parts 的品类和完整型号匹配本轮目录；不修改用户需求、不把已有正式配置当成已购，也不自动核销采购金额。工具反馈附带剩余额度。

**预算核验**：报价完整性按用户实际预算口径——明确 new_purchase 且已有件已准确对应时，只要求新购件报价完整；full_build 沿用完整整机报价检查。预算金额、费用口径及明确授权的浮动比例由报价核验共同判断，不要求模型重复提供 met 评语；模型原评估保留供诊断，既不能否决已核实的算术，也不能覆盖超预算/缺价事实。

## 5. 语义选件

语义选件维护 embedding 文本、候选检索与工具接口；默认只在明确软偏好时补充语义候选，硬约束始终由确定性过滤负责。

- 软偏好素材单独维护在 `scripts/data/styles/styles.json`(按 SKU 键入):noise、color、side_panel、style_tags、summary;case/cooler/gpu 三类逐 SKU 标注，缺失键降级为“品类+品牌型号+specs 摘要”。标注是外部数据，当数据不当指令；拿不准的字段填 null,不编造。
- embedding 拼接模板:`"{品类中文}: {brand} {model}。{specs 关键参数摘要}。{结构化风格字段人话化}。{style_tags}。{summary}"`,缺失段直接省略。模型输出 1024 维(维度只写 `cmd/embedparts` 代码常量);`embedding_text` 落库是可解释性关键——检索命中时能给出“因哪些词命中”。`cmd/embedparts` 幂等全量重算，任一 SKU 失败整批报错。
- `store.SemanticCandidates`:`ORDER BY embedding <=> $query` 取 top_n,只召回 `embedding IS NOT NULL AND active`,返回 similarity 与 match_text;与 SQL 结构化过滤并联双路，候选仍要过预算判断与规则校验。
- 不建向量索引：160 SKU 顺序扫描远快于索引收益，SKU 上千再议。

## 6. 网页读取策略

`read_page` 默认 `method=auto`,先普通 HTTP,只有可识别的动态空壳才自动升级到 Crawl4AI;HTTP 非成功状态、验证码、登录、Cookie 同意墙、限流、网络故障不自动换浏览器重试，收到访问限制后应换公开来源，不尝试绕过。

- Docker 使用固定 `unclecode/crawl4ai:0.9.3` 镜像，入口为仓库内 `deploy/crawl4ai/reader.py` 的 `POST /read {"url":...}`(专用小接口，不用上游通用 `/crawl`)。端点和 Bearer 凭据来自环境，不接受模型指定；宿主只暴露 `127.0.0.1:11235`。启动:`python scripts/start-crawl4ai.py`,健康检查 `/health` 返回协议 `pc-page-reader/1`。
- `Evidence.text` 保存完整有界正文，HTTP 原始响应及解码文本各限 2 MiB,浏览器 Markdown 限 2 MiB;超限明确失败。HTTP 按响应头或 HTML 声明解码字符集(含 GBK),保留段落与表格单元边界。每次模型视图最多 16000 Unicode 字符，支持 query/offset/limit 分页；跨轮恢复后可 `read_evidence` 续读。
- 每次 read_page 计一次页面工具调用；自动升级最多实际读取两次，共用 55 秒截止时间；服务整体期限 45 秒，实际 `/read` 路径最多 2 个执行、8 个等待，每分钟 60 次准入，超出返回 429。每次浏览器读取独占进程组和临时目录，不复用 Cookie 或浏览器上下文，完成或断开都回收进程组。
- Go 侧拒绝私网和非 HTTPS 目标；抓取缓存显式 bypass,避免缓存旧报价冒充新读取。服务是网络查询辅助依赖，不加入产品 API 硬性就绪条件；清空 `CRAWL4AI_URL` 并重启 buildsvc 可只使用 HTTP。
- 服务端新注册外部候选时清除网页报价及其来源映射，防止偶然读到的标价进入配置总价；本地价格快照继续使用并保留原观察日期。买手补价格属于独立、人工复核的数据维护流程，不是客户端实时联网查价。
- 扩库原则：新型号先建公共产品候选身份(品牌、准确型号、后缀、容量/条数、盒装/散片)，再补字段级规格；衡量扩库效果采用关键字段覆盖率、价格新鲜度、误绑率和常见需求本地完成率，不能仅以 SKU 总量验收。会话候选留在会话；重复出现且证据足够的公共商品事实走现有 review/quarantine/release 流程。

## 7. 证据、存储与产品

- 迁移 `00016_planning_proposals.sql` 新增 session_proposals、共享 search_quota,builds 增加 candidate_snapshot;迁移 00017 增加正式配置关联。候选和证据只属于当前会话，不写入全局商品库或个人画像；正式配置保存同一候选快照，分享、导出和后续改单从该快照读取。
- `model_outcome` 保留模型原始意图,`outcome` 为最终业务结果,`delivery.status` 为服务端交付核验(not_applicable / unresolved / eligible / delivered / stale)。完整且无实质待解决问题的 proposal 和 ready 使用同一核验路径：真实兼容性、完整报价和有效必须条件评估满足后自动交付。必要追问必须输出 clarify,不能只藏在回复文本中。
- 已有草稿但核验仍有缺项时，collect/clarify 也标记 delivery.status=unresolved,回复由实际缺项生成；不能靠模型路由标签透传“全部兼容”或“已正式交付”。
- 方案、版本、需求快照、关联信息、助手回复和运行完成状态通过一个事务保存；run_id 幂等，同一运行并发或重复完成只生成一版。保存时锁定会话并比较需求 revision;需求已改变则保存 stale 方案，不生成版本或覆写当前需求。
- 素材参数属于工作负载事实(如“剪 4K 视频”)，不是屏幕分辨率，也不重复写入 notes;后续更正复用已有 free.* 条目编号，跨字段重复内容由模型发出同轮 set/remove 原子处理。
- 来源附带 candidate_id、field、kind 与获取日期；catalog 是本地库已有资料，search 是搜索摘要，page 是已读取正文；本轮调用数与资料获取时间分别展示，旧来源不伪装为本轮联网。SerpAPI 的交互路径与 Python 后台采集都先原子预留同一 PostgreSQL 月额度，计量失败不发搜索请求。

## 8. 观测与验证

- 结果记录 model_calls、tool_calls、search_calls(尝试)、search_requests(已预留并发出的)、page_calls、tokens、duration_ms 和 stage_ms。
- 运行时观测(F3):planning run 结束时 `agent_runs` 行持久化 screening/builder 模型身份与计量列,`builds` 行回链 run_id 与快照 id;终态事件镜像进 PG `run_events`;完整产物按 run 归档 `planning_artifacts`。
- 额度与预算(F7):外部搜索额度请求成功后结算本地预留;`RUN_TOKEN_BUDGET` 硬限单轮 token,超限立即进入整理轮并保留 proposal;`DAILY_TOKEN_BUDGET` 由产品侧在启动规划前硬限。两个预算默认 0(不限)，只作运行时硬限，不进提示词。
