无产品失败样例(本基线全绿)。开发过程中出现并修复的两类问题:

1. **评估设施缺陷(technical fault 类)**:断言用 `*product.Problem` 做 `errors.As`,
   而 `NewProblem` 返回值类型,导致 5 条本应通过的拒绝断言误报失败。修正为
   `problemCode` helper(值类型匹配);该教训固化为门禁 technical_fault 与产品
   行为失败分离的必要性。
2. **产品缺陷(多 owner 冲突来源可辨认)**:前端建议列表只显示 `choices[0]` 的
   来源原话,冲突时第二个候选值的原话不可见,用户无法辨认选项出自哪个身份的哪句话。
   服务层本就为每个 choice 携带独立 source(quote/session/date,PM-ISO-02 断言覆盖);
   修复 `preferences-panel.tsx` 把原话行移入逐候选渲染,新增组件测试
   "多身份冲突时每个候选值各自展示来源原话,不能只显示首选"。

## 覆盖与不覆盖

- 覆盖:显式保存(白名单/来源核验/supersede/幂等)、按显式 subject 手动召回
  (隔离/当前需求优先/多 owner 冲突)、逐项确认(确认前不生效、确认后 kind=edit
  写入)、显式删除(物理删除含墓碑)、temporary 与白名单外字段拒存。
- 不覆盖(与 README 边界一致):自动提取、初筛注入、Builder 模型注入(未接入,
  不宣称模型效果);易失事实新鲜度窗口(PM-STALE-01 仅验证拒绝写入);
  auth 认领流程;HTTP 层(另有 producthttp 测试)。

## 下一步的证据基础

- **recipient→subject 映射**:尚无证据支持自动化。现有隔离评估(ISO-01/02)只证明了
  "显式选择 subject"合同下的正确性;产品没有从会话 `recipient` 字段推断 subject 的
  通道,也没有该行为的误推断失败样本。决定映射策略前需要先在真实对话里收集
  "recipient 提及与用户实际选择 subject 不一致"的频率与后果数据。
- **召回入口优化**(如自动提示可召回的偏好):本基线确认了"确认前不生效、当前
  需求优先、冲突不代选"三条安全性质都有确定性保障,这是任何入口改动必须保持的
  不变量;入口本身的产品决策(何时提示、提示多少)仍缺使用数据,暂无足够证据。
