## 一、目标口径:先把"成功"定义成可计算的

**建议采用双口径 + 否决项**,对应 §三(指标)与 §六(验证谱系):

- **日常回归报 Pass@1**:每条用例跑 1 次,提示词/检索/规则改动后必跑(升级现有"用例 A 回归"纪律,见 §十一提示词敏感性评估)。
- **发布门禁报 Pass^3**:关键子集每条用例独立跑 3 次(不同采样),全部通过且零否决项触发才可发布;对应"装机单属硬约束交付"的业务可靠性要求。
- **一票否决项清单(成文,进校验器/runner)**:

| 否决项 | 判定方式 | 对应现有接缝 |
|---|---|---|
| SKU 编造:selection 中 sku 不来自本次检索工具返回 | runner 侧记录检索返回集,与 selection 求差 | 检索调用在 `internal/buildharness/planner.go`,需在 runner 侧留存返回 |
| 预算越界:报价合计落不到 budget_cny × (1 ± budget_flex) 闭区间 | 已有校验规则,复用 | `internal/agents/pipeline/validator.go` |
| 锁定品类被改动:locked 品类 SKU 与基版本不一致 | 改单用例专用断言,逐字节比较 | 基版本在 `build_state`,由校验节点回写(`validator.go`) |
| 交付兼容性冲突:overall_status=fail 仍交付 | 校验器已有 fail 态,补"fail 不可交付"断言 | 同上 |
| 报告编造:人话报告中价格合计 ≠ selection 求和、出现 specs 之外的技术参数 | **新增**确定性断言(见验证器矩阵) | 报告生成在交付节点,需把 selection/specs 一并交给断言 |

## 二、评估集 v0 蓝图(建议 30–35 条起步)

按 §五(数据集设计)的三个来源论,自建业务集是唯一能指导产品决策的来源;按 AndroidWorld 经验采用**参数化模板实例化**,按 GAIA 经验**难度分层**。v0 建议构成:

**L1 单轮整机生成(约 15 条,参数化生成)**
维度:`预算档(3k/8k/15k/25k) × use_case(gaming/productivity/general) × 分辨率(1080p/2K/4K) × brand_pref(默认/intel+nv/amd) × noise_pref × existing_parts(0–2 项)`。每条用例是模板 + 参数,不写死期望配置单(选件自由度留给 Agent),只锁**可验证约束**:预算区间、brand_pref 满足、existing_parts 品类被标注、全 pass。

**L2 改单 / 轨迹前缀(约 10 条)**
冻结 `build_state`(用例 C/D/E 的 v1→v3 脚本素材,`docs/tech/版本快照与增量改单.md`)+ 一条 ChangeRequest,断言(§六轨迹前缀回归):
- 锁定品类 SKU 与基版本**逐字节一致**;
- 仅解锁品类重新选件;
- adjust_budget 后合计重新落区间;
- **可接受动作集合**而非唯一答案:换件方向符合 `target_hint` 即可,不锁具体 SKU。

**L3 陷阱与边界(约 8 条)**
直击提示词里有纪律、无用例验证的行为:
1. **品牌推断陷阱**:用户只说"要安静的机器",不含品牌词 → 断言 brand_pref 缺省(初筛提示词明令禁止从噪音/风格推断,§二渐进式信息透露同理);
2. **预算缺失**:只说"想装台电脑" → 断言**只追问一次、不输出 JSON**;
3. **游戏缺分辨率**:断言追问或按显示器推断,不许沉默编造;
4. **超三类意图**:用户要求"推倒重来换平台" → 断言降级输出完整 RequirementSpec 且 notes 注明;
5. **预算不可能**:预算明显低于最低可用配置 → 断言如实交付 review/warning 而非编造越界配置;
6. **语义偏好命中**:「要安静的显卡」「白色海景房」→ 断言命中品类 + rationale 引用命中词(用例 F 的可自动化版);
7. **existing_parts**:用户已有 GPU → 断言照常选件但标注"用户已有,可不购买";
8. **校验反馈定向修复**:构造一次 review 反馈 → 断言换掉冲突件而非从头乱换(可用 `harness_test.go` 的 fakeModel 脚本化,零 LLM 成本)。

防泄漏在本项目语境下风险低(评估集不进任何训练),但参数化本身同时解决覆盖率与"用例被演示脚本背答案"的问题(§五防泄漏)。

## 三、验证器矩阵:确定性优先,Judge 只补一段

按 §六"向右移动不放弃左侧":

| 检查内容 | 方式 | 成本 |
|---|---|---|
| schema 严格解码、SKU 存在性、兼容性、预算区间、fail 不可交付 | 复用现有校验器 + golden 规则 | 零(已有) |
| 锁定品类一致、brand_pref 满足、existing_parts 标注、追问行为(无 JSON 输出) | runner 侧断言(新增,均为纯函数) | 低 |
| SKU 溯源(不在检索返回即否决)、报告合计=selection 求和、rationale 引用命中词 | runner 侧断言(新增,需留存检索返回与报告文本) | 低 |
| 报告/rationale 质量(是否说到点子上、解释是否可信) | **LLM-as-a-Judge,Rubric 四档 + 幻觉否决**,仅这一维度 | 中 |

Judge 设计要点(§六 Rubric 四准则与偏见对策):每档写可验证行为(如"rationale 对每个品类给出了与所选型号 specs 对应的理由",不写"解释深刻");幻觉设否决;**评判模型与被评 builder 模型异族**;评分与长度的相关性定期抽查。v0 阶段 Judge 可以只覆盖"人话解释报告"一个维度,甚至先缓一缓——确定性断言已能拦住大部分风险。

## 四、失败归因:领域分类表 v1 + 三段 diff 定位法

按 §六失败归因方法,本项目三段流水线每段输出结构化 JSON,**首错定位 = 相邻两段 diff**:RequirementSpec(初筛输出)→ ChangeRequest(意图)→ BuildDraft(生成输出)→ ValidationReport(校验输出),合法输入变成非法输出的那一环即首错所在。

领域错误分类表 v1(由书中 Coding Agent 九类表改编,生产中随归因案例迭代):

| 错误类别 | 典型表现 | 首错定位 |
|---|---|---|
| A1 需求理解错误 | RequirementSpec 漏条件/范围宽窄;该追问没追问 | spec 与用户原话逐条对照 |
| A2 brand_pref 违规推断 | 用户未点名品牌却填了 cpu/gpu 偏好 | spec.brand_pref 与原话比对 |
| A3 改单意图误判 | 意图与载荷不对应;该降级整单未降级 | ChangeRequest 与 build_state/原话比对 |
| B1 SKU 溯源违规 | selection sku 不在检索返回 | 检索返回集 ∩ selection 差集 |
| B2 预算违约 | 合计越区间;明显未利用预算 | 合计与区间公式 |
| B3 unknown 未消除 | 存在字段完整候选仍选 null 字段型号 | specs 对照候选池 |
| B4 锁定品类违规 | locked 品类 SKU 被改 | 与基版本逐字节比对 |
| B5 冗余检索 | 已有足够候选重复同条件检索;逐品类串行 | 检索调用序列分析 |
| B6 忽视校验反馈 | review 后未定向换冲突件、乱换无关件 | 两轮 selection diff 与 feedback 比对 |
| C1 信息告知错误 | 报告合计不一致;rationale 无命中词;已有件未标注;编造参数 | 报告断言 vs selection/specs |
| C2 执行异常 | 输出截断、超时、3 轮熔断 | 区分模型停止 / Harness 超时 / 工具故障 |

配套纪律(§六):记录**结构化归因 JSON**(首错环节、类别、证据引用、根因 vs 后果、置信度),连同评估集用例参数、快照日期、模型配置、完整轨迹一起存档;"最早且能解释后续失败"原则选主因;能规则筛的(B1/B2/B4/C1)先规则筛,再 LLM 归因。

## 六、阶段路线建议

- **P0 评估集 v0 + runner 骨架**:固定快照开关 + L1 参数化 15 条 + 确定性断言矩阵 + `cmd/eval` 出 Pass@1 报告。DoD 方向:提示词改动回归从"用例 A"升级为"评估集 v0 全绿";runner 在固定快照下重复运行结果可复现。
- **P1 可靠性与归因**:否决项清单进 runner、L2 改单前缀 10 条、L3 陷阱 8 条(其中无 LLM 用例先落 golden 式测试)、归因 JSON schema + 分类表 v1、发布门禁 Pass^3。
- **P2 闭环与选型**:负反馈端点 + 会话级事件 + 回流管线(失败案例 → 归因 → 新用例)、语义检索/修复环消融开关补齐、SCREENING/BUILDER 双档对照实验(模型替换,§一)、LLM-Judge 报告质量子集。

## 七、统计显著性纪律(写给未来每一轮对照实验)

按 §八:v0 的 30 条评估集,70% 成功率时 95% 置信区间约 ±16 个百分点——**只够筛方向,不够做精细决策**;扩到 100 条约 ±9 个百分点。因此:

1. 对照实验(换提示词/换模型/开关消融)一律**配对**:同批用例逐题记录胜负,McNemar 或配对 bootstrap,不拿两个总分相减;
2. 涉及 LLM 采样的结论,每配置 ≥3 种子报均值与波动;
3. 分差小于噪声带宽 → 不做切换/合入决策,先扩样;
4. 评估集用例与快照日期随报告一起写明——结论只对"该分布 × 该快照"负责。

## 八、开放问题清单(留待实施策划决策)

1. **runner 的 LLM 策略**:真实模型(贵、慢、随机,但测真实能力)vs fakeModel 回放(零成本、确定性,只锁行为)——建议分层:L3 之 8、B6 类行为回归用 fakeModel 进 `go test`;L1/L2 用真实模型走 `cmd/eval`。两者边界要在 P 设计文档里定死。
2. **评估运行的落库策略**:不落库(校验器交付路径需旁路)vs 隔离会话/隔离 build 写入——影响 build_state 回写与版本树清洁度。
3. **评估集 fixtures 存放**:`internal/.../testdata` 随包走 vs 顶层评估目录;基线更新开关(仿 golden `-update`)的动用纪律。
4. **Pass^3 门禁的子集定义**:全量 × 3 成本高;关键子集选哪些(L1 高预算档 + L2 全部 + L3 陷阱)?
5. **负反馈的最小形态**:仅 API + fingerprint,还是连前端点踩一起做(涉及 `web/` 与 P 序列排期)?
6. **LLM-Judge 的引入时机与成本**:评判模型选哪家(须与 BUILDER_MODEL 异族)、Rubric 先只做报告一个维度还是连 rationale 一起?
7. **归因记录的存放位置**:并入 `P10_METRICS_DIR` 体系(继承脱敏纪律)还是独立目录;与 `docs/eval/` 的验收记录如何衔接。
8. **可接受动作集合的机器可读格式**:改单前缀用例的 verdict 规则用代码写死还是声明式 YAML(影响后续用例生产成本)。

## 九、与现有纪律的衔接

- 本体系**取代**"改提示词只重跑用例 A"的回归口径(P2 设计 §8、P3 设计 §回归),`prompts.go` 头注在 P0 落地后应同步改写;
- golden 50 组与 `cmd/validate` 保留不动,作为校验器自身的单元回归层;
- 真人评审(`docs/eval/`)继续承担人工验收职能,评估体系不替代它,而是把其中可自动化的部分(用例 A/C/D/E)吸收为 L1/L2 用例;
- 本文与 [01](01-Agent的评估方法论精读.md)、[02](02-本项目评估现状与差距分析.md) 同属 `docs/eval/methodology/` 应用系列,实施设计文档(若立项)应回指本文的开放问题清单并逐条给出裁决。
