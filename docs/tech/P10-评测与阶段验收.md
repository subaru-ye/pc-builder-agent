# P10 评测与阶段验收 — 实现设计

> 状态:实施中。评测工具、全部自动门禁和 Live Pass³ 已完成;真人盲评待执行。P10 不新增功能,只补评测覆盖、修复阶段 1 缺陷并形成可复验结论。

## 1. 目标

P10 回答四个问题:

1. 规则仍然正确吗?
2. Agent 多次运行是否稳定,而非碰巧成功一次?
3. Web 主路径在真实环境中是否可恢复、可理解、可分享?
4. 普通用户是否认为方案可以直接作为购买前参考?

任何一项未满足都不能宣布阶段 1 完成。不得为了过门禁降低既有规则、隐藏 unknown、放宽所有权或删除失败样本。

## 2. 测试分层

| 层级 | 默认是否运行 | 数据/模型 | 目的 |
|---|---|---|---|
| Go unit | 是 | fake | 状态机、handler、presenter、规则 |
| Go integration | 验收时是 | PostgreSQL/Redis | 事务、所有权、SSE 重放 |
| Web unit/component | 是 | mock API | 表单、状态、渲染、SSE parser |
| Playwright mock E2E | 是 | mock SSE/fixture | 快速稳定回归完整 UI |
| Playwright live E2E | 显式 | 真实 PG/Redis/百炼/A2A | 最终链路和恢复 |
| 真人评审 | 阶段退出 | 真实产品 | 可理解性与配置可用性 |

真实模型测试不能混入每次 go test 或 pnpm test,避免成本与波动;但阶段退出必须显式执行并保留匿名化结果。

## 3. Golden set 扩展

### 3.1 数量与类别

现有 20 组保留,新增至少 30 组,总数 ≥50。新增用例按以下覆盖分配:

- 插槽/芯片组边界:4。
- 内存代数/频率/缺失字段:4。
- 显卡限长、无独显、供电接口:5。
- 风冷/AIO 高度、冷排、散热能力:5。
- 电源 115%/130% 邻界和多接口:4。
- 板型、M.2 数量与字段缺失:4。
- 多条规则同时失败/unknown:4。
- 正常 all-pass 代表配置:至少 4。

一份 fixture 可以覆盖多条规则,但总集必须让每条规则至少出现一次 pass、一次 fail 或 unknown;不适用的 fail 必须在说明中解释。

### 3.2 断言

继续锁定固定顺序、outcome、severity、missing_fields、overall_status 和稳定 observed;detail 不做逐字 golden,但进入解释一致性人工/半自动检查。

更新 golden 必须先人工审查差异。禁止把 -update 当作修复失败测试的默认手段。

## 4. Agent 稳定性矩阵

每个核心场景连续运行 3 次,三次均满足才通过:

| 编号 | 输入/动作 | 必须满足 |
|---|---|---|
| L1 | 8000 元,2K 玩黑神话 | 需求可确认;最终 pass;预算在 flex 内 |
| L2 | 安静的显卡,白色海景房 | 语义检索命中有解释;不凭空加 GPU 品牌 |
| L3 | 对 L1 降 500 | 新版本;未涉及件锁定;预算更新 |
| L4 | 对 L3 换成 A 卡 | GPU 为 AMD;其他件尽量不动;最终 pass |
| L5 | 信息不足的开场 | 只追问关键字段,不调用 buildsvc 生成 |
| L6 | 编辑需求后确认 | 严格采用编辑后字段,不是旧 Agent 输出 |

每次记录:

- run id、输入、最终状态、版本号。
- 首个进度事件耗时、完整耗时。
- 初筛/远程调用次数、生成校验轮数。
- embedding cache 是否命中。
- 失败 code 和是否可重试。

不保存 API key、完整模型请求/响应或真人隐私信息。

## 5. Web E2E 场景

### 5.1 默认 mock E2E

1. 新用户首次输入,创建匿名 cookie 和会话。
2. 初筛追问,刷新后历史仍在。
3. requirement.ready → 编辑预算/品牌 → 保存 → 确认。
4. SSE partial、无 partial、心跳、断线重连与 Last-Event-ID。
5. build.saved 后配置/校验/版本自动刷新。
6. 更换此件只预填,用户编辑发送后生成新版本。
7. 回看旧版只读,任意两版 diff。
8. Markdown、分享链接、分享图、撤销。
9. owner A 访问 owner B session 得到通用 404。
10. Redis degraded、buildsvc 503、timeout、interrupted 恢复。

### 5.2 Live E2E

固定执行顺序:

1. 启动健康 PostgreSQL/Redis。
2. 执行迁移并核对 parts/prices/embeddings。
3. 启动 buildsvc、api、web。
4. 用全新匿名浏览器上下文完成 L1。
5. 刷新页面,确认同 run/session 恢复。
6. 完成 L3、重启 api、恢复页面,再完成 L4。
7. 验证 v1→v3 diff、Markdown、分享页与 PNG。
8. 撤销分享并确认 404。

API 重启只要求已完成 run 恢复;正在运行的 run 应显示 interrupted 并允许重试,不要求阶段 1 实现跨进程续跑。

## 6. 性能与可观测指标

### 6.1 交互指标

- 创建会话/读取本地数据 p95 ≤500ms。
- 首个 run.started/progress ≤1s。
- 业务事件空窗 ≤15s;否则至少有 heartbeat。
- 30s 无字节触发前端重连提示。
- 60s 未完成显示长任务说明。
- 10min 服务端硬超时。

完整生成 ≤60s 仍是 PRD 的体验目标,但模型供应商波动可能导致暂时不达标。P10 必须报告 3 次运行的原始值、中位数和最大值;不得只写「性能正常」。如果 3 次中任一次超过 10min 或无进度静默超过 30s,阶段退出失败。

### 6.2 质量指标

- 错误级规则准确率 100%。
- 含警告级 golden 通过率 ≥95%。
- 改单未涉及件锁定率 100%。
- LLM 解释与规则结论矛盾数 0。
- 预算符合率 ≥90%。
- 需求理解一致率 ≥90%。

## 7. 真人评审

### 7.1 样本

邀请 3–5 位未参与开发的人,至少包含:

- 1 位装机新手。
- 1 位了解硬件但不熟悉本项目的人。
- 1 位有实际配单经验的人。

每人用自己的真实或假设需求完成一台配置。开发者只观察,除非受试者明确卡死,不口头补充产品未表达的信息。

### 7.2 任务

1. 输入预算和用途。
2. 理解并确认需求卡。
3. 判断配置是否可直接照买。
4. 找到价格日期和免责。
5. 修改一项偏好或降低预算。
6. 找出两个版本改变了什么。
7. 导出或分享结果。

### 7.3 Rubric

每项 0/1/2 分:

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 需求一致 | 明显误解 | 部分正确需修 | 准确 |
| 配置完整 | 缺关键件 | 完整但有疑问 | 完整清楚 |
| 可信度 | 看不懂结论 | 能理解部分 | 校验/快照/免责清楚 |
| 改单可控 | 非目标件乱变 | 有少量不合理变化 | 变化符合意图 |
| 可直接照买 | 否 | 修改后可用 | 是 |
| 分享可理解 | 关键信息缺失 | 基本可读 | 独立可读 |

「可直接照买」取该维度得 2 的人数占比,目标 ≥80%。同时记录卡点、误解和受试者原话摘要,不收集姓名等非必要信息。

## 8. 缺陷分级与退出纪律

| 等级 | 示例 | 处理 |
|---|---|---|
| P0 | 越权、密钥泄漏、错误配置显示 pass | 必须修复并全量回归 |
| P1 | 主路径中断、版本错乱、分享撤销无效 | 必须修复 |
| P2 | 移动布局阻碍核心操作、文案易误解 | 原则上修复;延期需记录 |
| P3 | 非关键视觉细节 | 可进入 backlog |

退出时不得存在 P0/P1。P2 若延期,必须有明确 issue、规避方法和不影响可用率的证据。
