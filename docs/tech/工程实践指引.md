## 一、核心立场印证(贯穿全程)

这几条不是新增要求,而是既有设计决策在书中的印证——写在这里防止未来动摇:

1. **"Agent = Model + Harness,大部分代码投入约束/验证/纠正"** —— 本项目的校验核算 Agent(纯规则引擎)+ 自动换件重试正是 harness 的教科书形态。书中案例:LangChain 不换模型只改 harness,Terminal Bench 得分 52.8%→66.5%。坚持:规则引擎的判定权不因"模型变强了"而让渡。
2. **"约束优先于指导"** —— 能用代码强制的不写提示词:兼容性用规则表、`internal/rules` 零 LLM 用 depguard、schema 校验用 struct 定义,而不是在 prompt 里写"请确保兼容"。
3. **"从简单到复杂渐进"** —— P2 单进程流水线 → P5 才拆 A2A 的排序被书中原则直接支持;不要为架构感提前拆。
4. **"评估先行"** —— P1 的 golden set 在任何 LLM 代码之前建立,正是"动工前先建评估体系"。
5. **"执行前先做意图澄清"** —— 初筛 Agent 的存在(追问缺失字段、消解预算冲突)就是这条的产品化。

## 二、上下文工程(P2 三 Agent 流水线)

1. **KV Cache 前置约束:静态前缀冻结,动态信息尾部追加**。系统提示词与工具定义定稿后不动;时间戳、报价快照日期、当前需求单状态一律作为消息追加,**绝不嵌进 system prompt**(书中真实案例:前缀嵌时间戳导致首 token 延迟 0.5s→3-5s、账单翻倍)。百炼同样有 prompt cache,同理适用。
2. **系统提示词用流程驱动 SOP,规则细化到可执行**。初筛 Agent 的追问顺序写成分步 SOP;生成 Agent 的预算分配写死数字区间(游戏机显卡 35-45%、生产力 CPU 优先),不写"合理分配预算"这类给模型自由裁量的模糊话。依据:Tau-Bench 消融显示仅打乱信息组织结构,成功率降超 30%。
3. **提示词按代码工程化管理**:随代码入 Git、确定性渲染、每次改动跑一遍端到端用例(A/C/D)当回归。不搞"聊天窗口里调好了就贴进去"。
4. **调不好先做消融,不要全面重写**:某个 Agent 表现差时逐项关掉提示词组件定位根因。

来源:[02-上下文工程与记忆](../ai-agent-book/dev-notes/02-上下文工程与记忆.md)

## 三、状态管理(P4 增量改单)

1. **配置单状态用代码维护、显式注入,不让 LLM 从历史里数**。改单会话中"当前版本号、总价 vs 预算余量、已锁定件、修改历史摘要"提炼成结构化状态块,由 Go 代码生成并注入上下文末尾——绝不让模型翻多轮历史自己统计(书中实测:让大模型批量统计长历史大多出错)。这正是我们 Redis 会话热上下文(P6)该存的东西。
2. **状态覆盖不足比没有状态更糟**:状态块必须覆盖改单会用到的全部维度(锁定清单尤其关键——FR-402 的 100% 锁定正确率依赖它),新增字段当"改表结构"级别对待。
3. **数字读数配操作策略**:注入"重试第 2/3 次"时同时写明"到 3 次带失败报告出栈";只给读数模型推不出该怎么办(书中基准:配操作手册后通过率 +19~49 个百分点)。

来源:[02-上下文工程与记忆](../ai-agent-book/dev-notes/02-上下文工程与记忆.md)

## 四、工具接口设计(P2 校验/检索 tool)

1. **真值不采信模型自报——本项目最重要的一条**。BuildDraft 只传 SKU 引用,价格、参数、性能分一律由校验 Agent 从 PostgreSQL 真值获取,模型报的数字仅作 checklist 比对,不一致记告警。这从结构上消灭"幻觉价格/幻觉参数"进入报告的可能。
2. **工具描述从 Agent 视角写:边界 + 示例 + 协作关系**。检索工具要写清"何时用 SQL 结构化过滤、何时用语义检索、不接受什么输入",附 2-3 个真实调用示例(书中数据:加示例准确率约 72%→90%,删描述错误率 +45%)。
3. **参数保真,禁止静默转换**:SKU 名规范化、单位换算若必须做,写进工具描述并在返回值里告知模型,否则模型陷入无法自诊的反复失败。
4. **检索返回结构化候选 + 显式截断**:零件候选返回结构化列表(sku/关键参数/价格),超出 top-N 必须注明"另有 X 条被截断",严禁静默截断——模型会误以为看到了全部候选。
5. **执行-验证-反馈闭环**:校验不通过时,规则引擎的结构化错误(哪条规则、哪个件、什么值)原样喂回生成 Agent 自纠;反馈越具体自纠成功率越高。这正是 LoopAgent 回路的正确实现方式。

来源:[03-工具与执行环境](../ai-agent-book/dev-notes/03-工具与执行环境.md)

## 五、循环控制与错误恢复(P2 LoopAgent / 全程)

1. **不信模型单方面宣告完成**:配置单"合格"由校验器判定,不由生成 Agent 宣称——本项目架构天然如此(书中术语 proposer-reviewer,生成↔校验正是这一对),坚持不破例。
2. **主循环三停止条件**:校验全过 / 最大重试轮数 / 不可恢复错误,命中即停;另加**重复检测**——连续两轮换回同一 SKU 视为死循环,立即出栈(书中失效模式:Agent 反复执行相同调用)。
3. **错误先分类再恢复**:LLM 超时/限流可重试(指数退避),schema 校验失败原样重试无意义必须改输入,数据缺失(unknown)不算错误直接进报告。维护错误→策略映射表,每条路径设独立熔断上限。
4. **熔断后如实出栈**:重试烧完后带着失败报告与原因面向用户,不硬撑、不展示半成品(书中案例:同一恢复路径连续失败三千余次)。
5. **成本三件套**:单会话 token 预算上限自动终止、结果缓存(P6 前进程内 map)、模型分层(已定:初筛低价档/生成旗舰档)。注意书中提醒:只比单价选便宜模型,若成功率低导致重试,实际花费可能更高——分档效果要用端到端成本验证。

来源:[04-评估与可靠性](../ai-agent-book/dev-notes/04-评估与可靠性.md)

## 六、评估体系(P1 golden set / 阶段 1 评测)

1. **Pass^k 与 Pass@k 分清**:规则引擎确定性,golden set 天然 Pass^k;但含 LLM 的端到端用例(A/C/D)**单跑一次通过不算数**,同配置跑 3-5 次全过才算稳定(单次成功率 60% 时 Pass@5≈99% 而 Pass^5≈7.8%——差别就是这么大)。
2. **小样本分差不下结论**:20 组 golden set 上 1-2 组的差异在噪声带宽内,不足以支持"这个 prompt 更好"的切换决策;要下结论先扩用例或多跑几轮。
3. **轨迹与最终状态双重验证**:验收不只看对话说了什么,还要查 PostgreSQL 里 build 版本树、快照绑定是否真实落库——防"说了但没做到"的表面完成。
4. **用户模拟器渐进透露(阶段 1)**:评测时用 LLM 模拟用户按脚本逐步透露需求("我想配台电脑"→追问后才给预算),而非一次性全盘托出;初筛 Agent 的追问能力本身就是被测对象。可加陷阱用例(用户坚持超预算配置)测冲突消解。
5. **分数异常先自检评测系统**:golden set 挂了先查数据/环境/断言本身,再动 Agent 代码。
6. **model swap 定位瓶颈**:效果不好时固定 harness 换模型档位(百炼分档正好支持),分数不涨说明瓶颈在提示词/工具设计,不在模型。

来源:[04-评估与可靠性](../ai-agent-book/dev-notes/04-评估与可靠性.md)

## 七、检索与记忆(P3 pgvector / 阶段 3 画像)

1. **混合检索的印证**:本项目"SQL 结构化过滤 + pgvector 语义"并联,对应书中"稀疏(精确)+ 稠密(语义)双路召回,没有单一策略在所有场景可靠"。硬约束(预算、插槽、品牌)永远走 SQL,语义只负责软偏好——不要让语义检索承担硬过滤。
2. **统计与规则类知识不进 RAG**:兼容规则、预算分配比例是规则引擎和代码的事,绝不做成"检索相关规则片段给模型看"——模型注意力是软检索,天然干不了规则执行(书中黑猫白猫计数反例)。
3. **embedding 文本带上下文**:零件 embedding 用"型号 + 品类 + 关键参数摘要 + 风格标签"拼接(runbook 已如此设计),孤立型号串无检索价值——这是 Contextual Retrieval 的简化应用。
4. **外部数据当数据不当指令**:pc-part-dataset 的文本字段(描述、评测摘要)来自外部,进 prompt 前视为纯数据;若未来引入用户评测内容做 embedding 素材,同样处理——检索内容是间接提示注入的典型载体。
5. **阶段 3 用户画像走"提取-对比-决策"流水线**:新偏好入库前先检索旧记忆,由 LLM 裁决 ADD/UPDATE/DELETE/NOOP("现在喜欢 A 卡"应更新旧记录而非并存);聚合类偏好(历史预算区间)用结构化字段存,不靠 LLM 读文本心算。

来源:[02-上下文工程与记忆](../ai-agent-book/dev-notes/02-上下文工程与记忆.md)、[05-安全与部署](../ai-agent-book/dev-notes/05-安全与部署.md)

## 八、多 Agent 与 A2A(P5)

1. **协作环节的价值判据:引入新信息才存在**。校验 Agent 引入规则引擎判定(单靠生成 Agent 无法获得的确定性信息)——合理;将来任何"加个反思 Agent/审查 Agent"的念头,先问它带来什么新信息,纯文本自我审查不带新信息就砍掉(书中:无外部反馈的自我修正把对改错的比改对的多)。
2. **移交只传三样**:任务描述与验收标准、已确认的事实约束、结构化引用——A2A 消息(RequirementSpec/BuildDraft)已是此形态,坚持不往消息里塞对话全文或推理过程。
3. **确定性断链器**:跨 Agent 传递中错误会因"转述一致"获得虚假可信度;规则引擎作为流水线末端的确定性部件,是系统里"唯一不会说谎的环节",其结论永远覆盖上游任何 Agent 的自评。
4. **强模型给关键决策者**:生成 Agent(核心决策)用旗舰档、初筛用低价档的分配与书中"最强模型给规划者"同构。
5. **诚实标注 A2A 的账**:单跳拆分是学习目的,不是性能需要(书中:多 Agent token 开销数倍到 15 倍)——mvp.md 已如实定位,开源文档保持这个口径。

来源:[06-多Agent与持续进化](../ai-agent-book/dev-notes/06-多Agent与持续进化.md)

## 九、阶段检查单(评审时过一遍)

**P1(规则引擎)**:规则遇缺失字段输出 unknown 不崩溃 ✧ golden set 含故意错配与字段缺失用例 ✧ 规则包零 LLM import(depguard)

**P2(流水线)**:系统提示词 SOP 化、预算比例写死 ✧ 静态前缀冻结、动态信息尾部追加 ✧ 工具描述含边界+示例 ✧ Loop 有最大轮数+重复 SKU 检测 ✧ BuildDraft 只传 SKU 引用、价格从 DB 取 ✧ 提示词入 Git、改动跑回归

**P3(语义选件)**:硬约束走 SQL、语义只管软偏好 ✧ 检索返回结构化候选、截断显式 ✧ embedding 文本带品类与风格上下文

**P4(版本与改单)**:改单状态块由代码维护注入 ✧ 锁定清单进状态块 ✧ 验收查 DB 落库而非只看对话

**P5(A2A)**:消息只传三样 ✧ schema 单一出处(internal/schemas)✧ 重试回路留在服务进程内

**P6(Redis)**:会话状态即 §三的状态块,恢复后改单可继续 ✧ 缓存命中有日志

**阶段 1 上公网前**(远期,先记账):用户输入与外部内容来源标记 ✧ 分享页只读、无工具调用面 ✧ LLM 评判引入时先金标校准且与被评模型异构 ✧ 用户模拟器评测
