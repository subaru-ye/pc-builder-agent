# 评估设施

> 本文维护评估工具链:`cmd/evalplanning`(当前默认产品链路离线评估)、`cmd/eval`(历史执行器评估)、`cmd/evalchange`/`cmd/evalcompare`(对照与回归)、`cmd/evaldesk`(本机工作台)、`cmd/evaljudge`(解释诊断)、`cmd/feedbackexport`(反馈导出)。评估集内容见[评估入口](../eval/README.md),当前基线见[planning-v2](../eval/planning-v2/README.md)。

## 1. 入口与分工

- **当前产品链路**:`python scripts/eval/planning/run.py --out artifacts/<新目录>`,执行冻结 178 行目录(126 件 active)的离线机制集;`--live` 通过相同产品与工具路径调用真实 Screening/Builder,网页仍为冻结回放。真实套件必须标记 `live:true`、禁止含 oracle,总调用上限跨角色共享。
- **历史执行器**:`go run ./cmd/eval -mode run -snapshot-date <日期> -seeds 3`;v1.5 固定模型基线不代表当前 planning 成绩。产物为 `cases.json`、`meta.json`、`results.jsonl`、`report.md`,写入 `artifacts/eval/<时间戳>/`,不入库。
- **变更对照**:`cmd/evalchange` 保留的历史执行器对照流程,不能替代当前产品链路验收。
- 评估真实调用模型并读取数据库，但不经过产品版本保存层，不写 builds/versions;replay 不调用模型。

## 2. Runner 机制

- **快照与依赖**:`CatalogSnapshotByDate` 为候选、校验和报价提供指定价格批次；更换固定模型后需新建基线，不能继承额度链成绩。评估不使用 Redis embedding 缓存。
- **用例契约**:fixtures 在 `internal/evalsuite/testdata/cases/`,清单固定题目顺序与内容哈希；运行前校验清单，同一次读取的内容执行并保存完整副本。build 用例含 RequirementSpec、期望及可选 ChangeRequest/BaseSelection/Locked;screening 用例含用户文字和 spec/clarify 期望(`clarify_fields` 指定必须追问字段，`forbidden_clarify_fields` 指定禁止追问字段)。
- **断言与否决**:build 成功交付断言 A1–A10 覆盖结构、快照、预算、品牌、SKU 成员、报价合计、锁定、已有件(A4/A6/A8/A9 为 veto);期望非交付用 N1 校验类型、原因和证据，不把任意失败当正确拒绝。多轮 screening 用 `turns`(2–8 轮)，runner 回填真实前轮可见回复，所有轮次通过才计一次正确。S1 检查 JSON 形态，S2 检查预算/分辨率/品牌，S3/S4 是中文近似规则(追问字段/重复追问)，可能误判生僻表达，遇争议查看原文并人工复核。
- **判卷版本**：当前 `independent-v2`:A6 核对本轮实际候选包对应品类；A10 从冻结规格重新运行兼容规则，拒绝 fail 交付或保存报告与重算不符(veto);A7 将实际选件报价与冻结价格重算对比；缺必需证据记 E1。重算复用领域校验引擎，独立于 Harness 的成功声明和缓存结果。改变判卷规则必须显式演进 grader version 并保留旧版分支；历史运行继续按原版本重放，同口径重评另列，不覆盖首跑。
- **replay 边界**：通过 `cases.json` 恢复 Locked/BaseSelection 和期望，重判 build;screening 在 `results.jsonl` 保存最终可见回复，重放从原文重新执行 ExtractPayload 和 S1–S4,不信任旧分数。旧产物没有原文/完整题目时保留旧结论，标为“部分重放”。初筛核验规则修改后，可设 `SCREENING_GUARD_RUN_DIR` 执行 `TestScreeningGuardSavedRun` 零模型审计。
- **指标与门禁**：通过项拆分为成功交付、合理非交付、单轮初筛正确、多轮对话正确；Pass@1 是任务处理正确率，不能称为装机交付率；`AllGreen()` 要求无失败、无 data-error。当前场景用于方向性回归，不能支持精细模型排名。
- **元数据与归因**：保存三角色脱敏模型配置、Git commit/dirty、Go 版本和实际程序 SHA256;新运行另存提示词 SHA256(`prompts.json`)和完整 `SnapshotView` 指纹,由 `VerifyRunEvidence` 校验。归因是失败断言到领域码的规则映射(主因标首个)，不是自动因果分析。`candidates` 保存本轮实际候选包独立副本。
- **用量**：逐记录统计逻辑模型/Embedding 调用、返回 token 元数据的调用数及已知 token;nil 表示未测量，缺上游用量不能当作零，不换算费用。

## 3. 变更回归

目标：修改后能直接看到哪些题的结果或输出发生变化、是否退步、失败证据是什么、调用和 token 增加多少。

```bash
# 查看基线范围与当前复核；零调用
go run ./cmd/evalchange -baseline artifacts/eval/<目录> -max-calls 300
# 改完提示词或逻辑后实跑对照（需与基线一致的评估库）
go run ./cmd/evalchange -mode run -baseline artifacts/eval/<目录> -max-calls 300
# 两次运行已存在时生成对照报告；零调用
go run ./cmd/evalchange -mode compare -baseline <A> -candidate <B>
```

- 退出码：0 全部通过且无新增失败；1 仍有失败(含限额耗尽的未执行题)；2 条件、证据、完整性或工具错误。
- 流程：先离线复验基线题目/记录/模型/快照 → 固定基线的题目、快照、模型及 Harness 参数，构建并标识本轮实际程序 → 同版判卷规则复核两侧，逐题输出原成绩、复核成绩、失败断言及证据、输出变化、用量差异 → 报告写入新目录。新增失败或重复通过数下降应使回归检查失败；小样本变化表示需要调查，不自动证明因果。
- 源码身份：构建前后核对 `cmd/`、`internal/` 下 Go 源文件及 go.mod/go.sum 摘要，实际程序 SHA256 必须与 runner 元数据一致；该清单是构建输入摘要，不是完整源码备份，也不是自动因果定位。
- 自动化:`.github/workflows/eval-offline.yml` 零模型运行题库校验、判卷反例和报告测试；真实模型评估由明确命令触发，不在不可信 PR 上注入 API key。Judge 只作诊断，不参与自动回归门禁。

## 4. 对照实验纪律

- `cmd/evalcompare -a <目录A> -b <目录B> -factor repair|semantic|builder|screening` 零模型读取两轮产物，复验判卷并要求同清单、同快照、同二进制、至少三次重复和唯一变量变化；报告含逐题胜负和按题目聚类的 bootstrap 区间。
- 对照复验完整产物，包括多轮实际上下文；效果仅在该变量对应阶段计算，其他阶段的题号明确列为排除项。按固定顺序保留每组首跑，不挑选更好看的重复结果。
- 已完成实验(实测见[运行记录](../eval/运行记录.md)):修复环消融(单次组交付 18/93,主要证据是预算调整收益)、语义检索消融(关闭组 93/93 硬分相同，但白色需求命中 Black 型号，说明硬评分未覆盖偏好质量)、两角色模型配对(差异不足以据此选型)、解释质量 Judge(首跑有效 4/18,引用存在不能充当语义正确)。生产机制均保持原设置。
- 实验结论边界：软偏好题判断需候选/选件与命中证据，仅硬校验通过率相同不能判定偏好满足；样本不足不自动选型；遇到模型不可用单列环境结果，不把静默换模型后的输出记到原模型名下。

## 5. 解释质量诊断

`cmd/evaljudge` 使用[固定八题清单](../eval/judge/selection-v1.json)和[评分规则 v1](../eval/judge/rubric-v1.md):范围是冻结运行中的最终选配理由和程序非交付说明，不是网页或重新生成文案。规则锚点由 AI 编程助手编写，独立人工校准未完成——**评分只作诊断，不作发布门禁**。每个解释诊断三次，空理由记 0 档；评分必须给出原文与事实的逐字引用；原文、规则、清单及用量保存后可零模型重放，拒绝事后润色文本。Judge 使用与 Builder 不同模型家族。

## 6. 本机评估工作台

工作台入口 `/eval`。独立 Go 程序 `cmd/evaldesk` 读取已有评估产物，比较和复核留在 Go;Next.js 只代理、展示，不定义另一套判卷规则。

```bash
# 终端 1：默认只监听 127.0.0.1:8086
go run ./cmd/evaldesk -root .
# 终端 2：显式开启本机评估代理
cd web && EVALDESK_API_BASE_URL=http://127.0.0.1:8086 pnpm dev --hostname 127.0.0.1
```

无需 PostgreSQL、Redis、生产 API 或模型凭据；不执行真实评估。`-addr` 只接受 loopback;生产启动不设置 `EVALDESK_API_BASE_URL`。

- **评估运行**：按产物时间查看历史成绩与调用量；展开“版本证据与完整性”查看原始标识及缺项。
- **运行对比**：显式选择基线与候选，先看“改了什么”(模型配置、实际程序、题库与商品数据分类)，再看共同题指标增减、退步与调用变化。基线不代表官方标准。
- **代码提交记录/溯源时间线**：只列评估产物关联的提交，串起运行、题库、模型配置和当时 Git 提交；缺运行时间的记录归入“时间未记录”。提交文件列表来自该提交相对第一父提交的变化，不包括运行时未提交改动。
- **题库与评估集**：按完整有效内容指纹分组；不同指纹分别展示，不因版本名相同断言题目相同。题库详情支持按题号/标题/输入搜索，展开逐轮冻结输入、期望摘要和完整期望。
- **指标口径**：“执行通过”按一次题目重复计数；“全部重复通过”要求每次重复均通过且无 veto/data-error,重复数未记录时比例未知，不推测 Pass³;跨题库比较仅完全相同的共同题进入差异；多因素或证据不足降为观察比较。原成绩保持原样，统一复核用当前 `independent-v2` 在内存计算。
- **只读边界**:`internal/evaldesk` 只扫描 `artifacts/eval` 和 `artifacts/evalchange`;运行 ID 是相对路径生成的不透明标识，请求不能指定任意文件路径；DTO 字段白名单和脱敏，不发送完整模型配置、候选目录、原始日志或本机绝对路径；API 无写路由、无 CORS 授权，响应 no-store。不提供自动运行、基线升级、定时评估或完整源码 diff。
- 测试:`go test ./... && go vet ./...`,`cd web && pnpm typecheck && pnpm lint`,`pnpm exec playwright test --config=playwright.evaldesk.config.ts`(默认只跑桌面 1440×960)。真实历史样本不入 Git,缺失时相关测试明确跳过。

## 7. 反馈与评估回流

- **最小闭环**：工作台对有运行 ID 的已结束助手回复提供“不满意”入口，选择原因并填说明。只接受自己会话内的运行；相同运行只保留一份当前反馈，重复提交相同内容返回同一记录。归属检查在数据库查询中再次执行。
- **证据记录**：反馈保存运行 ID、原因、说明及提交时冻结的证据副本(输入、输出、模型配置来源、实际保存版本)，证据哈希用作 fingerprint;不记录 API Key、DSN、Cookie。历史运行未捕获的证据明确标缺，不取当前需求或模型替代。运行终态及最终可见消息来自数据库，反馈首次提交时一起冻结，之后的对话和编辑不改变这份证据。
- **导出与人工复核**:`go run ./cmd/feedbackexport -id <反馈UUID>` 仅按明确反馈 ID 导出本机待复核候选到 `var/data/feedback-candidates/`(含证据、反馈、`pending_review` 状态、空标准答案)，不调用模型，不写正式 fixtures。复核流程：判断问题属于模型/程序/数据/判卷 → 脱敏 → 用证据或独立判断确定正确行为 → 必要时构造正反例并冻结新版本，不改写旧题换取通过率 → 固定模型与快照回归。
- 该功能收集问题线索，尚不实现自动归因、自动脱敏、自动金标或自动冻结题库。

## 8. Jev 影子意图评测（evaluation-first，未接入生产）

`internal/decision` 定义有界意图契约（`collect`/`confirm`/`plan`/`ambiguous`），`internal/providers/jev` 用标准库实现 TypeSafe SystemOne `POST /v1/systemone` 的单个 Choice 问题（固定问题定义 SHA256 进 provenance）。Jev 只在显式评测模式下可达：`internal/product.Service` 不引用它，无生产 `JEV_MODE`，无后台 worker，不改任何产品结果。

```bash
# 冻结意图套件自检（零调用）
go run ./cmd/evalplanning -mode check -suite internal/planningeval/testdata/jev-intent-v1/suite.json
# 影子评测：录制的 Screening/Builder oracle + 真实 Jev 调用
JEV_API_KEY=... go run ./cmd/evalplanning -mode shadow-live \
  -suite internal/planningeval/testdata/jev-intent-v1/suite.json \
  -out artifacts/jev-shadow-<新目录> -jev-model jev-1.13.0 \
  -jev-max-calls 70 -jev-timeout 2s \
  -jev-input-price <元/百万输入token> -jev-output-price <元/百万输出token>
# live 模式并行观测 Jev（可选）：-jev -jev-max-calls <正数>
```

- **凭据与预算**：`JEV_API_KEY` 只从环境/`.env` 读取，`JEV_BASE_URL` 默认 `https://api.typesafe.ai`；缺失密钥在建输出目录前失败。`-jev-max-calls` 必须为正，且与 Screening/Builder 的 `max-calls` 分开记账；预算耗尽或请求前证据落盘失败即中止，provider/合同失败只记录在该步，不改变产品判定。plan.json 在首次请求前写入 model、endpoint host、timeout、问题哈希、套件/目录/二进制哈希与调用上限；日志与报告不含 Key 或 Authorization。
- **输出**：`report.json` 的 `intent` 段含调用/成功/失败分类、歧义计数、延迟 p50/p95、token 与按显式费率的现金估计、逐意图混淆矩阵、与最终 Screening `next_action` 的一致率（≠正确率），以及 confidence 与 selected probability 两条独立阈值曲线（校准分割选点、会话不相交保留分割报告一次；空接受集的 precision 记 undefined 而非 100%）。`correct_share` 是假设存在确定性路由资格策略时的上界，不是已实现的生产削减。`events.jsonl` 逐请求保存脱敏证据。
- **数据集**：`internal/planningeval/testdata/jev-intent-v1/`（37 案例、63 个带标注 message 轮）由 current-178 三个套件（同一冻结目录）加 6 个手写 oracle 的合成意图用例组成；每条标注按现行初筛动作契约逐条复核，复核说明与边界轮理由在 provenance.json。`intent_split` 按案例（会话）轮转划分。
- **已知边界**：confidence 不是正确率概率；首轮"点名执行"被产品首次确认门覆盖（标注为最终状态动作 confirm）；套件继承源冻结件的 4 个已知 red 检查（C123-002/003/005 与 R-REF-01#2，与原始套件本机 replay 基线一致，不影响 Jev 观测）。标注为 AI 辅助复核（2026-09-22），63 轮只支持方向性结论，不支持生产精度承诺；是否开生产 Shadow change 按 change 文档的 Follow-on gate 判定。

## 9. Requirement v2 评估（evaluation-first）

`internal/planningeval` 内新增 v2 契约（`requirement_v2*.go`），入口 `cmd/evalrequirement`，数据集 `internal/planningeval/testdata/requirement-v2/`（六层：extraction/reducer/readiness/policy/conversations/ui-contract + manifest/provenance/gates/selftest）。判卷版本 `reqv2-grader-v2`（provider/延迟/单轮调用与预算一致性统计模型层全部真实 provider 轮；跨 grader 版本走显式 regrade，v1 产物以 superseded 归档），金标按五份 v2 change spec 冻结并经 2026-09-22 人工复核 16/16 接受；当前 v1 实现的 red 是预期证据。详细口径、split、gates 与冻结基线见 [requirement-v2](../eval/requirement-v2/README.md)。

- **模式**：`check`（零网络校验 fixture/manifest/split/gates + 9 项 veto 的 grader 反例与通过样例）、`live`（确定性层零模型 + 需要数据库的 policy/ui 层 + 真实 Screening 的 extraction/conversations 层；显式正数调用预算、新输出目录、plan/provenance 在首次请求前落盘）、`replay`（零模型重判冻结观测，不信任旧分数）、`compare`（零模型配对对照，同 manifest/grader 才可比，样本足够时精确 McNemar）、`freeze-manifest`（显式重算清单，需人工复核）。
- **适配器边界**：readiness 适配自 `schemas.RequirementStateSpec`（blocking 分离与系统默认记 contract gap，不伪造）；policy/ui/extraction/conversations 驱动真实 `product.Service`（隔离 peval_ 库），scripted screening 轮是适配器输入（含 guard 纠偏重调的第二条 oracle），builder 用 scripted-error oracle——Builder 输出质量归 planning-v2，本评估只看 admission 行为。
- **纪律**：holdout 会话级锁定且不得与其他 split 混跑；确定性层必须 100%，模型层平均分不能抵消 veto；失败分类区分 v2 契约缺口与行错误；产物不含凭据或隐藏思维链。
- **门槛与统计**：模型质量阈值已冻结（extraction op precision ≥0.95 > recall ≥0.80、forbidden op 零容忍；conversations 任务成功 ≥0.80、veto 零容忍），`check` 拒绝 pending/非法阈值；compare 只统计模型层独立 case（repeat 折叠为 pass^k，确定性层单独报告，<30 例声明样本不足）；金标人工复核表在 [requirement-v2/人工复核](../eval/requirement-v2/人工复核-20260922.md)。
