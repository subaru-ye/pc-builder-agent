> **来源与口径**

> 本文聚焦 Agent 的评估方法论,与同目录的项目差距分析、落地建议配套阅读。
> 本文只做书本方法论的忠实提炼,**不涉及本项目映射**;配套的项目差距分析与落地建议文档已于 2026-09-22 清理,当前能力见 [评估设施](../../tech/评估设施.md)。

全章回答一个问题:**怎么判断 Agent 变好了还是变坏了**。链条由四个环节构成,每个环节都会影响结论的可信度:

1. **什么算成功**——指标口径(Pass@k / Pass^k / Best@k);
2. **任务从何而来**——公开基准、自建业务集、生产轨迹回流;
3. **由谁验证**——确定性验证器 → Rubric + LLM 评判 → 配对比较的谱系;
4. **分数如何转化为决策**——统计显著性、失败归因、回归任务、模型选型。

本章在全书"发现循环"中承担**证据**段:失败归因决定了后续改进提案有没有可依之据。核心方法论一句话:观察 → 假设 → 实验 → 验证 → 新认识 → 新假设,使 Agent 工程从经验驱动的"炼金术"转向数据驱动的科学工程。

## 一、评估对象:模型 + Harness 的组合体

构建 Agent 时的大量设计选择(选什么模型、给哪些工具、提示词怎么组织)没有显而易见的答案,评估提供科学的决策依据,基本手段有两种,不要混淆:

| 实验 | 操作 | 回答的问题 |
|---|---|---|
| **消融实验(Ablation)** | 固定模型,逐一关闭 Harness 的某个组件,看整体性能变化 | Harness 内部**哪个部件**重要 |
| **模型替换(Model Swap)** | 固定 Harness,只更换更强/更弱的模型,观察分数变化幅度 | 瓶颈在**模型**还是在 Harness |

换强模型分数不涨 → 瓶颈在 Harness(改提示词、工具设计、反馈循环,而不是换模型);换弱模型分数大跌、随模型能力大幅波动 → 当前表现主要由模型能力决定。

评估体系在模型快速演进时代的额外价值:新模型公开基准更好 ≠ 在你的任务上更好(可能出现 regression);只有在自己的评估集上完整测试,才能做数据驱动的升级决策。更进一步,完善的评估体系使"**为未来的模型开发产品**"成为可行策略——先完成产品并建立评估集,持续追踪新模型,一旦达标立即上线。

## 二、一条评估任务的解剖:τ²-bench 的 telecom 领域

τ²-bench(Sierra 开源)是人机交互型评估的范本。一条任务定义包含四个组成部分:

1. **ticket**:给 Agent 的工单(用户的初始表述);
2. **user_scenario**:给用户模拟器的行为规范,内分 `known_info`(用户知悉的范围)与 `task_instructions`(透露方式、情绪设定、验收口径、事实锚定要求);
3. **initial_state**:`initialization_actions` 重置脚本,运行前把两侧状态拉回同一起点;
4. **evaluation_criteria**:评分标准。

四个设计要点:

- **渐进式信息透露(Progressive Information Disclosure)在任务定义层实现**:真正的故障原因不在 `known_info` 里,用户无从主动陈述,Agent 只能通过提问和引导获取。不是靠一句"不要一次说完"的提示词约束模拟器,而是把用户的知识范围建模为独立字段。真实用户的初始表述往往只是"我上不了网"——**把需求澄清到可执行的程度,本身就是被测能力**。
- **防止用户模拟器被 Agent 忽悠**:`task_instructions` 含三类约束——情绪设定(首次修复失败后表现轻度不满)、验收口径(仅当测速结果为 excellent 才算解决,poor/fair/good 均不接受,针对**敷衍性修复**)、**事实锚定(Grounding)**(关于设备状态的回答必须以工具返回为依据)。缺少事实锚定时,模拟用户会顺应 Agent 确认"问题已解决",评估退化为两个模型互相确认。
- **双方都不具备完全信息**:部分开关在用户侧、部分配置在运营商侧,故障位于数据库不可见的一侧,只有引导用户操作才能发现。
- **双控(Dual-Control)环境**:模拟用户拥有一套独立工具集(查状态栏、开关飞行模式、测速等),Agent 必须引导用户执行并**重新调用工具**才能获知结果。

**评分标准的四层检查**,按 `reward_basis` 聚合(此处为二元):`env_assertions` 查终态、`actions` 查关键动作是否发生、`communicate_info`/`nl_assertions` 查必要信息是否告知用户。

**二元奖励的固有代价**:以过程颗粒度换跨模型可比的单一数字。一条满分轨迹中 Agent 一次发出两个工具调用、违反"每次只调一个"的政策,验证器没有捕获——因为 reward_basis 只看终态。生产评估系统往往需要更多:不仅判定对错,还要指出问题出在哪里(见失败归因一节)。

## 三、评估指标:成功的定义

同一个数字在不同业务里含义完全不同:0.8 的通过率对退款客服不可接受,对漏洞挖掘 Agent 已相当可观——差别在业务场景对成功率的要求。两个关键口径:

**Pass@k(能力上限,"技术奇观")**:同一任务运行 k 次,至少一次通过即算通过;连续得分取最好记 Best@k。公式:`Pass@k = 1 − (1−p)^k`。适合科研发现、漏洞挖掘等"给足探索预算后出现一条突破性轨迹"的场景——人类可以从 k 条候选里挑最好的那条。

**Pass^k(业务可靠性,"连续 k 次全对")**:同一任务连续运行 k 次,**每一次**都通过,且不触发安全、合规、幻觉等一票否决项。公式:`Pass^k = p^k`。它回答"能否稳定可靠地交付",而不是"能否偶尔创造奇迹"。

单次成功率 p=0.6、k=5 时:Pass@5 ≈ 99.0%,Pass^5 ≈ 7.8%。**前一个数字适合衡量探索天花板,后一个才接近支付、退款、生产部署类场景的可靠性要求。**

三条配套纪律:

- 评估报告必须写清 k 次口径:是同一任务的 k 次独立采样,还是流水线上连续 k 个任务;
- 有副作用的操作不能"重试直到成功",应在沙盒或可回滚环境采样,每次失败都记入可靠性指标;
- 安全合规遵循零容忍:一票否决,不因其他维度优秀而豁免。

## 四、评估环境:五个组成要素

评估环境是一套可重复运行的装置:同一初始状态 + 同一 Agent → 可比较的结果。五要素缺一,评估便无法构成可重复的循环:

| 要素 | 内容 | 关键要求 |
|---|---|---|
| **数据集** | 任务文件:初始状态 + 工单 + 模拟器规范 + 验收标准,一条记录即一个用例 | — |
| **环境状态** | 执行中的可变信息(数据库、设备开关等) | **可重置**(初始化脚本)、状态变化符合业务逻辑 |
| **工具接口** | Agent 侧与用户侧两套工具 | **原子操作**,不存在"解决用户问题"式高层抽象——抽象层次过高会把规划与推理环节吸收进工具,评估退化为单次函数调用考察 |
| **评分标准** | 多层检查 + 聚合规则(reward_basis) | 机器可独立复核 |
| **执行协议** | 交互顺序与终止条件(停止信号、轮数上限、模拟用户耐心耗尽即终止) | **沟通效率过低本身计为失败** |

按是否有对话对象分两类:

- **工具调用型**(代码、数据分析、数学):无交互对象,正确性由执行验证决定。Verifiers 框架按"是否保持跨轮状态 / 是否需要隔离"分级:

  | 环境类型 | 状态保持 | 工具调用 | 典型用例 |
  |---|---|---|---|
  | SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
  | ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
  | StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
  | SandboxEnv | 有+隔离 | 多轮 | 代码执行与测试 |

  工具失败时应返回清晰的错误信息而非单一失败标志,让 Agent 能据此调整策略。
- **人机交互型**(客服、技术支持):必须有用户模拟器,考察沟通策略的合理性。前者验证**行动**,后者验证**引导**。

## 五、评估数据集的设计

### 基准横向对照

| 基准 | 被测能力 | 任务来源 | 环境扮演者 | 验证器 |
|---|---|---|---|---|
| τ²-bench | 客服人机交互 + 工具调用 | 人工编写 + 组合生成 | 用户模拟器 + 业务数据库 | 四层检查按 reward_basis 聚合为二元 |
| SWE-bench Verified | 软件开发 | GitHub 真实 issue 人工筛选 | 代码仓库 + 测试套件 | FAIL_TO_PASS / PASS_TO_PASS 双重验证 |
| AndroidWorld | Android GUI 操作 | 参数化模板实例化 | 真实 Android 模拟器 | 最终 UI 状态断言 |
| OSWorld | Linux 桌面 GUI 操作 | 从预置中间状态启动 | 真实虚拟机 | 134 个独立评估函数 |
| Terminal-Bench | Linux 终端操作 | 人工编写 | Docker 容器 | 文件系统检查 + 真实执行 |
| GAIA | 搜集信息的通用助手 | 人工编写 + 专有附件 | 开放互联网 | 精确字符串匹配 |

### 验证器:核实事实,而非自我陈述

Agent 很容易写一篇洋洋洒洒的报告声称完成,评估框架必须核实**机器可独立复核的事实**:

- **SWE-bench Verified 把"修复完成"拆成两个独立命题**:FAIL_TO_PASS(修复前失败、修复后通过,证明问题确已解决)+ PASS_TO_PASS(修复前后均通过,证明未引入新缺陷)。只查前者,Agent 可以删改断言蒙混;只查后者,等同未检验。另确认测试自身稳定,排除 flaky test。
- **OSWorld 的 134 个评估函数**能发现"表面完成、实质错误":确认报告文件存在之外,还连接数据库核实 SQL 真实执行、分析 DOM、查 cookie/localStorage、向后端发验证请求确认表单生效。
- **Terminal-Bench** 的内核编译任务要求在 QEMU 启动日志中出现自定义 printk——Agent 无法伪造输出,只能真正完成全流程。

### 难度划分、陷阱与防泄漏

- **难度分层兼具诊断价值**(GAIA 466 题三级):Level 1 失败指向基础工具使用,Level 2 指向多步规划与信息整合,Level 3 指向长序列复杂性管理——各层对应的改进方向不同。分层也让评估集不会随模型进步快速过时。
- **陷阱任务**(τ²-bench):用户声称"客服已批准取消"但实际不符政策,检验 Agent 在压力与误导下能否维持正确判断。
- **防泄漏三招**:GAIA 答案必须组合多个信息源 + 专有附件,无法单页检索;AndroidWorld 参数化模板每次随机实例化,回放固定序列失效、单模板生成近乎无限实例、固定部分参数可精确测量特定因素;Terminal-Bench 题面嵌 canary GUID,模型能输出即证明泄漏已发生(不阻止但可检测)。

### 质量控制:评估集是逐轮修补的产物

- **τ-bench → τ²-bench 的五处重设计**:①任务指令笼统致答案可猜 → 拆 known_info / task_instructions;②成功条件不精确致误判("网络恢复"→"测速 excellent 才算解决");③模拟用户机械 → 补情绪、耐心上限、事实锚定;④引入双控;⑤任务实例参数化批量生成(同时改善覆盖率与抗泄漏)。
- **SWE-bench Verified 发布前淘汰 71%**:2294 题抽检 1699 题、93 名开发者逐条审查,仅 500 题通过。高淘汰率带来高信噪比,评估成本反降约 80%(前沿模型跑一个评估集成千美元 token,降本很重要)。
- **OSWorld 发布后 15 个月暴露 300+ 问题**,归为四类:环境问题(反爬/CAPTCHA/动态内容)、任务描述歧义、验证逻辑过严过松、初始状态不完整——分别以锁定版本离线备份、改写表述、人工建基线调条件、完整性校验解决。
- **人肉执行基准任务**(实验 7-2 的方法论):完成后回答两问——任务描述是否存在多种合理解释,验证器认可哪一种?若想蒙混过关,成本最低的路径是什么,验证器能否拦截?

### 评估集的三个来源

1. **公开基准**:粗筛模型、借鉴设计手法,**不用于产品决策**——其任务分布与业务分布不一致,GAIA 上涨两个点与退款成功率无必然关系;
2. **自建业务集**:覆盖真实任务分布,是模型选型、Harness 设计决策的依据;τ²-bench 可作为"需要仿真用户的评估系统骨架",换领域数据与工具集即得;
3. **生产轨迹回流**:线上真实失败(用户明确纠正、点踩、事后状态检查/规则验证器/LLM 评审发现)经失败归因沉淀为回归用例。**成本最高、准确性最高**。

起步阶段只有公开基准 + 少量手写业务集;上线后,回流用例会成为主体。

## 六、自动化评估方法:验证方式的谱系

公开基准的验证器几乎都是确定性的——不引入模型开销、完全可复现、可像单元测试一样纳入 CI、便于跨模型排名。代价:只知结果对错,不知错因;且许多判断(投诉回复是否得体、报告是否遗漏关键信息)根本写不成代码断言。

因此生产评估沿"**可机械验证程度**"这条谱系向右移动:

```
确定性验证器 → 检查项清单(Rubric) → LLM-as-a-Judge → 配对比较
```

**向右移动不等于放弃左侧**:凡能写成程序化断言的检查都应继续用断言(更便宜、更稳定、适合长期回归);LLM 评判只用于确实无法机械判定的维度。Rubric + Judge 把笼统失败率还原为可着手修复的具体问题,再配合失败归因,构成生产评估的完整闭环。

### LLM-as-a-Judge 与 Rubric

开放式任务无标准答案、人工评估难规模化,LLM 按专家定义的 Rubric 逐项打分并说明理由,在自动化规模与专业判断之间取得平衡。

**Rubric 四准则**(Scale AI,"Rubrics as Rewards"):

1. **基于专家指导**:反映领域知识,捕捉核心事实与推理步骤;缺乏专业基础的 Rubric 只能捕捉语言流畅度等表面特征;
2. **全面覆盖**:覆盖事实准确性、逻辑连贯、完整性、安全性,不仅定义正面标准,还要明确**陷阱(Pitfall)**——高风险常见错误;
3. **按重要性加权**:分必要项(Essential)/重要项/可选项/陷阱项,支持**一票否决(Veto)**——如客服场景的幻觉:无论其他维度多优秀,出现虚假信息即判零;同时防关键词堆砌式奖励作弊;
4. **评价标准自包含**:每项独立可操作,不依赖评价者领域知识。避免"回应展示了深刻理解",改写为"引用了至少两个权威理论并准确解释如何支持结论"。

配套实践:为每个维度定义客观可验证的评分档次(优秀/良好/及格/不及格),提供示例和**边界案例**;主动防**奖励作弊(Reward Hacking)**——明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题;Rubric 靠试用中的评价者分歧不断迭代,从抽象准则演化为详尽判例集。

书中示例(用户记忆 Agent,"我女儿的儿科医生是谁?"需跨两次对话关联):事实正确性(必要项,四档写明"准确回答 Dr. Chen 且关联到女儿 Lily"→"回答不知道")、信息完整性(重要项)、思考正确性(重要项,是否正确关联两条跨会话信息)、**幻觉检测(否决项:编造对话中不存在的信息即总分归零)**;边界案例如"多个女儿分别看不同医生应追问"。

汇总几十个用例的逐项分数后回看低分轨迹,笼统的"成功率下降"就能拆成几类具体问题——**Rubric 不只告诉我们得了多少分,还告诉我们下一步该改哪里**。

### 评判模型的已知偏见与对策

- **长度偏差**:偏爱更长更详尽的回答。对策:Rubric 显式惩罚冗长、同类任务设长度上限;配对比较前把候选长度对齐;**定期审计评分与回答长度的相关性**——高分几乎总伴随长回答即已被带偏。
- **同源模型问题(古德哈特定律)**:度量指标一旦成为优化目标就不再是好指标;Agent 与评判模型同家族时,会学会利用其偏好盲点、避开其检测不到的错误类型。对策:**多源异构评判**——用不同模型家族的多个 LLM 用同一 Rubric 分别评判(不同家族偏见正交,难以同时欺骗),加权平均或一致性检查聚合;日常单模型快评,定期多源审计。
- **多模态评判**(TTS 准确性/自然度/情感/音色、ASR 语义影响判断、UI 提议者-审核者、视频关键帧):把评判从文本扩展到其他模态。书中 TTS 实验的教训:**选什么参考音频/图片本身就是评估设计**,不是开始前的准备工作。
- 评估规模再扩大时,可训练专门的**生成式奖励模型**自动打分(第八章)。

### 失败归因:从整条轨迹定位首个错误

端到端评估只给成功/失败,不回答"为什么失败、从哪一步开始"。要让评估驱动修复,必须对失败轨迹做**失败归因**:标出主要错误类别、**首次出现不可接受行为的步骤**、对应工具调用或模型输出,附可复核证据。归因对象是**首个导致任务偏离的错误**——后续错误往往只是连锁反应,不能把最后一个报错当根因。

生产问题案例的三个信号来源:①用户明确纠正;②用户点踩/负面反馈;③事后状态检查、规则验证器或 LLM 评审发现的不当行为。

**归因标注可以借 LLM 规模化,但不能全靠 LLM——失败归因往往反映产品问题,不止技术问题。**错误分类可发展到大类套小类、多达数百种,分类体系本身就是归因 Agent 的提示词/Skill。

书中以 Coding Agent 为例的九类错误(结构:错误类别 / 典型表现 / 首错定位方式):

| 错误类别 | 典型表现 | 首错定位方式 |
|---|---|---|
| 需求理解与歧义处理 | 做出来的不是用户要的;两个同名配置文件直接选一个不追问 | 原始需求与实际动作序列逐条对照,定位第一处偏离再回溯 |
| 流程与规范缺失 | 未跑测试就提交;绕过既定架构约定 | 找第一次违反流程约定的动作,回看之前是否读过约定来源 |
| 工具调用错误 | 反复编辑失败;schema/参数格式错误;转义抄写错误 | 记录第一次失败的工具调用与原始请求、错误返回;重复失败属后续症状 |
| hack 验证环境 | 改断言、加 skip、mock 被测逻辑;声称通过但没跑 | 取第一次改动测试/验证逻辑的 message;完成声明与轨迹中真实执行的命令交叉核对 |
| 修改不完整 | 改签名漏改某处动态调用/schema | 声称影响面与真实影响面做集合差,取第一个遗漏项,回看检索关键词 |
| 对用户的信息反馈错误 | 工具与环境全对,答复却错了金额/状态;把部分做完说成全部 | 每个事实断言与工具返回逐条对齐,取第一条无法溯源或矛盾的 |
| 非功能性回归 | 改公开 API/schema 而无迁移脚本;删校验换通过 | 取第一次做出改动的 message,看是否意识到动的是公开接口 |
| 模型执行异常 | 输出截断、无故停止、超时 | 定位第一个异常终止点,区分模型停止/Harness 超时/工具故障 |
| 过早停止任务 | 多目标只完成一部分;未穷尽方案就宣布不可能 | 定位第一次遗漏目标或放弃探索的决策,与最终验证失败分开记录 |

**归因记录必须结构化**(JSON/YAML),引用具体步骤号、工具名、观察证据,区分根因与后果、判断可恢复性、给出置信度。例:`edit_file` 匹配失败后连续三次重试——主因是"文件编辑与工具调用错误"一类,三次重试是**后果**而非三个独立根因。多类并发时按"**最早且能解释后续失败**"原则选主因,其余记次因。保存归因记录时,连同任务目标、环境状态、Agent 版本、工具集版本、完整轨迹一起存,以便回归测试。

**规则先筛、LLM 再定位**:九类中至少三类可先规则筛嫌疑轨迹再交 LLM——完成声明与实际执行命令交叉核对、diff 是否触及断言与 skip、diff 是否改公开 API 而无迁移。比全量喂 LLM 更便宜也更准。

三个深度案例的教训:

- **"做对了但说错了"**:τ²-bench 公开基线中,带信息告知要求的 704 次运行失败 240 次,其中 162 次信息告知出错;**80 次(占失败的三分之一)环境状态正确、信息告知错误**。多数评估只检查环境状态,这类失败被整体成功率掩盖——验收应对答复内容本身设断言,而不只查环境终态。
- **根因别归错(AndroidWorld T3A)**:转录图片内容的任务,Agent 第 8 步思考里已写"I cannot actually see the content",既不停下也不报告,第 11 步四条开销数据凭空出现,此后全部基于幻觉数据推进——全程无工具报错的**静默失败**。根因最初被记成"视觉模型缺乏 OCR 能力",但 T3A 的观察空间里根本没有图像像素:**真根因是 Harness 的观察通道缺失**。归因记错,改进方向就会错(去换模型/做 OCR 训练,而真正该做的是补观察通道)。
- **静默失败的两种定位法**:①**事实锚点比对**——把 Agent 陈述与工具返回逐步对齐,取首次背离;②**轨迹前缀二分**——把轨迹截到第 k 步交人接手,能救回来说明错误在 k 之后。不能用搜索报错关键字代替。
- **精确复制错误的逐层定位**(工具开发向):对同一字符串保存原始字节哈希、Unicode code point 序列、tokenizer token ID 序列,沿"文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文 → 模型输出 → 解码 → JSON/tool-call 解析 → 工具匹配"找首个差异。模型在直接探针中输出正确而工具调用失败 → 修 tokenizer/序列化/Harness/工具协议;首个差异确在模型输出,才转训练数据。

### 回归任务的两层结构

失败归因的产出要写成可重复执行的测试用例,即**回归任务**,两层互补:

- **端到端回归任务**:从初始状态和用户请求出发跑完整任务,检查最终状态、必要输出与安全条件。最接近生产结果,但难以定位失败发生在哪一步。公开基准(OSWorld、τ²-bench 等)都属于这一层。
- **轨迹前缀(trajectory prefix)回归任务**:把已有上下文、对话、工具返回、环境状态**冻结**下来,只要求 Agent 思考并执行下一步或下几步可观察动作。成本更低,能隔离单个策略或工具问题。**对高可靠性生产 Agent,前缀回归任务集往往比端到端更重要。**

关键设计:前缀回归的答案定义为**可接受动作集合**而非唯一动作——可以要求"先读仓库规则""先询问用户""拒绝危险操作",同时列出**禁止动作**。按错误类别构造:流程缺失→带计划文档与测试验收的端到端用例;工具调用错误→截断出错前缀测修正;执行异常→加截断/超时/故障恢复场景;需求歧义→冻结多解任务,把"先澄清"列入可接受动作;症状修复与验证造假→验收补"不得修改测试断言""完成声明必须附真实执行过的命令输出"两条硬约束;信息反馈类→对答复内容设断言。

一个实证(实验 7-7,用户记忆的三种上下文表示):同一组 11 个边界用例 × 3 种语义等价表示,总成绩都是 6/11,但**失败位置并不相同**;三类表示都没通过"过度泛化、过时偏好覆盖当前要求、高风险删除前确认"。教训:改变上下文的表示方式不会自动修复应用策略;**"获得一条信息"和"正确地将它用于当前决策"是两种不同能力**,端到端回归保证任务不退化,前缀边界集直接检查作用域判断、指令覆盖、澄清与危险确认。

### 配对比较与模型排名

"A 和 B 哪个更好"可不依赖绝对分数:**Elo 评分**(Bradley-Terry 模型的在线更新实现)通过大量两两对决收敛出相对实力,分差越大预期胜率越高,爆冷带来更大调整。Chatbot Arena 用匿名盲选数百万投票,局限是排名受用户问题分布影响。

LLM 做配对评判须防**位置偏差**(系统性偏向先出现的候选):标准做法**交换顺序各评一次**取平均;更严格的做法是两次判决一致才计入,不一致记平局或送人工复核。

## 七、评估驱动的模型选型

### 关键维度

- **吞吐与延迟分两段看**:Prefill(一次性读入上下文)决定**首字延迟 TTFT**,上下文越长越慢;Decode(逐 token 生成)决定出字速度与思考时长(50 tokens/s 生成 2000 思考 token 要 40 秒)。思考 token 用量各模型差数倍且与效果不一定正相关,须在自己的负载上实测。看 **p95 尾部延迟**而非均值——均值会被大量快速请求拉低。
- **性能指标按场景取**:日常看 Pass@1;关键操作优先 Pass^k;探索性任务优先 Pass@k/Best@k。
- **成本**:便宜但成功率低的模型因频繁重试,实际花费可能更高;算每任务平均成本与成本-性能比。
- **速率限制与鲁棒性**:RPM/TPM、高峰动态限额;分布外数据、对抗输入、长时运行稳定性。
- **预算–能力曲线**:固定预算的单点成绩不能外推长程能力。RE-Bench 人机对照:2 小时预算下最佳 Agent 约为人类专家 4 倍,8 小时时人类反超,32 小时约 2 倍——**须在接近真实任务时长的多个预算点上比较**。
- **异构模型组合**(轻量模型处理简单请求 + 强模型处理复杂任务)需通过评估验证整体效益、检查性能回退(简单问题误路由到轻量模型的决策错误)。

### 模型的行为策略

选型还要比较"默认会怎样做"。同一代码任务,有的模型先广泛探索再修改,有的凭局部证据快速定位先改再补——行动阈值差异来自系统提示词与后训练塑造的工程习惯。测量方法(实验 7-9):固定 Harness、中性提示、多题多次,统计首次修改前的工具调用数/读文件数/时间。书中实测:两个模型的工具步数差 50%,但首个受测补丁与最终测试全部通过——**证据支持"行动策略随模型而变",而非"多读或早改必然更好"**;工具步数、并行调用与模型延迟要分开看。

### Agent 系统的成本分析

成本三层构成,Agent 场景呈非线性增长:

1. **模型推理**:两个放大因素——**上下文累积效应**(每轮重发全部历史,3 轮总量 1000+2000+3000=6000 而非 3×1000;KV Cache 未用好则更甚)与**思考 token 成本**(不展示给用户但计费)。
2. **工具调用**:外部 API 计费、沙盒资源,及易忽视的间接成本——**工具返回注入上下文后在后续每轮反复计费**(一次网页搜索可占 2000–5000 token)。
3. **基础设施**:向量库、消息队列、日志与追踪存储。

书中八轮客服任务的实测对照:基线每轮输入从 1113 token 涨到 3668;**仅稳定前缀(KV Cache)省 28.3%,仅压缩历史省 17.5%,两者合用只省 30%——不是相加**,因为压缩历史同时缩短了可命中缓存的前缀。**多项上下文优化合用时必须在完整任务中一起实测,不能把各自节省比例相加。**

优化杠杆:KV Cache 复用(保持前缀不变)、压缩上下文、分层选模型——最好都能**独立开关**,既看清每项作用,也检查合用是否互相抵消;再加异步批处理(吃波谷定价)与成本监控(按任务/模型/用户维度追踪,设单任务成本上限,Agent 陷入循环时自动终止)。

### 评估驱动的持续迭代

模型切换决策的正确问法不是"Gemini 是否比 Claude 强",而是"**在我的特定任务上,好多少?切换成本是什么?**"。拥有评估集的团队数小时内可答:新模型简单任务更优更便宜、复杂多轮编排成功率反降 5%——确认差异超出噪声带宽后,决策是"简单任务迁移降成本、复杂任务保留保质量"的**差异化策略**,而非全量切换。这种精细化决策只有在预建评估体系的前提下才可能。

## 八、评估结果的统计显著性

评估集有限、输出随机,分差可能只是抽样噪声。成功率 p 在 n 个用例上的标准误 ≈ √(p(1−p)/n):100 用例 70% 成功率,95% 置信区间约 ±9 个百分点——"73% 对 70%"不足以支持切换。

实务纪律:

1. **分差超过噪声带宽 + 配对分析成立 + 能复现**,三者齐备才值得切换模型或发布改动;
2. 同批任务比较两配置,优先**配对分析**:逐题记录谁胜出,用 McNemar 检验或配对 bootstrap,而不是两个独立成功率相减。配对的含义是两组共享任务与随机条件,不是分别抽两批样本比均值;
3. Agent 每次运行可能不同,每配置用多个随机种子(3–5 次)报均值与波动;单次运行只能筛方向;
4. 预期收益只有 2–3 个百分点而评估集只有几十题 → 先扩样本(标准误按 1/√n 缩小);
5. **多重比较**:并行验证多个假设时收紧显著性阈值(如 Bonferroni)或对正向结果独立复跑。

for task in paired_tasks:

## 九、Agent 的可观测性

无法打开系统内部看它在做什么,只能靠日志、指标、追踪推断。价值:问题诊断(完整轨迹回放,而非靠猜)、持续优化(哪些任务多轮迭代、哪些工具成功率最低、哪些检索总空)、成本管理(不同任务成本差一两个数量级,追踪可定位异常)、为后训练积累数据。

数据基础是**追踪(Trace)**,沿用 span 树模型:一次任务一条 trace,每个 LLM 调用/工具调用/检索是一个 span(输入输出、起止时间、token 消耗、错误),父子关系构成执行树。标准化协议:**OpenTelemetry**(通用分布式追踪)+ **OpenInference**(LLM 语义约定:如何记提示词、模型参数、token 用量)——采集与分析解耦,避免单一平台锁定。代表平台 LangSmith(同类 Langfuse、Arize Phoenix),整合追踪、A/B 测试、提示词版本管理,异步批量采集不影响响应延迟。

**最有价值的去向是回流成评估资产**:生产轨迹筛出失败与可疑案例 → 脱敏(去隐私、密钥)→ 沉淀为评估集新用例与回归测试。评估集从一次性静态集合,变成随产品演化、持续贴近真实分布的**活资产**——今天线上暴露的失败模式,明天就是守住底线的回归用例。

## 十、从 Benchmark 报告到系统改进

**首要原则:看到表现下降,先检查评测系统本身,再动 Agent。**运行环境资源不足(表现为随机失败)、验证器 bug 把正确答案判失败、用例与生产脱节——在结果数字上与模型退化一模一样,只有审查完整轨迹才能区分。基于失真信号调整方向,从一开始就是错的。

读懂报告的方法:**先找失败集中在哪些任务和能力上,再回放轨迹,分清问题出在看、想、做还是验**。只盯总分,小而集中的失败簇会被平均掉;只加最大步数,会把"看不见界面"误诊为"不够耐心"。

书中 AndroidWorld 三轮实验(每轮只改一个变量、固定模型/参数/种子/步数/环境、交替运行顺序):

| 实验 | 只改了什么 | 成功率(对照→实验) | token(实验/对照) | 结论与下一步 |
|---|---|---|---|---|
| H1 | 补导航提示 | 25%→25% | 0.47× | 没用——提示写得再细也补不回 Agent 根本没看到的信息 |
| H5 | 界面观察通道换成完整元素树 | 25%→100% | 2.498× | 方向对但太贵,继续优化 |
| H5C | 删元素树中无语义节点 | 100%→100% | 0.506× | 成功率不变 token 减半,获得完整复测资格 |

三条元教训:①遇到"看不见"类失败,先检查输入而非堆提示词;②输入不是越多越好,信息增量与 token 成本要一起权衡;③**一轮证据只支持与它规模相称的下一步**——H5C 通过 4 项任务只说明值得进入下一轮(标准环境 116 任务 × 5 种子、成功率不降、token ≤75%、延迟 ≤1.5 倍),在完整复测前不能把子集 4/4 写成系统 100%。好的报告不只给分数,还应写清结论适用于哪里、哪些底线没通过、下一轮验证什么。

## 十一、生产级 Agent 的内部评估基础设施

外部评估告诉你"Agent 有多好",内部评估基础设施告诉你"**哪项改动让它变好了**"。五个组件:

1. **消融基础设施**:内置总开关一键禁用主要特性(思考/压缩/记忆/后台任务),得到"裸模型"基线,回答"这个特性是真改善体验还是只是感觉有用"。开关必须在**启动路径极早期**注入(任何模块级常量捕获配置值之前)——消融设施要从一开始设计进架构,不能事后加装;定期消融(如每次大版本发布前)可发现**特性债务**(随模型进化已不再必要的特性)。原则:**每个主要特性都可独立关闭,定期验证其真实贡献**。
2. **AB 测试方法论**:多臂而非二元(多个渐进变体揭示剂量-效应关系);**区分机制指标与目标指标**——正在改变的东西(计划文件长度)不是真正关心的东西(会话级成本),机制改善可能因更多编辑循环反而推高目标,始终自问"我改变的机制和我关心的目标是同一个吗";设**护栏指标**(满意度/操作次数/错误率不能变差的底线,触线即停);记录基线统计(样本量、分布分位、相关性)。
3. **双层特性开关**:编译时开关把代码从产物物理移除(内部特性对外部构建不存在,也是干净的消融机制);运行时开关服务端下发 + 本地磁盘缓存(宁读稍旧缓存也不阻塞启动),分组走实验平台,曝光事件每会话最多记一次防污染。特性开关是**一等架构组件**,同时服务实验、渐进发布、紧急熔断。
4. **提示词敏感性评估**:系统提示是 Agent 的核心"代码",却常缺版本控制与回归测试。要求:①系统提示可**确定性渲染**(相同配置输入永远产生相同输出);②版本化快照机制;③**每次提示词变更都在评估集上跑回归——像代码跑 CI 一样**。配合工具可在指定 git 版本提取完整渲染后的系统提示(含动态条件展开后的最终文本),精确回答"哪次提交改了提示词、对评估集的影响是什么"。
5. **隐私感知分析**:分析接口只接受特殊类型包装的值,类型名即审计线索,把隐私约束从文档规范变成编译时强制。**从一开始设计进去而非事后加装**;隐私约束迫使你想清楚真正要度量什么,反而催生更精准的指标。

## 十二、仿真环境:从评估到后训练的桥梁(概要)

评估的终点是改进,最深的改进路径是训练。评估环境演化为仿真环境的三个变化:交互频率高得多(数百万次 vs 数千次)、需要随机化(防死记硬背)、必须即时反馈。评估资产可近乎无缝转为训练信号:定义清晰的 Rubric/验证器本质就是**可验证奖励(RLVR)**的奖励函数——验证脚本直接是奖励脚本。但训练额外要求:**可靠的 reset 语义**(每个 episode 重置到确定干净的初始状态,否则梯度被残留状态污染)与**远高于评估的吞吐**。数字环境的 sim-to-real 缓解手段是**领域随机化**(随机注入延迟与失败)。详见原书第八章。
